# 需求追溯矩阵（已回填 · 综合方案 v0.1）

约定：
- 需求 ID 沿用简报编号；`R-*` 为需求矩阵补充项（来自截图归纳）。
- `落点模块` 见 `docs/20-synthesis/02-architecture-v0.1.md` §1 的 7 个领域模块。
- 阶段：P0 纯飞书试运行 / P1 凭据服务 / P2 账务闭环 / P3 预算与视图 / P4 可选。
- 数据权属：飞书权威 / 本地权威 / 派生展示。

## C. 待确认细节（简报 1.4 的 20 条）——默认决策

> 说明：以下为**可执行的默认决策**；用户可用一句话推翻任何一条，成本已在"推翻代价"列注明。

| 编号 | 待确认内容 | 默认决策 | 理由 | 推翻代价 |
|---|---|---|---|---|
| Q-01 | 收集表结构（具体字段） | 见综合方案 §4.1：提交侧仅 3 图必填；字段分"必填/OCR 预填/后补"三档 | 提交阻力是项目最大风险 | 中（改表单与 OCR 映射） |
| Q-02 | 是否需要项归属、组间相对归属 | 需要：`group_id` 必填（含子组闭包，支持"本组及其子组"汇总） | 复盘需求 A2.2 的前提 | 低 |
| Q-03 | 信息提交是否需要人工审核 | 提交不审核；审批/付款时刻硬门禁 | 裁定 2：校验放在能拦住钱的位置 | 高（会显著增加队员负担） |
| Q-04 | 数据存储平台 | **飞书为唯一入口与最终交付面；Linux 主机上的 Go 服务做处理路由；SQLite 只存飞书无法表达的 3 类数据** | 用户拍板：入口与交付都在飞书、处理路由到 Linux；数据量小、轻量库、主体 Go | 已定 |
| Q-05 | 上传发票负责人是否兼资金管理 | 默认不兼任（至少票据保管人 ≠ 审批人）；≤2 人时如实记录例外 | SoD 底线 | 低 |
| Q-06 | 个人垫付如何催办/保证上传 | 一律进催办队列；**"不交三图 → 不结清"必须真实可执行** | 否则系统外循环、幽灵交易 | 高 |
| Q-07 | 保底用飞书即可，开发优先级低 | 采纳，成为 **P0**：0 行代码试运行两周再决定投入 | 用真实数据决定后续 | 低 |
| Q-08 | 单条/批量记录更新 | 批量更新必须经本地单表串行队列（飞书同表禁止并发写） | `1254291 Write conflict` | 低 |
| Q-09 | 可识别的截图模板 | 做群置顶样例卡，不做规范文档 | 低成本、高依从 | 低 |
| Q-10 | 提取失败需反馈给提交方 | 失败不阻塞登记；标记 `NEEDS_MANUAL` 私聊反馈；只问 2 个问题 | 绝不重填整表 | 低 |
| Q-11 | 资金来源是新增项还是新增字段 | **新增枚举值**，不新增表/子表 | 同一本账的多个池 | 低（若拆表则查询全部变复杂） |
| Q-12 | 费用类别口径（差旅/物资采购/垫付…） | 建可维护的费用类别字典表（飞书），并作为凭证行属性 | 需要人工维护的枚举 | 低 |
| Q-13 | 个人只能查自己的表 | 免费版无行级权限 → **本地服务裁剪**；付费版用 `rec_rule` | 官方权益表：行列权限为付费档位 | 中 |
| Q-14 | 公示看板是否需要权限 | 需要：禁"人名+金额"组合，用组别汇总+金额区间；某组 <3 人做小样本抑制 | 数据最小化 | 低 |
| Q-15 | 是否需要定期提醒更新 | 需要：催办节奏 D+3/D+7/D+14/D+30；≤2 条/人/周 | 避免催办疲劳 | 低 |
| Q-16 | 固定资产如何自动生成 | P4 可选：以"物资字典 + 单价阈值"规则自动打标资产，不做自动盘点 | 避免过度建设 | 低 |
| Q-17 | 如何让人工登记最少 | 三个杠杆：OCR 预填、历史值默认、一键跳转预填表单；催办自动化 | 直接对应 A3.3/A4.1 | 低 |
| Q-18 | 如何确保每个订单都能开票 | 采购前置约束（下单前提示开票要求）+ 垫付单自动进催办 + 不交票不结清 | 上游问题，不能只靠下游催 | 中 |
| Q-19 | 是否与流水记录独立、成对 | 不独立：**统一入同一本账**（复式分录），采购/报销/垫付都是分录来源 | 避免两本账对不上 | 高（若分家则对账成本长期存在） |
| Q-20 | （与 Q-19 重复） | 同 Q-19 | — | — |
