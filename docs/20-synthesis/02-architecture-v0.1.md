# 财务流程重构：综合方案 v0.1.1

> **v0.1.1 修订（用户已拍板，架构已相应收紧）**
> 1. **交付在飞书、入口在飞书、处理在 Linux 主机** → 本地服务的定位是"**路由与处理器**"（router/processor），
>    不是"另一个面向人的前端"；它对飞书只做**回写镜像与状态**，不做替代入口。
> 2. **明确不考虑 NAS** → 部署收敛为**单机单二进制 + 单个 SQLite 文件**，无跨设备存储、无分布式假设（见 §5，已重写）。
> 3. **数据量很小** → 本地只存"证据与账"（不存原图），存储需求从 GB 级降到**百 MB 级**。
> 4. **欠票主因确认为"懒得填"** → 产品重心定在**下游提交摩擦**（OCR 预填 / 历史默认 / 一键跳转 / 催办节奏），
>    而非上游"约束商家开票"；这提高了 P0 的优先级与验收权重。
>
> 立项目标：把"发票收集 / 流水信息 / 信息查询 / 预算同步 / 采购审批 / 资金返还"六大类需求，
> **替代、分解、归纳、重构**为模块化、可拓展的程序项目。
>
> 证据基础（全部落在本仓库）：
> - 需求：`docs/00-brief/01-requirements-brief.md`（原文需求 + 需求矩阵归纳）
> - 平台事实：`docs/00-brief/02-feishu-capability-facts.md`（**一手官方文档核实**，61 条链接实测）
> - 环境事实：`docs/00-brief/03-host-environment-facts.md`（本机实测）
> - 四份独立方案：`docs/10-proposals/A-feishu-first.md`（飞书极致派）· `B-self-hosted.md`（自托管派）· `C-product-ux.md`（产品体验派）· `D-compliance.md`（合规审计派）

## 0. 一页纸结论

**推荐形态：飞书是"唯一入口 + 唯一交付面（采集 / 审批 / 触达 / 展示）"，Linux 主机上的一台轻服务是"路由与处理器"（router/processor），只持有飞书无法表达的 3 类数据（发票唯一性、账务分录、审计痕迹）。**

> 用户口径：**最终产物交付在飞书、入口也在飞书、处理路由到 Linux**。因此本地服务**不渲染任何面向队员的页面**，
> 它的输出只有两种：① 写回飞书的表/状态/通知卡片；② 需要时的导出文件。这消灭了自研前端的最后一个理由。

三句话版本的架构判断：

1. **平台事实推翻了"纯飞书就够"的所有权假设，但同样推翻了"必须重写一个财务系统"的必要性。**
   飞书有五处硬缺口（无唯一索引、同表禁止并发写、行级权限付费、自动化 200 次/月、审批→多维表格无原生回写），
   其中**只有"发票防重复报销"（简报 A2.3 点名）是必须由自研层硬保证的**；其余四处在明确取舍后可由飞书或本地队列兜住。
2. **数据所有权必须分级，而不是"整体单向同步"。** 见 §3.1 的权威矩阵：飞书是主力载体，
   少数几张表由本地做权威，**权属按字段/表划分并写死，永不允许双向写同一字段**。
3. **归属边界就是用户给的那句话**：入口在飞书、交付在飞书、处理在 Linux。
   本地服务的每一次输出都必须能在飞书里被人看见（写回记录 / 改状态 / 发卡片 / 导出），**没有"只有本地才看得到"的状态**。
4. **数据量小 + 单机 = 不做分布式假设**：单机 Compose、单库、本地磁盘、串行队列即可；
   本地**只存证据与账，不存票据原图**（原图归飞书附件，本地只存 sha256 指纹），存储需求百 MB 级。
5. **立项的第一个里程碑不是代码，是"两周纯配置试运行"。** 先用零代码方案验证"队员到底会不会交票"，
   用真实数据决定后续投入；这也正是自托管派与飞书派都同意的交集（B 方案自己也把纯飞书列为第一阶段）。
   **用户已确认欠票主因是"懒得填"** → 这个试运行的核心指标就是"提交摩擦是否真的降下来了"。

**对我而言唯一不可让步的一点**：发票唯一性与审计痕迹不能停留在"公式标红 + 人工眼力"。
这两件事一旦出错，代价是"全队被学校财务处追问"，而它们的实现成本约为**一个进程 + 三张表 + 约 200~400 行代码**。

## 1. 六类需求的重构（问题空间 → 领域模块）

四个派别各自做了重构，收敛后一致的是：需求矩阵的"6 大类"是**按组织分工切的**，不是按系统职责切的，
因此直接照抄会得到互相渗透的模块。重构后按"领域职责"切成 **6 个域 + 1 个横切**：

| 领域 | 一句话职责 | 吸收的原需求（ID） | 数据权属 |
|---|---|---|---|
| **1. 采集域 Intake** | 把三张图 + 最少字段变成一条**可被三单匹配**的申请 | A1 A3.3 R-01 R-08 R-11 R-12 R-21 | 飞书权威 |
| **2. 凭据域 Evidence** | 三单匹配、发票唯一性、票据与原件保管、OCR 结构化 | A2.2 A2.3 R-10 Q-09 Q-10 Q-16 | **本地权威**（唯一性/哈希） |
| **3. 账务域 Ledger** | 资金的收入/支出/垫付/返还必须是同一本账 | A2.2 A4.2 R-11 R-12 R-19 R-20 R-22 Q-19 | **本地权威** |
| **4. 预算域 Budget** | 申请时可见余额、审批后占用、花销聚合、超额预警 | A4.3 R-16 R-17 R-18 | **本地权威**（口径在飞书展示） |
| **5. 协同域 Workflow** | 审批、催办、状态机、通知、待办 | A2.1 A4.1 R-02 R-03 R-06 R-09 Q-06 Q-15 | 飞书权威（本地只读事件） |
| **6. 视图域 Insight** | 看板、公示、导出、个人查询、权限裁剪 | A2.4 A3.1 A3.4 R-04 R-07 R-13 R-14 R-15 Q-13 Q-14 | 飞书权威（本地裁剪） |
| **7. 横切 Cross-cutting** | 身份与权限、审计、导出留痕、幂等与同步、配置字典 | A4.2 R-05 Q-01 Q-02 Q-12 Q-17 Q-18 | **本地权威**（审计） |

**重构带来的三个删减**（这是"替代/归纳"的实质收益，不是换个名字）：

- **删掉"三种资金来源三张表"的建模**。流动资金 / 个人垫付 / 老师代付是**同一本账上的三个资金池**，
  用 `方向（收/支）+ 资金来源（枚举）` 表达即可。若拆成三张表，"项目当前花销"这种最简单的问句要三表 UNION，
  且第四条资金来源出现时要改表结构。（Q11/Q20 的答案：**新增枚举值，不新增表**。）
- **删掉"审批后扣减预算"这个动作**。它制造了两个真相（表里的余额 vs 实际花销），驳回/撤销/超时都要补偿。
  改为**预算 = 三口径派生值**：`额度 - 已占用(申请中+已批准) - 已支出`，其中"已占用""已支出"都是由单据派生的聚合，
  **驳回即自动回弹，不存在对账不一致**（A 派建议，采纳）。本地权威版在此之上用数据库 CHECK 兜住并发（见 §4.4）。
- **删掉"流水登记表"与"采购表"的分家**。采购申请通过后直接生成账务分录，而不是"再抄一遍到流水表"（R-19/R-20 合并）。

## 2. 四派主张对照与关键裁定

### 2.1 主张对照

| 议题 | A 飞书极致派 | B 自托管派 | C 产品体验派 | D 合规审计派 | **综合裁定** |
|---|---|---|---|---|---|
| 主存 | 飞书多维表格 SSOT | 本地 Postgres 唯一真源 | 不站队，但要求 ≤6 个首屏字段 | 飞书不可当账本 | **§3.1 权威矩阵分级**（本地权威面收窄到 3 类） |
| **实现栈** | 尽量零代码 | Python/FastAPI + PG16 + Metabase | 不站队 | 不站队 | **Go 单二进制 + SQLite（用户指定）**，处理路由在 Linux 主机 |
| 代码量 | MVP 0 行 / V1 ~800 行 | MVP 纯飞书 / V1 25~35 人日 / 1855 行设计 | V1 不上 H5，1 个 ~100 行跳转服务 | 底线：本地 3 张表 | **P1 只做 7 张表 + 1 个进程**（Go，约 8~14 人日） |

| 预算扣减 | 不做破坏性扣减，纯公式派生 | reserve/commit/release + CHECK 约束 | 表单内实时显示余额 | 分档审批 + 防拆分 | **采纳 A 的口径 + B 的并发兜底**（§4.4） |

| 催办 | 汇总卡片到财务群（自动化 200 次/月够用） | 本地定时引擎 | D+0 不催 / D+3 / D+7 / D+14 / D+30 静默 | 超期强制催办留痕 | **采纳 C 的节奏 + 本地引擎**（配额决定它不能长期住在飞书自动化里） |
| 对外暴露 | 长连接，零公网 | 长连接，零入站端口 | 短链服务走 Tailscale Funnel | 不给建议 | **长连接（官方原文确认无需公网 IP）+ Tailscale 运维** |
| 发票验真 | 反对做成硬门禁（税局限流 5 次/天/张） | 字段已含验真入参 | 不阻塞提交 | 学校常要求验真 | **V2 可选项，异步批量，不阻塞提交**（§4.6） |

### 2.2 三处必须由我裁决的冲突

**裁定 1（最重要）：这到底是不是"软件开发项目"？**
A 派说"这是一次配置工程，不是一次软件开发"，B 派说"飞书无法表达'同一张发票不能重复报销'"。
**两者都对，但适用范围不同**：`02-feishu-capability-facts.md` 第 2、3 条证据是决定性的——
Bitable **没有任何唯一索引能力**（字段 API 全参数无 `unique`），且**同一数据表禁止并发写**（`1254291 Write conflict`）。
这意味着"查重后写入"在飞书上天然是 **TOCTOU 竞态**：两个人同时提交同一张发票，两次"查重"都会通过。
因此：**"配置工程"适用于采集、审批、展示、催办；"软件开发"只被允许侵入"唯一性、账务口径、审计痕迹"这三件事。**
这就是 §3.1 权威矩阵的全部依据。

**裁定 2：队员侧"0 必填"与合规侧"三单匹配"如何共存？**
C 派与 D 派的争论实质是**校验发生的时刻**，而不是字段的存废。裁定：
- **提交时刻**：唯一必填是 3 张图；金额、日期、商家、物资名允许由 OCR 预填、允许为空、允许错。
- **审批时刻（财务/负责人）**：三单匹配（金额 / 时间 / 收款方 / 商品）在此**硬门禁**，不通过不给付款/不给报销。
- **依据**：同一份完整性校验，前置到队员侧要增加约 12 个字段/笔，后置到财务侧只需约 5 秒/笔（C 派量化）；
  而 D 派真正要防的风险（重复报销、无凭证付款）**发生在报销与付款时刻**，不是提交时刻。
  这不是"少核"，是**把校验放在能真正拦住钱的位置**。

**裁定 3：报表/看板能不能自动生成？**
不能。`02` 文档第 5 条：**仪表盘无法通过 API 创建**（只有 list 与 copy），**自动化流程也无法通过 API 创建**（只能 list + 启停）。
因此任何"系统自动生成看板"的设计都作废：看板在 UI 手工建一次作为模板，此后靠 `copy` 克隆。
同理，"审批通过自动写回多维表格"**没有原生路径**（原生连接器是单向、每小时、只读；官方自动化 9 项触发器里没有"审批"），
必须由本地服务订阅 `approval_instance` 事件后回写——**这一条本身就强制了"必须有那个本地进程"**。

## 3. 模块化架构

### 3.1 数据权属矩阵（本方案的核心契约）

| 数据对象 | 载体 | 权属（唯一写者） | 同步方向 | 理由 |
|---|---|---|---|---|
| 采购申请、发票收集表单 | 飞书（表单视图 + 表） | 飞书 | 飞书 → 本地（事件） | 采集场景飞书体验最好，且是唯一入口 |
| 审批实例与状态 | 飞书审批 | 飞书 | 飞书 → 本地（长连接事件） | 审批是飞书的强项，不自研 |
| **发票指纹与唯一性** | **本地 DB** | **本地** | 本地 → 飞书（只读展示） | 飞书无唯一索引 → 不能在飞书保证 |
| **账务分录（收/支/垫付/返还）** | **本地 DB** | **本地** | 本地 → 飞书（镜像表） | 需要借贷平衡与"还欠谁多少"的可计算性 |
| **审计日志 / 状态跃迁 / 导出留痕** | **本地 DB** | **本地** | 本地 → 飞书（可选摘要） | 飞书无字段级旧值、管理员可静默改 |
| 预算额度（各组总额） | 飞书表 | 飞书 | 飞书 → 本地 | 低频维护，人填即可 |
| 预算派生口径（已占用/已支出/可用） | 飞书（查找引用 + 公式） | 派生 | 本地 → 飞书 | 展示用，不参与写路径 |
| 票据原图 | **飞书附件（唯一副本）** | 只读 | 本地不落盘；仅在抽字段时临时下载，保留 `sha256` 指纹用于查重 |
| 物资/费用类别字典 | 飞书表 | 飞书 | 飞书 → 本地 | 人工维护的枚举 |
| 个人查询视图 | 飞书视图 / 本地裁剪 | 飞书（付费版）或本地 | — | 免费版无行级权限 → 本地裁剪兜底 |

> **不可违反的两条铁律**：(1) 同一个字段只有一个写者；(2) 派生字段绝不反写。

### 3.2 模块总览（可独立部署性）

```

                    └───────▲──────────────────────────┬──────────────────────────────────┘
            出站 HTTPS 调用 │                          │ 长连接(WebSocket，无需公网 IP)
                            │                          ▼
   ┌────────────────────────┴───────────────────────────────────────────────────┐
   │  finance-router（Go 单二进制 · 单实例 · Docker 或 systemd）                   │
   │  ├ M1 intake-adapter   表单/审批事件 → 领域事件（幂等 event_id）                │
   │  ├ M2 evidence         三单匹配 · 发票指纹 · 批次占用 · 原件 sha256             │
   │  ├ M3 ledger           复式分录 · 资金池 · 垫付余额                             │
   │  ├ M4 budget           三态口径 · CHECK 约束保证不超预算                         │
   │  ├ M5 notify-scheduler 催办引擎（D+3/D+7/D+14/D+30）· 汇总卡片                  │
   │  ├ M6 sync-outbox      outbox → 飞书镜像表（单表串行队列 + 退避 + 死信）          │
   │  └ M7 audit            哈希链追加日志 · 导出留痕                                │
   └───────┬───────────────────────────────────────────────┬─────────────────────┘
           │                                               │
      ┌────▼──────────────┐                    ┌───────────▼───────────┐
      │ SQLite (WAL)      │                    │ OCR（可选，HTTP 调用）  │
      │ data/finance.db   │                    │ 飞书API / 视觉模型 /    │
      │ 3 年 < 200 MB      │                    │ PaddleOCR sidecar      │
      └───────────────────┘                    └───────────────────────┘
      票据原图只在飞书，本地不落盘；备份 = VACUUM INTO + 每日推飞书快照表
```

**为什么是"一个进程 + 一个 SQLite 文件"**：B 派原始设计有 44 张表 / 7 视图 / 8 触发器（已实测），
对"实验室自用"这个规模**明显过度**。综合后压缩为 **7 张核心表**，
**唯一有状态的东西就是一个 `.db` 文件**（队列用表实现，不引入 Redis/MQ/Nginx，也不需要独立数据库进程）；
OCR 是**可选的 HTTP 调用**，挂掉不影响业务（飞书原生识别 + 人工确认仍然可用）。

### 3.3 模块接口（领域事件契约）

模块之间只通过事件与表契约通信，便于后续替换任一实现：

| 事件 | 发出方 | 载荷（最少字段） | 消费者 |
|---|---|---|---|
| `intake.submitted` | M1 | `submission_id, applicant, group_id, amount?, currency, images[3], source(流动资金/垫付/老师), biz_type(采购/差旅)` | M2 M3 |
| `evidence.matched` / `evidence.rejected` | M2 | `submission_id, match_result, invoice_fingerprint, defects[]` | M3 M5 M7 |
| `invoice.duplicate_detected` | M2 | `submission_id, fingerprint, hit_record_id, layer(L1..L5), score` | M5（通知+仲裁） M6 |
| `approval.decided` | M1（来自飞书） | `approval_code, instance_code, decision, operator, at` | M3 M4 |
| `ledger.posted` | M3 | `entry_id, lines[], pools_delta, order_ref` | M4 M6 M7 |
| `budget.overdraft_blocked` | M4 | `fund_account, requested, available, applicant` | M5（退回提示） |
| `notify.due` | M5 | `target(人/群), template, order_ref, deep_link, due_level` | M1 M7 |
| `export.performed` | M7 | `operator, scope, row_count, watermark, file_hash` | M7 |

## 4. 关键机制设计

### 4.1 最小数据模型（7 张核心表，替代 B 派的 44 张）

```sql
-- 方言：SQLite（同时保持与 Postgres 兼容的写法，便于日后切换）
-- 金额一律以"分"为单位的 INTEGER（避免浮点，D 派硬性要求 H9）；表用 STRICT 防类型混用
submission(id, applicant_id, group_id, biz_type, fund_source, amount_cent NULL, state, submitted_at)
invoice(id, submission_id, fingerprint_key, fingerprint_layer, image_sha256, file_token_ref,
        invoice_no NULL, invoice_date NULL, seller_tax_id NULL, amount_cent NULL,
        dedup_status, arbiter_id NULL, created_at)
        -- 部分唯一索引：只对"已判定为清晰（CLEAR）"的指纹生效
        CREATE UNIQUE INDEX uq_invoice_clear ON invoice(fingerprint_key) WHERE dedup_status='CLEAR';
batch(id, name, state, created_by, closed_at)                      -- 报销批次
batch_invoice(batch_id, invoice_id, is_active BOOLEAN, added_at)    -- 占用，允许驳回后释放
        CREATE UNIQUE INDEX uq_batch_invoice_active ON batch_invoice(invoice_id) WHERE is_active;
fund_account(id, pool_type, owner_id NULL, balance_cent)            -- 三个资金池
ledger_entry(id, entry_no, posted_at, memo, source_submission_id)
ledger_line(id, entry_id, account_code, debit_cent, credit_cent, group_id)  -- 借贷平衡
budget_account(id, group_id, period, quota_cent)
emission(id, group_id, period, quota_cent, reserved_cent, committed_cent)   -- 额度，CHECK 兜底
        CONSTRAINT ck_not_overdrawn CHECK (reserved_cent + committed_cent <= quota_cent);
audit_log(id, at, actor, entity, entity_id, action, before_json, after_json, row_hash, prev_hash)
state_transition(id, entity, entity_id, from_state, to_state, actor, at, reason)
export_log(id, at, actor, scope, row_count, watermark, file_sha256)
```

> B 派已在**真实 PostgreSQL 16.2** 上执行验证过 151 条语句与 9 组不变式（含"12 个并发事务抢 3 份额度→恰好 3 个成功"），
> 并暴露了 4 个真实缺陷（`CREATE CONSTRAINT TRIGGER` 不支持 `FOR EACH STATEMENT`；批次关闭后发票被永久锁死；
> 视图表名笔误；幂等重放导致**额度扣两次**）。
>
> **本项目改用 SQLite，上述三类约束仍全部成立**（部分唯一索引 `WHERE`、`CHECK`、`BEFORE UPDATE/DELETE` 触发器，见 §6.3），
> 但**必须做两处适配**（这是从 PG 设计迁移到 SQLite 的真实工作量，不是零成本）：
> 1. **`CREATE CONSTRAINT TRIGGER` 用不上**。PG 的延迟约束触发器在 SQLite 无对应物 → 借贷平衡改为
>    **在写入事务内显式校验**（Go 侧校验 + `CHECK` 兜底），或改为"分录状态字段 + 应用层平衡断言"。
> 2. **金额类型**：PG 的 `NUMERIC(18,2)` → SQLite 用 `INTEGER` 存"分"（本来就该如此），并启用 `STRICT` 表防类型混用。
>
> **验收要求**：那 9 组不变式必须**在 SQLite 上重跑一遍**再进入 P1 验收，不能假设 PG 上通过就等于 SQLite 上通过。

### 4.2 采集：0 必填 + 三段式校验（裁定 2 的落地）

| 阶段 | 谁 | 系统做什么 | 拦不住会怎样 |
|---|---|---|---|
| 提交 | 队员 | 只强制 3 张图；其余字段 OCR 预填 + 默认值 + 历史值 | 允许脏数据进入（可接受） |
| 自动 | M2 | 三单匹配打分；发票指纹查重；原件 `sha256` 指纹（下载后即删原图） | 不确定的进 `SUSPECT` 与人工仲裁队列 |
| 审批/付款 | 财务/负责人 | **硬门禁**：无凭证不给付款；重复发票直接拒绝；金额分档审批 | 钱不会出门（这就是要拦的位置） |

三单匹配的判据（D 派）：金额（允许分位差容差）· 时间（付款日 ≤ 订单日 + N 天）· 收款方（订单商家 vs 发票销方）· 商品名（字典 + 模糊）。
匹配失败**不阻塞提交**，只把缺陷列表挂到审批卡片上，让审批人一眼看到缺哪一单。

### 4.3 OCR 与"一键补充信息"：三级可换，Go 只做客户端

- **主力**：飞书原生 `document_ai/v1/vat_invoice/recognize`（增值税发票，<10 MB，10 QPS，返回发票号/日期/金额/税额）。
- **硬约束**：智能文档解析配额 —— 基础免费版认证后 **100 次/月**，商业专业 1,000，旗舰 10,000，超出报 `2110003`。
  **用户已确认数据量很小**（年 300–600 张票）→ 月均 25–50 张，**在免费配额内**，因此本地 OCR 整体降级为 P4。
- **三级路由（可换引擎、不改主程序）**：
  1. 飞书原生发票识别（主路径，免费额度内）；
  2. **通用视觉模型抽字段**（Go 直接发 HTTP，模型可替换；处理非增值税票据与飞书额度耗尽）；
  3. **PaddleOCR/RapidOCR sidecar**（HTTP 服务，Go 只做客户端；离线、无外部依赖，作为最后兜底）。
  > 在 Go 里**不做内嵌 OCR**（CGO 绑定会破坏静态单二进制）。把 OCR 当成 HTTP 服务，是"便捷可拓展"的直接兑现：
  > 换引擎 = 改一行配置，不动核心流程。
- **降级规则**（C 派 + D 派共识）：OCR 失败**绝不要求重填整表**，只问 2 个问题（金额是多少 / 是哪家商户），
  并把该条标记为 `NEEDS_MANUAL` 私聊反馈提交方，而**不阻塞登记**（B 派原则：入库成功即成功）。
- **截图模板**（Q-09）：不做规范文档，做一张群置顶样例卡片——这是产品派验证过的低成本做法。
- **"懒得填"的针对性设计**（用户已确认欠票主因）：OCR 预填只是三分之一，另外两个杠杆是
  **历史值默认**（同一人上次的组别/资金来源/类别自动带入）与**一键跳转预填表单**（通知卡片直达已填好的页面）。

### 4.4 预算：口径在飞书，并发安全在数据库

- **对外口径（飞书展示）**：`可用余额 = 额度 − 已占用(申请中+已批准) − 已支出`，由查找引用/公式派生，
  **驳回自动回弹**，不做破坏性扣减。
- **对内兜底（本地 DB）**：若采用预占语义，必须有**过期时间**，并用
  `CHECK (reserved + committed <= quota)` 让**并发不超预算由数据库保证而不是代码**；
  预占写入必须用 `INSERT ... ON CONFLICT` **并判断是否真的新建**（`xmax = 0`），否则幂等重放会重复扣减（B 派实测缺陷）。
- **两者只允许同时存在一个**：展示口径与实际扣减口径同源同义，禁止出现"表里余额 ≠ 系统余额"。

### 4.5 催办引擎与通知（含成本控制）

- **节奏（采纳 C 派）**：D+0 不催（票还没开出来）→ D+3 合并提醒 → D+7 二次且组负责人可见 → D+14 升级财务 → D+30 静默归档。
- **频次上限写死**：一人一周系统消息 ≤ 2 条。
- **为什么必须放本地**：飞书自动化**免费版仅 200 次/月**且 API 不能创建自动化流程；
  改为"财务群汇总卡片"后月耗约 89 次（A 派测算）可以活，但**按人催办必爆**。
  因此规则：**低频汇总留飞书，按人/按单的催办走本地引擎**（本地引擎挂掉时降级为群汇总卡片，功能不丢，只丢精度）。
- **一键动作**：每条通知必须携带 `deep_link` 到已预填表单（表单预填走 `?prefill_字段=`，注意链接上限 16,000 字符）。

### 4.6 合规底线（采纳 D 派，但明确执行成本与豁免）

**底线五条**（D 派的"只做 5 件事"）：
1. 发票唯一性硬阻断（DB 级）；2. 三单匹配门禁（审批/付款时刻）；3. 状态单向流转 + append-only 审计；
4. 资金统一入账且**付款凭证号必填**（不接受"备注"）；5. 返还三件套（转账凭证 + 本人确认 + 季度抽检）。

**采纳但降级的**：
- 金额分档审批（D 派默认：≤100 免审 / 100–500 队长 / 500–2000 财务+队长 / 2000–10000 +老师先审后付 / >10000 集体决策）
  ——**必须按团队真实预算重标定**，并**与学校《经费支出审批办法》取较低门槛**（这是待确认问题 #1 的直接后果）。
- 职责分离：允许"申请人 = 付款人"，**绝不允许"申请人 = 审批人"**；管理人员 ≤ 2 人时部分控制在制度上无法成立，需如实写明。
- 公示看板**禁止"人名 + 金额"组合**，用组别汇总 + 金额区间，某组人数 < 3 时做小样本抑制。
- 审计日志用**哈希链**（`row_hash = H(prev_hash || 本条)`）+ 每日 `VACUUM INTO` 备份产物作为离线锚点，低成本防静默篡改。
- 发票验真：**V2 可选、异步批量、不阻塞提交**（税局查验有频率限制，做成硬门禁会卡住正常提交）。

**明确放弃的**（避免"好看但没人执行"）：正式财务报表模板、电子签章、期间关账（除非学校要求）。

### 4.7 权限与公示：免费版是硬门槛

`02` 文档第 4、7 条：**"每人只能看自己创建的记录"能力有，但行列权限是付费档位专属**（基础免费版/基础标准版**不支持**）。
因此：

- **主路径（免费可用）**：飞书侧不依赖行级权限，个人视图由**本地服务做数据裁剪**（应用身份读全量 → 按人过滤 → 只返回本人记录）。
- **升级路径（若已付费）**：使用内建「成员本人创建的记录」规则（API `rec_rule`，`field_name=""` 即"创建人包含访问者本人"），
  但**授权面收窄是必须的**：`Q-13` 的"个人只能查自己的表"在免费版**不是配置问题，而是实现问题**，这一点必须在立项时讲清。
- **导出**：导出必须审批 + 水印 + `export_log` 留痕；且注意**飞书导出不含附件**、产物 10 分钟后删除、不支持 `.base`。

### 4.8 飞书接入：长连接 + 幂等 + 单实例

- **传输**：官方原文确认长连接"**无需提供公网 IP 或域名、无需使用内网穿透工具**"，
  仅限企业自建应用，每应用 ≤ 50 连接，**集群模式不广播**（多实例只有一个收到），**3 秒内必须处理完**。
  → **消费端单实例**，回调只做入队，重活异步；`event_id` 幂等。
- **同步**：outbox/inbox + 幂等键 + 指数退避 + 死信 + `v_sync_lag` 可见性（让用户知道"还没同步过去"）。
- **飞书侧硬点**：同一数据表**禁止并发写**（`1254291`）→ 本地必须**按 `table_id` 串行写入队列**；
  单次批量新增/更新 ≤ 1,000、删除 ≤ 500 且**全成全败**；**只读字段（公式/查找引用/自动编号/创建时间/创建人）绝不能作为写入目标**；
  事件订阅必须**按文档逐个注册**且不能按类型筛选；**公式字段变化不触发事件**。
- **运维通道**：直接用既有 Tailscale（100.110.91.90），不暴露 SSH、不做端口映射。

## 5. 部署形态（单机 · 无 NAS · 数据量小）

### 5.1 收敛后的部署：一台 Linux 主机上的一栈

用户已明确**不考虑 NAS**、**数据量很小**、**处理路由到 Linux**。因此部署不再有跨设备分工：

| 组件 | 位置 | 资源 | 说明 |
|---|---|---|---|
| `finance-router`（Go 单二进制） | Linux 主机 | <100 MB 内存常驻 | 长连接消费事件 + 规则处理 + 写回飞书 |
| SQLite（单文件） | Linux 主机本地磁盘，`./data/finance.db` | **预计 3 年 < 200 MB** | 只存"证据与账"，不存原图 |
| 票据原图 | **飞书附件（唯一副本）** | 0 | 本地只在抽字段时临时下载，用完即删 |
| 迁移文件 / 备份 | 本地目录 + 轮转 | 每日几 MB | 见 §5.2 |
| 反向代理 / 证书 | **不需要** | — | 长连接为出站连接，零入站端口 |
| 运维通道 | Tailscale（已装） | — | 不暴露 SSH、不做端口映射 |

**存储量估算（"数据量很小"的量化确认）**：
按一年 300–600 张票据、每条记录约 1–2 KB（含指纹、状态、审计链）计算，**SQLite 年增约 1–5 MB**，
3 年累计 < 200 MB，含导出与备份轮转后仍 < 1 GB。**这彻底消除了原 v0.1 中"NAS 存储 + 根分区 82%"的部署风险**
（仍是唯一需要注意的运维项：备份目录要轮转，不要把导出文件堆在根分区）。

### 5.2 备份（无 NAS 的最简可靠方案）

数据量小反而让备份变简单，三件事按顺序做即可：
1. **SQLite 在线备份**：用 `VACUUM INTO 'backup/finance-YYYYMMDD.db'`（Go 里一条语句，无需停服务、不会撕裂），保留最近 14 份并轮转。
2. **每日导出到飞书**：本地服务定时把关键表推成一张飞书"快照表"（或调用导出 API）——
   **这同时满足"最终产物交付在飞书"的要求**：即使这台 Linux 主机彻底损坏，飞书里仍有可读的账。
3. **异地一份**：把 `VACUUM INTO` 的产物 `rsync`/`rclone` 到任一网盘或 `git` 私有仓库（百 MB 级完全可行）。

> 恢复演练目标（验收项）：从备份文件到服务可查，**≤ 5 分钟**。因为备份就是"复制一个文件"，这个目标是可达的。

### 5.3 部署风险（实测环境暴露，已按新形态重新评估）

| # | 风险 | 新形态下的处置 |
|---|---|---|
| 1 | 根分区已用 **82%**（剩 74 G） | 从"一号风险"降级为**运维注意事项**：数据与备份加起来 < 1 G；仍建议把 `data/` 与 `backup/` 放到独立卷或外接盘，并做 >85% 告警 |
| 2 | 主机为**无线 wlo1** 接入 | 长连接需**指数退避重连 + 15 分钟轮询补偿**；无线抖动只造成同步延迟，不造成数据丢失（本地先写库，再投递飞书） |
| 3 | 长连接**集群模式不广播** | 消费端**必须单实例**（本方案就是单进程，天然满足）；如日后要双实例，需改 Webhook + 公网入口 |
| 4 | SQLite **库级写锁** | 全部写入收敛到**一个写协程**（与飞书同表禁止并发写的约束同构），`busy_timeout` 兜底 |
| 5 | 实验室项目易腐化 | 单二进制 + SQL 迁移文件 + 配置化字典，降低"换人接手"的难度；**任何新增表必须有追溯矩阵依据** |

## 6. 技术选型

| 层 | 首选 | 替代 | 理由 |
|---|---|---|---|
| 语言/框架 | **Go 1.22+**，标准库 `net/http` + `chi`（或直接用 `http.ServeMux`） | Python/FastAPI | 用户指定；单二进制部署、交叉编译、低内存、无运行时依赖，最契合"实验室自用 + 迭代快" |
| 数据库 | **SQLite（WAL 模式）** | PostgreSQL 16（仅当日后需要多进程并发写或外部分析时切换） | 用户指定轻量级。**SQLite 完全支持本项目全部硬约束**：部分唯一索引 `WHERE`、`CHECK`、触发器、`STRICT` 表；单文件、零运维、备份 = 复制一个文件 |
| DB 驱动 | `modernc.org/sqlite`（纯 Go，无 CGO） | `mattn/go-sqlite3`（CGO，性能略好） | 纯 Go 可静态编译单二进制，交叉编译无障碍；本项目吞吐量下性能差异无意义 |
| 数据访问层 | 手写 SQL（`database/sql`）+ 薄封装 | `sqlc`（SQL → 类型安全 Go 代码） | 迭代快 = 改 SQL 即改行为；`sqlc` 可选，不引入 ORM（ORM 会挡住部分唯一索引这类能力） |
| 队列 | **SQLite 表队列（`outbox` / `jobs` 表 + 单写入协程）** | 无（不需要） | 数据量小，进程内单写入者即可；不引入 Redis/MQ |
| 飞书接入 | 官方 Go SDK `larksuite/oapi-sdk-go/v3`，**长连接（WebSocket）接收事件** | Webhook + Tailscale Funnel | 官方文档确认长连接无需公网 IP/域名/内网穿透，最契合本机部署 |
| OCR | ① 飞书原生发票识别 API ② **通用视觉模型抽字段**（本地 HTTP 调用，模型可换） | ③ PaddleOCR/RapidOCR **sidecar**（HTTP 服务，Go 只做客户端） | Go 里不做内嵌 OCR：把 OCR 当成一个 HTTP sidecar 或外部 API，**换引擎不改主程序**。这一条直接满足"可拓展" |
| 票据原图 | **飞书附件为唯一副本**（本地不落盘） | 本地目录缓存（仅在需要重算哈希时，带 TTL） | 用户已确认数据量小；本地只存 `sha256` 指纹即可完成查重 |
| 前端 | **不自研**：飞书表单/审批/仪表盘/卡片 | H5（仅当触发条件成立） | 用户已明确"入口也在飞书"；自研前端等于重写 SSO、行级权限、移动端、图表、通知五件事 |
| 可视化 | 飞书仪表盘（UI 手工模板 + copy） | Metabase（读 SQLite 文件，只读挂载） | 仪表盘**不能 API 创建**；真要外部分析时 Metabase 可直接读 SQLite 文件 |
| 编排 | **Docker Compose 单机**（已装 v5.5.1）；或 `systemd` + 单二进制 | — | 两种都极简：Go 编译出单文件，连运行时都不需要 |
| 运维通道 | Tailscale（已装，100.110.91.90） | 局域网直连 | 已有资产，不暴露 SSH |

**明确不引入**：Kubernetes、Kafka、Redis、消息队列服务、Nginx/Caddy、ORM、微服务拆分、NAS/分布式存储。
理由统一为一句：**这个系统的并发峰值是"报销季一天几十笔"，任何为规模而引入的组件都是负债。**

### 6.3 为什么"轻量"不等于"放弃约束"

用户说"轻量级数据库"，需要澄清一个常见误解：**SQLite 不是"功能缩水的数据库"**。本项目三条最关键的正确性约束它全部原生支持：

```sql
PRAGMA journal_mode = WAL;      -- 读写并发
PRAGMA foreign_keys = ON;       -- 外键必须显式开启
PRAGMA busy_timeout = 5000;     -- 单写入者排队而非报错

-- ① 发票唯一性（防重复报销的核心）—— 部分唯一索引，SQLite 支持
CREATE UNIQUE INDEX uq_invoice_clear ON invoice(fingerprint_key) WHERE dedup_status = 'CLEAR';
CREATE UNIQUE INDEX uq_batch_invoice_active ON batch_invoice(invoice_id) WHERE is_active = 1;

-- ② 预算不可超支 —— CHECK 约束，SQLite 支持
CREATE TABLE fund_emission (
  ...,
  quota_cent     INTEGER NOT NULL,
  reserved_cent  INTEGER NOT NULL DEFAULT 0,
  committed_cent INTEGER NOT NULL DEFAULT 0,
  CHECK (reserved_cent + committed_cent <= quota_cent)
) STRICT;

-- ③ 审计不可篡改 —— 触发器拦截 UPDATE/DELETE，SQLite 支持
CREATE TRIGGER trg_audit_no_update BEFORE UPDATE ON audit_log
BEGIN SELECT RAISE(ABORT, 'audit_log is append-only'); END;
```

**唯一需要留意的两点**（都不构成阻碍）：
1. 金额一律用 `INTEGER` 存"分"，禁用 `REAL`（浮点误差），并用 `STRICT` 表在 schema 层禁止类型混用。
2. 写并发只有**一个写入者**（SQLite 的写锁是库级）。本项目全部写入本就要求串行（飞书侧同表禁止并发写的约束天然一致），
   实现上就是**一个写协程消费 `jobs` 表**——这不是妥协，而是与飞书约束同构的设计。
   若日后真的需要多进程写，切换 Postgres 的成本被压到最低（SQL 方言差异极小，见 §6.4）。

### 6.4 可拓展性设计（"迭代快"的具体兑现）

需求是"便捷可拓展、迭代快"，用机制而不是口号来保证：

| 机制 | 做法 | 带来的可拓展性 |
|---|---|---|
| **单二进制** | `go build` 出一个静态文件，含所有逻辑 | 部署 = 复制文件 + 重启；回滚 = 换回旧文件 |
| **迁移即 SQL 文件** | `migrations/0001_init.sql`、`0002_add_xxx.sql`，启动时按版本号顺序应用 | 加字段 = 加一个文件，不需要改代码结构 |
| **规则化匹配流水线** | 三单匹配/校验拆成 `Validator` 接口的实现（金额、时间、收款方、商品、重复），按名字注册 | 新增一条校验 = 新增一个实现 + 注册一行，**核心流程不动** |
| **OCR 引擎可换** | `OCREngine` 接口：飞书 API / 视觉模型 / PaddleOCR sidecar 三种实现 | 换引擎只改配置；配额爆了自动降级到下一个 |
| **飞书字段映射外置** | 表名/字段名写在配置文件（`mapping.yaml`）而不是硬编码 | 飞书表结构调整时改配置，不改代码 |
| **事件总线即 outbox 表** | 业务动作先写本地库 + `outbox`，再由投递器写飞书 | 加一个下游消费者 = 加一段订阅，不影响主流程 |
| **DB 可换** | 只依赖 `database/sql` 接口，SQL 保持通用子集 | SQLite → Postgres 的切换成本约为改连接串 + 少量方言 |
| **配置即能力** | 资金来源、费用类别、审批分档、催办节奏全部放字典表 | 加一个资金来源/类别 = 加一行数据，**不等版本发布** |

> 与"企业级"划清界限：本方案**不**做多租户、不做 RBAC 引擎、不做审批流引擎、不做审计合规报表平台。
> 这些是"实验室自用"场景下纯粹的负债（B 派的 44 张表设计正是被这一条压缩到 7 张的原因）。

## 7. 分期路线图与验收标准

| 阶段 | 时间 | 交付物 | 验收标准（可测） | 自研代码量 |
|---|---|---|---|---|
| **P0 保底试运行** | 第 0–2 周 | 纯飞书配置：1 张台账 + 1 张票据 + 表单 + 审批 + 财务群汇总卡片 + 手工看板 | 队员 **≤ 90 秒**提交三图、手打字段 ≤ 4 个；财务能回答"谁欠票、欠多少、欠几天"；**0 行代码** | 0 |
| **P1 凭据服务** | 第 3–6 周 | Go 单二进制最小版：发票唯一性硬约束（SQLite 部分唯一索引）+ 批次占用 + 审计哈希链 + 状态跃迁 + 长连接事件入口 | 同一发票并发提交**恰好 1 次成功**；任何金额变更可回放；镜像失败不影响业务；**9 组不变式在 SQLite 上重跑通过**；**约 8–14 人日** | ~600–900 行 Go |
| **P2 账务闭环** | 第 7–10 周 | 复式分录 + 资金池 + 垫付余额 + 采购审批落账 + 催办引擎（D+3/D+7/D+14/D+30） | "还欠某老师/某队员多少"是一句 SQL；人工统计欠票归零；通知 ≤ 2 条/人/周 | +600 行 |
| **P3 预算与视图** | 第 11–16 周 | 预算三口径 + 并发安全额度 + 镜像回表 + 导出留痕 + 个人视图数据裁剪 + 公示脱敏 + 每日备份到飞书 | 申请时可见余额；并发不超预算（CHECK 保证）；免费版下个人只能看到自己的记录；**从备份恢复到可查 ≤ 5 分钟** | +400 行 |
| **P4 可选** | 按需 | 视觉模型/sidecar OCR 兜底 / 发票验真 / 固定资产（Q-16）/ 资金返还模块（R-22） | 按触发条件启动，不预设 | — |

**Go/No-Go 判据（采纳 C 派，作为 P0 的硬指标）**：
14 天发票回收率 ≥ 80%、提交耗时中位数 ≤ 60 秒、≥ 60% 队员无需指导即可完成提交。
**未达标不加功能，先改交互**——因为如果队员不交票，后面所有模块都是空转。
**用户已确认欠票主因是"懒得填"**，因此 P0 的判据就是"摩擦是否真的降下来"的直接检验。

**触发式升级条件**（避免过度建设）：
- 升级到 P3 的前提是 P2 已跑满一个报销周期且无人工对账差异；
- 只有当"飞书原生 OCR 月配额被用尽"或"非增值税票据占比高"时才启用第 2/3 级 OCR；
- 只有当"多维表格表单首屏可见字段 > 6"或"需要一次传多组图自动分组"时才做 H5；
- 只有当"单进程写入成为瓶颈"或"需要外部分析工具直连多写"时才从 SQLite 切到 Postgres（SQL 差异已控制在极小范围，见 §6.4）。
