## 1. 已经做出的架构裁定（可被用户一句话推翻，但推翻需改架构）

| # | 裁定 | 依据 | 若推翻的影响 |
|---|---|---|---|
| 1 | 飞书是门面与主力载体；**本地只对 3 类数据权威**：发票唯一性、账务分录、审计痕迹 | 飞书无唯一索引、同表禁止并发写、无 append-only | 架构级重做 |
| 2 | 同一字段只有一个写者，派生字段绝不反写 | 双向写同一字段必然产生两个真相 | 中 |
| 3 | 提交时刻 **0 必填**（3 图外）；合规校验放在审批/付款时刻 | 校验必须放在能拦住钱的位置；前置成本高约 12 字段/笔 | 高（队员依从性） |
| 4 | 预算**不做破坏性扣减**，用"额度 − 已占用 − 已支出"派生；如需预占必须有到期时间 + DB CHECK 兜底 | 驳回/撤销/超时要补偿，制造两个真相 | 中 |
| 5 | 看板与自动化流程**不能由 API 创建** → 手工建一次做模板 + copy | 官方文档：仪表盘仅 list/copy，自动化仅 list/启停 | 低 |
| 6 | 审批→多维表格**无原生回写** → 必须有本地服务订阅 `approval_instance` 事件 | 原生连接器单向/每小时/只读；自动化无审批触发器 | 低（但意味着"必须有那个进程"） |
| 7 | 发票验真**不做硬门禁**，V2 可选、异步批量 | 税局查验有频率限制，硬门禁会卡住正常提交 | 低 |
| 8 | V1 **不自研前端**、不上 H5；四件套 = 表单 + 审批 + 仪表盘 + 机器人卡片 | 自研前端 = 重写 SSO/行级权限/移动端/图表/通知 | 中 |
| 9 | 长连接（WebSocket）接收事件，**不需要公网 IP / 内网穿透**；消费端单实例 | 官方原文；集群模式不广播、3 秒内处理完 | 中（若要水平扩容需改 Webhook + 公网入口） |
| 10 | 分档审批门槛**先按 D 派默认值占位，必须按真实预算重标定，且与学校办法取较低门槛** | 不标定就是凭空约束 | 低 |
| 11 | **Go 单二进制 + SQLite（WAL）**，单机单进程；SQL 保持通用子集，保留切 Postgres 的路 | 用户指定轻量 + 实验室自用 + 迭代快；SQLite 支持部分唯一索引/CHECK/触发器，三条关键约束不打折 | 中（切回 Postgres 约 1–2 人日） |
| 12 | **本地不存票据原图**，只存 `sha256` 指纹；原图唯一副本在飞书附件 | 数据量小；原图落本地会带来备份与容量问题，且飞书附件已可用 | 低 |
| 13 | 扩展方式是**规则/引擎接口 + SQL 迁移文件 + 配置化字典**，不是微服务或插件框架 | 实验室项目的扩展需求是"加一条校验/加一个资金来源"，不是"加一个服务" | 低 |

## 3. 已知未解决的技术未知（不得当作结论使用）

来源：`docs/00-brief/02-feishu-capability-facts.md`「未能核实的问题」共 18 项。其中最影响设计的是：

1. 审批定义能否通过 API 修改（**官方自相矛盾**）。
2. 公式字段新增时能否同时设置表达式（**官方自相矛盾**）。
3. Bitable 记录变更事件延迟量级、是否有序。
4. Bitable 记录变更事件能否走长连接（**高置信推断：能**）。
5. 单表记录上限（开放平台与帮助中心口径冲突，**应以目标租户 UI 实际为准**）。
6. 单选/多选选项数量上限（官方三处口径不一：5,000 / 10,000 / 20,000）。
7. Bitable API 具体 QPS 限制（A 派与调研均未确认到确切数值；B 派核实到批量写 50 req/s、批量查 20 req/s）。
8. 导出记录条数上限、附件字段独立上限与总容量。
