## 1. 项目背景与痛点

### 1.1 项目背景
原财务流程在需求累加的情况下，各环节之间**信息不互通**（收集、审批、垫付、发票、流水、预算各自成表），
绩效/复盘时无法追溯物资花销由哪个组产生；对一般队员来说，上手审批与提交发票需要填写的字段过多。

### 1.2 痛点清单（原文归纳）

**A. 财务报销 / 对接学校**
- A1 对接学校：收集信息必须带齐三要素 —— 购买订单记录、付款截图、发票。
- A2 队内资金管理角度：
  - A2.1 使用**流动资金垫付**的订单必须开出发票，要能**自动化催办**上传发票。
  - A2.2 发票要便于整理，需知道物资花销产生在哪个组，便于事后复盘。花销记录至少带属性：
    - 物资名称、种类、归属组
    - 订单时间
    - 花销金额
    - 金额来源（个人垫付 / 老师垫付 / 流动资金）
  - A2.3 已提交发票是否已提交报销、提交后资金是否已返还（**避免多次报销过程中重复提交同一张发票**）。
  - A2.4 公示当前花销、催办看板、项目开销比例。
- A3 用户（普通队员）反馈：
  - A3.1 无法知道自己买过什么（无论用流动资金还是个人垫付）。
  - A3.2 登记时查找转账记录、订单等信息不方便。
  - A3.3 希望在提交时**只提交票、付款记录、订单记录三张图片**。
  - A3.4 想得知当前项目的花销。
- A4 流程不互通的卡点：
  - A4.1 交发票催办需人工统计未提交项、人工催办。
  - A4.2 流动资金支出登记依赖管理者自觉统计，且备注填写不规范 → 没有有效信息、难以寻源。
  - A4.3 <OTHER_APPROVAL_1>流程无法向各组反馈"项目还剩多少预算 / 已支出明细"，项目负责人无法做成本控制。

### 1.3 原始需求矩阵归纳（按需求大类）

| 需求大类 | 需求方 | 子类 | 现行实现 | 优先级 | 需求要点 |
|---|---|---|---|---|---|
| 发票收集 | 管理员/财务 | 信息收集 | 飞书 | 高 | 收集发票、付款截图、订单截图，以及对应信息，便于整理 |
| 发票收集 | 管理员/财务 | 信息处理 | 新插件 | 高 | 发送通知：催办发票收集，针对流动资金代付的订单 |
| 发票收集 | 管理员/财务 | 信息处理 | 新插件 | 中 | 催办自动化：付款一段时间后自动发送信息催办发票 |
| 发票收集 | 管理员/财务 | 信息处理 | 新插件 | 高 | 导出发票并保存导出记录 |
| 发票收集 | 管理员/财务 | 信息处理 | 新插件 | 中 | 信息包含：操作人、操作时间、操作事项（哪笔报销、发票处理阶段） |
| 发票收集 | 管理员/财务 | 信息处理 | 新插件 | 高 | 更新发票状态：待报销 / 已上传 / 上传批次 / 已报销 / 已到账（大额报销需有对应负责人） |
| 发票收集 | 管理员/财务 | 信息可视化 | 飞书 | 中 | 记录看板：显示已付款待交发票记录对应责任人统计、金额统计；显示项目当前累计花销统计 |
| 发票收集 | 一般队员 | 信息收集 | 飞书 | 高 | 填写发票收集，只提交发票、付款记录、订单记录三个信息 |
| 发票收集 | 一般队员 | 信息处理 | 新插件 | 高 | 查询自己是否有待提交发票的支出，一键跳转填写 |
| 发票收集 | 一般队员 | 信息处理 | 新插件 | 高 | 一键补充截图内信息，并处理为表格字段 |
| 流水信息 | 管理员/财务 | 信息收集 | 飞书 | 高 | 登记流动资金支出情况：时间、登记人、去项、金额、是否提交发票、备注 |
| 流水信息 | 管理员/财务 | 信息收集 | 飞书 | 高 | 流动资金收入情况登记：时间、登记人、来源、金额、备注 |
| 流水信息 | 一般队员 | 信息可视化 | 新插件 | 低 | 个人垫付：记录查询、总花销、消费曲线等 |
| 信息查询 | 一般队员 | 信息可视化 | 飞书 | 中 | 项目花销查询：记录查询、总花销、消费曲线等，与先前预算的对比情况 |
| 信息查询 | 管理员/财务 | 信息可视化 | 新插件 | 中 | 公示一段时间的流动资金花销情况，一键导出 or 公示看板（含更新时间、相关字段） |
| 预算同步 | 管理员/财务 | 信息可视化 | 飞书 | 中 | 登记各组当前可使用预算总金额 |
| 预算同步 | 管理员/财务 | 信息处理 | 新插件 | 低 | 流动更新，分析当前预算情况，亏损可能与预警 |
| 预算同步 | 管理员/财务 | 信息处理 | 飞书 | 高 | 一般队员在采购审批 / 申请流动资金时，显示当前申请资金类型余额 |
| 采购审批 | 管理员/财务 | 信息处理 | 新插件 | 高 | 审核对应的申请，并付款；更新审核状态 |
| 采购审批 | 管理员/财务 | 信息处理 | 新插件 | 高 | 记录当前的购买批销，并同步至流水表 |
| 采购审批 | 一般队员 | 信息收集 | 飞书 | 高 | 发起物资购买申请，提交物资清单、金额、选口使用金额项目 |
| 资金返还 | — | — | — | 低 | 待补充 |

### 1.4 需求矩阵中"需要确认的细节 / 约束内容"（原文，须在方案中回应）

1. 需要具体字段信息（收集表结构）。
2. 是否需要包含项归属、组与组之间相对归属范围。
3. 信息提交是否需要人工审核。
4. 数据存储平台？
5. 付款记录等上传：上传发票的负责人还负责资金管理？
6. 个人垫付的收集，如何催办 or 是保证上传？
7. 保底是可以用飞书表格实现的（验证保底后，开发优先级低）。
8. 单条记录可以更新 / 批量记录也可以更新（插件实现？）。
9. 提供可识别的截图模板。
10. 需要有效校验：若提取信息失败需要反馈给提交方。
11. 不同资金来源（流动资金、个人、老师代付）是新增项的，还是新增字段选择？
12. 按经验，一般分为：差旅、物资采购（个人垫付/老师付款）还三项，字段待确认。
13. 由于表格权限设置，个人最好只能查到自己的表。
14. 公示看板是否需要设置权限。
15. 是否需要定期提醒更新？
16. 固定资产如何自动生成？
17. 如何让人工登记的部分最少。
18. 如何确保每个订单都能开发票。
19. 是否需要与流水记录独立，成对？
20. 是否需要与流水记录独立，成对？（收入 / 支出 / 垫付的资金流是否统一）

## 2. 已发布的架构约束（用户最新指示）

- 现状基线：**原则上所有数据存储于飞书多维表格**，插件仅对其做处理。
- 用户已有资源：
  - 一台部署的 **Linux 主机**；
  - 一台 **NAS**；
  - 二者处于**同一局域网**；
  - 具备**开发飞书应用**（企业自建应用 / 多维表格 API / 审批 / 机器人）的条件。
- 交付目标：把上述需求做**替代、分解、归纳、重构**，最终得到
  **模块化、可拓展的程序项目** 来完成这些需求。

## 3. 本次任务的定义（给方案设计者）

### 3.1 必须回答
1. 需求重构：把 4 大类 + 20 项需求，重构成有限数量的**领域模块**（含模块职责、边界、依赖、可独立部署性）。
2. 数据架构：飞书多维表格（Bitable）作为主存 vs. 本地 Postgres + 飞书作为入口/展示层
   —— 两套方案的取舍与**推荐**，给出表结构（字段级）与迁移路径。
3. 关键机制的实现路径：
   - 三图上传 → OCR/结构化提取 → 校验失败反馈；
   - 发票催办（定时 + 状态机 + 通知）；
   - **发票唯一性/防重复报销**（如何在不引入昂贵基建的前提下做实体识别：发票号、金额+时间+开票方指纹）；
   - 预算联动：申请时显示余额、审批后扣减、花销聚合、预警；
   - 权限：一般队员仅能看自己的记录；公示看板的字段脱敏；
   - 导出与审计日志（操作人/时间/事项/批次/阶段）。
4. 自托管组件的落点：Linux 主机跑什么（服务/worker/DB/反向代理）、NAS 存什么（票据原图、备份），
   局域网与公网的暴露策略（飞书要求 HTTPS 回调 → 内网穿透 / frp / Cloudflare Tunnel / 飞书事件订阅长连接）。
5. 技术选型（含理由与替代项），以及**为什么不用**某些方案。
6. 分阶段路线图：MVP（保底可用，纯飞书表格/多维表格即可运转）→ V1 → V2，每阶段的验收标准。
7. 待确认问题清单（尽量少而关键）。

### 3.2 明确不做
- 不做超出"财务/发票/流水/预算/采购"范围的功能。
- 不假设有公网服务器预算、不假设有人付费云服务（可以免费额度，但不得为必需依赖）。
- 不假设飞书外部用户或跨租户能力。
