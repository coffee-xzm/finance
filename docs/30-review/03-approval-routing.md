# 审批如何路由回本项目

> 回答用户 2026-09-12 提问："现在我想问审批会怎么路由到这个项目"
> 关联：`docs/30-review/02-ocr-provider-interface.md`（识别层）、`docs/20-synthesis/02-architecture-v0.1.md` §4.8（飞书接入）。

---

## 0. 一句话结论

**审批不是"路由过来"，而是你的服务主动挂着一条长连接。**
你不是被调用方，你是**订阅方**——飞书在审批状态变化时，**沿着你已建好的出站 WebSocket 把事件推下来**。

```
❌ 错误心智模型：飞书审批 ──HTTP 回调──► 你在 Linux 上的某个端口   （需要公网 IP/域名/内网穿透）
✅ 正确心智模型：你的服务 ──出站长连接──► 飞书   ──事件沿连接推回──► 你  （零入站端口）
```

官方原文（已核实，`02-feishu-capability-facts.md` C13）：长连接模式
「只需保证运行环境具备**访问公网的能力**即可，**无需提供公网 IP 或域名、无需使用内网穿透工具**」。

| 方向 | 用途 | 需要入站端口吗 |
|---|---|---|
| **出站 WebSocket（长连接）** | 飞书 → 你：审批事件、卡片回调 | **否** |
| **出站 HTTPS** | 你 → 飞书：创建审批实例 / 写多维表格 / 发机器人消息 | **否** |
| 入站 | **完全不需要** | — |

**因此"路由到本项目"这句话本身就是个需要纠正的前提**：项目不需要被路由到，它只需要**在线**。

## 1. 端到端链路

```
队员（飞书多维表格表单，只强制 3 张图）
   │ 提交
   ▼
M1 intake-adapter ──► submission(RECEIVED) + 3×image_sha256 落本地库
   │  ① 立即回一条"已收到，正在识别"机器人卡片（不让队员干等）
   │  （回调只入队，绝不在回调里干活 —— 3 秒硬约束）
   ▼ 异步 worker
M2 evidence ──► SiliconFlow Qwen3-VL-30B-A3B 抽取 → Evidence(JSON)
   │            → L1 发票唯一性 / L2 金额 / L3 时间 / L4 收款方
   │            → 产出 match_status + 缺陷清单
   ├─► M3 ledger 落分录（本地权威）
   │
   ▼  ② 有了匹配结论，才创建审批实例
POST /open-apis/approval/v4/instances
   body: {
     approval_code: "<后台手工建的定义 code>",
     open_id:       "<申请人的 open_id>",
     form: [
       {id:"submission_id", value:"S-2026-0001"},                 ← 关联键（只读文本控件）
       {id:"amount",        value:"328.00"},                      ← 金额控件：条件分支用
       {id:"match_summary", value:"三单匹配通过：发票328.00/订单328.00/转账328.00"},
       {id:"defects",       value:"无"}
     ]
   }
   │  ← 返回 instance_code，与 submission_id 建映射（本地表 approval_link）
   ▼
飞书审批（定义在后台手工建，含金额条件分支）
   │  审批人看到匹配结论与缺陷清单 → 通过 / 驳回
   ▼
approval_instance / approval_task 事件
   │  沿已建立的长连接推下来（无需公网）
   ▼
Go 回调（3 秒内返回，仅入队）→ 幂等(event_id) → 严格状态机
   │
   ├─► M3 ledger 落账
   ├─► M4 budget 释放占用 / 提交已支出
   └─► M5 notify 机器人卡片通知申请人（**跳转链接放这里，不放审批表单**）
```

## 2. 飞书侧要配什么（一次性，共 6 项）

| # | 配置 | 说明 | 可信度 |
|---|---|---|---|
| 1 | **企业自建应用** | 长连接**仅支持自建应用**，商店应用不支持 | 已核实 |
| 2 | **订阅方式 = 长连接** | 开发者后台事件订阅处选择；内置加密鉴权，无需自行解密验签 | 已核实 |
| 3 | **审批权限 scope** | `approval:approval`（或 `approval:definition` / `approval:instance`） | 已核实 |
| 4 | **按审批定义订阅** | `POST /open-apis/approval/v4/approvals/:approval_code/subscribe`（按**定义**粒度、面向应用）。**不订阅就不会有事件** | 已核实 |
| 5 | **订阅事件** | `approval_instance`（实例状态）/ `approval_task`（任务态）/ `approval_cc`（抄送） | 事件名已核实；**"订阅后具体派发哪些事件类型"未找到逐字说明 → 需实测** |
| 6 | **审批定义在后台手工建** | 官方**明确不推荐** API 建定义（API 建的定义**无法停用/删除**），建议管理员在后台创建 | 已核实（原文） |

> ⚠️ 第 5 项是本设计**唯一需要沙箱验证**的飞书侧要点。不要把它当确定结论写进代码注释。
> 另外第 4 项"按定义订阅"的两个已知硬点：`tenant_access_token` 订阅要求应用具备所需权限；**订阅是按定义注册的，新增定义必须补订阅**。

## 3. 三个工程要点（不写会出事）

### 3.1 回调必须 3 秒内返回，重活全部异步

官方硬约束：长连接事件**须 3 秒内处理完成且不抛异常**，否则触发重推（重推节奏 15s/5min/1h/6h，最多 4 次）。
且长连接是**集群模式不支持广播**——同一应用多客户端时**只有随机一个收到**。

→ **消费端必须单实例**；回调**只做一件事：写 `inbox` 表并返回**。识别、匹配、落账、发消息全部由 worker 异步做。

### 3.2 幂等 + 严格状态机（飞书是"至少一次"投递，且可能乱序）

```go
// 合法迁移白名单：不在此表内的一律丢弃并记审计，绝不动账
var allowed = map[State][]State{
    StatePending:  {StateApproved, StateRejected, StateCanceled},
    StateApproved: {}, StateRejected: {}, StateCanceled: {}, // 终态不可再变
}
```

- 同一 `event_id` 重复到达 → 直接返回成功，不重复处理（幂等键唯一索引）。
- 事件乱序（如 `APPROVED` 先到、`PENDING` 后到）→ **状态机拦截**，这是乱序下唯一可靠的护栏。
- 卡片按钮回调同样要幂等 + 校验操作人身份（`card.action.trigger` 可走长连接）。

### 3.3 关联键是 `submission_id`，不是 `approval_code`

`approval_code` 只标识"这是哪张审批**定义**"，**它不告诉你这是哪一单**。所以：

1. 审批表单里放一个**只读文本控件**承载 `submission_id`（创建实例时灌入）；
2. 本地维护 `instance_code ↔ submission_id ↔ batch_id` 映射表；
3. 事件回来**先查映射表**，查不到就**告警而不是猜**（宁可不落账也不要落错账）。

## 4. 必须提前决定的取舍：审批表单值**创建后不能改**

审批实例一旦创建，`form` 就固定了。而识别是异步的（几秒到几十秒）。于是有两条路：

| | **A：等匹配完再建实例**（推荐） | B：提交即建实例 |
|---|---|---|
| 队员体验 | 提交后几十秒才看到审批进入财务 | 立刻进入审批 |
| 匹配结论给财务 | ✅ 直接灌进表单控件，审批人一眼可见 | ❌ 只能靠机器人卡片事后补发 |
| 风险 | 识别挂掉则审批起不来 | 财务可能**先批了、结论才到** |

**采纳 A + 超时降级**：识别 90 s 未完成 → **先用空结论创建实例**（保证审批不因识别故障卡住），
结论算完后通过**机器人卡片补发**给审批人。这样"识别故障"降级为"信息不全"，而不是"流程中断"。

### 4.1 分档审批与预算校验放哪

- **分档审批**：用飞书后台的**条件分支**，条件是"金额"控件。已核实分支条件支持
  **单选/多选/数字/金额/计算公式/日期区间/明细汇总** → 不必写代码。
- **预算校验**：放在**创建实例之前**。余额不足 → **不创建实例**，发卡片告知申请人"该资金池可用不足"。
  这样审批流里不需要再管余额，也就不会出现"审批通过但钱不够"。
- **职责分离**：`申请人 ≠ 审批人` 是硬约束。审批定义的节点审批人若用"提交人自选"，
  服务在创建实例时传入 `node_approver_open_id_list`，**必须校验不等于申请人**。

### 4.2 匹配失败/缺材料时怎么"补"

这是设计里最容易绕晕的一环，明确三条规则：

1. **不允许改已创建的审批实例**（表单值不可改）。
2. **缺材料 + 还没审批 → 队员撤回重交**：本地按 `image_sha256` 识别为**同一张发票** → 命中 L1，
   **把新图挂到原 `submission_id`**（补全材料），而不是建新单。这正是 L1 指纹"批次占用"语义的用武之地。
3. **已驳回 → 重新提交**生成新 `submission_id`，但**沿用同一发票指纹**（已有 L1 记录），
   不会被误判为"重复报销"。

## 5. 状态映射（飞书 → 本地）

| 飞书审批实例状态 | 本地 `submission.state` | 副作用 |
|---|---|---|
| `PENDING` | `IN_APPROVAL` | 置"已占用"（budget reserved） |
| `APPROVED` | `APPROVED` | 落账（ledger）；占用转已支出；通知申请人 |
| `REJECTED` | `REJECTED` | **释放占用**（budget reserved 回弹）；通知申请人 + 驳回理由 |
| `CANCELED`（撤回） | `WITHDRAWN` | 释放占用；**发票指纹保留**（允许补材料重交） |

> 注意：**"审批通过"≠"钱已到账"**。垫付返还需要独立的"学校到账 → 返还个人"环节
> （`R-22 资金返还`，架构稿 §8 已标注字段口径待补）。不要让 `APPROVED` 直接改资金池余额。

## 7. 立即可做的沙箱验证（半天，3 件事）

1. **建一个测试审批定义**（后台手工，含一个金额控件 + 一条条件分支），调 `subscribe` 后
   在客户端发起一次，确认**长连接能收到哪些事件、事件体里有哪些字段**（尤其是否带 `instance_code` 与表单值）。
    → 这一步直接决定第 5 节的映射表能不能落地。
2. **验证创建实例时能否灌入只读文本控件值**（`submission_id`、`match_summary`、`defects`）。
3. **验证附件/图片控件在创建实例 API 中的支持情况**（`02-feishu-capability-facts.md` 已标注"创建实例 API 有不支持的控件类型"）。
    → 若附件控件不支持，走本文 §1 的设计（**图片留多维表格，审批只带 `submission_id` + 金额 + 缺陷清单**），
      审批人看图的入口放在**机器人卡片的 deep link**（审批表单里**放不了可点击链接**，官方"暂无"）。
