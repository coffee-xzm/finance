## 0. 先说结论

| 项 | 结论 |
|---|---|
| 截图里的插件 | 官方叫「**多维表格插件**」，而截图那种侧边栏形态属于其中的「**侧边栏插件**」（不是记录视图/数据表视图插件）；**不是**自动化流程、不是字段捷径、不是连接器（已核实，§4.1 F1） |
| 截图那个插件是谁做的 | **三方开发者（杨思宇）开发**，托管在 Replit 官方 `@lark-base` 组织下，被飞书帮助中心点名引用（「超过 1 GB 可使用多维表格『附件批量下载』插件」）——**不是飞书自研**（已核实，§4.1 F10） |
| 我们要不要**自研同类插件** | 视形态而定：**侧边栏插件这条轻量路线值得认真考虑**（不要求开放平台开发者身份、无需上架审批）；但它的**网络能力仍是最大约束**——官方要求 HTTPS + 证书校验 + CORS 且 ACAO 不能为 `*`，**局域网服务依然够不着**，见 §4.1 F2/F3 |
| 推荐形态 | **已拍板并已实现**：侧边栏插件「浏览器内本地打包」（③B-1，见 `docs/30-review/34`）。服务端导出（NAS + 审计）仍在计划内，命名规则两侧共用 |
| 最省事的兜底 | 直接用**官方/市场现成插件**手工导出一次，先满足「这周就要把票据交去报销」的需求；服务端自动化按 §6 分期推进 |
| 最大的硬约束 | 附件的**临时下载链接只有 24 小时有效期**、`batch_get_tmp_download_url` **一次最多传 5 个 token**、**开启高级权限的表下载素材必须带 `extra` 鉴权参数**（否则 403）——所以「现取现下、不缓存 URL」这条纪律必须写进实现 |
| 一个意外的好消息 | 插件的附件单元格里带 **`token` + `permission{tableId,recordId,fieldId}`**（已核实，§4.1 F7）——**正好是服务端构造 `extra` 下载高级权限表附件所需的信息**，即插件与服务端组合可以绕开 R3 |
| 另一条可选形态 → **已采用** | **插件「浏览器内本地打包」**（③B-1）：不请求任何自建服务器，用 SDK 拿 URL + 浏览器 JS 打 zip（§4.3）。绕开域名/CORS 全部限制，但**文件落在操作者电脑、无 NAS、无审计**。**2026-09-19 用户拍板走这条，代码已落地**：`bitable-plugin/`，决策记录 `docs/30-review/34` |

一句话：**「选择性」这件事由人在飞书里勾出一份「记录清单」，真正干活的是 Go 服务。**
（飞书原生批量下载**只能「当前视图 / 整表」，没有"只下选中行"**，且单次 1 GB —— 这正是要自建的理由，见 §4.1 F10/R14。）

## 1. 与现有系统的对齐（这是本计划的地基）

现状（已核实，见 `finance-router/data/bitable/schema.md`、`docs/30-review/31`）：

- 两张表：**报销核对**（`tblO66…`，27→16 列）、**报销整合**（`tblyNZ…`，17 列）。
- 每张表都有**三个附件列**（type `17` / `Attachment`）：**发票**、**订单截图**、**付款记录**。
- 每行 = **一张发票**（幂等键 = 审批实例号 + 发票号码），行里还有
  物资所属部门 / 物资种类 / 购买人 / 资金来源 / 图读金额 / 图读日期 / 销方名称 等**可用于命名与分组**的列。
- 「报销整合」是归档表（`人工审核=通过` 后被 `cmd/archive` 复制过去），**天然就是「待交学校」的那批票**。
- 服务形态：`cmd/serve` 常驻，**出站长连接收审批事件**，已有 `-task` 一次性运维任务；
  目前**没有 HTTP 服务**，也没有任何 `batch_get_tmp_download_url` 的调用（下载链路要新建）。
- 附件来源：审批附件（24h authcode 直链）→ `UploadMedia` → 写进多维表格附件列，**已经是长期有效**的 `file_token`。

> 因此「选择性下载」在这套系统里的落点非常明确：
> **选一批行（按视图 / 按人勾选 / 按筛选条件）→ 取这些行的三个附件列 → 按规则命名 → 打包 → 落到 NAS + 交给人**。

## 3. 需求拆解：把「选择性」定义清楚

### 3.1 主路径已定：**勾选记录清单**（用户 2026-09-19 拍板）

用户选择：**按勾选的记录清单导出**，而不是「按视图全量」。

关键在于**「勾选」这一步不要自己开发 UI**：

| 步骤 | 谁做 | 用什么 | 说明 |
|---|---|---|---|
| ① 勾选 | 财务 | **飞书多维表格自带的多选**（Ctrl/Shift 点行；或原生批量下载/导出，筛出想要的记录） | 选中后把 **`审批实例号`（或 `record_id`）列复制/导出成一行一条** |
| ② 交清单 | 财务 | 把清单贴给机器人 / 存成 csv 喂 CLI | 清单只有一列，无需附件、无需外网 |
| ③ 导出 | 服务端 | `cmd/export -records-file list.csv` | 下载三个附件槽 → 按 §3.5 命名 → zip → 落 NAS → 写审计 |

**为什么这样设计（三条理由）**：

1. **勾选的体验飞书已经做好了**，自研插件要先解决「域名白名单 / 沙箱 / SDK 选型 / 发布」四道关（§4.2），
   而它带来的唯一增量只是「把勾选结果传出来」——用一列清单就能替代。
2. **服务端才是能把文件放对地方的人**（NAS + zip + 审计），这点与勾选方式无关。
3. 清单只有 `record_id`/实例号，**不含附件 URL**，天然没有 §4.1 F7 那个「10 分钟链接过期」的坑。

> 备选（不推荐，但保留）：如果将来确实希望「在侧边栏里勾选、点一下就走服务端」，
> 那就是 §4.2 的插件路线；**在此之前不要为它做任何前置投入**。

### 3.2 视图导出（后置的第二种口径）

用户当前选了清单口径，但**视图导出是清单口径的自然超集**，成本只有一个 `-view` 参数：

| 口径 | 参数 | 场景 |
|---|---|---|
| **清单（主）** | `-records-file list.csv` | 补交、抽查、按批次交票 |
| 视图（备） | `-view <view_id>` | 「把 2026-08 归档的全导出来」这种整批动作 |

在两张表上建议建的视图（供将来用）：

| 视图名 | 过滤 | 用途 |
|---|---|---|
| `待交学校` | 报销整合 · 归档时间在本次账期内 | 月度整批报销导出 |
| `按部门` | 按 物资所属部门 分组 | 分部门给复盘用 |
| `缺件` | 核对结果 = 缺件 | 催办前先看缺了什么 |

> ⚠️ 视图是**唯一需要人手工在 UI 建一次**的东西（自动化/仪表盘同理，见能力稿 A4/A8）。
> 建好后服务端只读 `view_id`，不再依赖 UI。
>
> ⚠️ **筛选条件必须写在视图里**：接口在传了 `filter`/`sort` 时会**忽略 `view_id`**（已核实，见 §5.1）。
> 所以 `cmd/export` 的设计是「**`-view` 与 `-filter` 不允许同时传**」，同时传直接报错。

### 3.3 清单的形态与校验（勾选口径的落地细节）

从飞书复制出来的清单**必须只当输入**，服务端要做四类校验（**失败一律报错退出，不静默跳过**）：

| 校验 | 目的 |
|---|---|
| 标识类型识别 | 名单可能混着 `审批实例号`（`7DB9ADCF…`）与 `record_id`（`rec…`），按前缀判别，两种都支持 |
| 存在性 | 名单里对不上的行 → 明确列出「第 3 行 `recXXX` 不在表里」 |
| 空附件行 | 该行三个附件列都为空 → 报「这条没有附件」；**这是常见情况**（列表里的附件确实会缺失） |
| 重复行 | 去重并提示（同一实例在「整合表」里可能已有多行 —— 因为**一行 = 一张发票**） |

> ⚠️ **一个必须先讲清的语义**：表里是「**一张发票一行**」（见 `docs/30-review/31`）。
> 所以财务在 UI 里勾选时，勾的是**行**（= 发票），不是**审批单**。
> 若同一审批单有多张发票，勾其中一行只会导出那一行的附件 —— 这是对的，但**要在 `manifest.csv` 与提示里写清楚**，
> 免得财务以为漏了。

### 3.4 记录集合的表达

一次导出 = 一个 **`ExportRequest`**（本地库留痕，可审计）：

```
账期        2026-08
来源表      报销整合 / 报销核对
视图        view_id（可选）
记录 ids    显式清单（可选，路径 C 用）
附件字段    发票 + 订单截图 + 付款记录
命名模板    见 §3.5
分组规则    部门 / 年-月
输出        zip + manifest.csv，落 NAS 与本地备份目录
操作人      飞书 user_id / open_id
```

### 3.5 命名与目录（这是最容易做错、也最影响可用性的部分）

原图文件名基本不可用（审批里的 `image.png`、`<32位hex>.pdf`），所以**必须按行数据重命名**。

建议模板（可在配置里改）：

```
发票          {部门}-{购买人}-{图读日期}-{销方简称}-{金额}元-发票{发票号码后6位}.{ext}
订单截图      {部门}-{购买人}-{图读日期}-{金额}元-订单{n}.{ext}
付款记录      {部门}-{购买人}-{图读日期}-{金额}元-付款{n}.{ext}
```

目录结构：

```
export/2026-08/
├── manifest.csv                 # 每行：实例号/发票号/部门/购买人/金额/日期/文件名/原始file_token/sha256
├── 视觉组/
│   ├── 张某某-20260602-某公司-48.90元-发票123456.pdf
│   ├── 张某某-20260602-48.90元-订单1.jpg
│   └── 张某某-20260602-48.90元-付款1.jpg
└── 电控组/...
```

**三条硬规则**：

1. **文件名必须做清洗**：去除 `/ \ : * ? " < > |`、控制字符与首尾空白，长度截断（建议 ≤ 120 字节），
   否则 Windows 侧解压直接失败。
2. **重名必须可处理**：同一 `{部门}-{购买人}-{日期}-{金额}` 撞车时追加 `-2`、`-3`，
   并在 `manifest.csv` 里留原始标识。
3. **`manifest.csv` 用 UTF-8 + BOM**，否则 Excel 打开是乱码（中文财务场景必踩）。

## 4. 技术路线与取舍（①现成 ②服务端 ③插件 ④插件本地打包）

### 路线 ① 飞书自带能力 + 现成插件（零开发，先解燃眉之急）

- **原生能力（已核实，不需要装任何插件）**：官方帮助中心原文——
  「在**表格视图**中，**右键点击附件字段**，选择 **批量下载附件**。在弹窗中，选择要下载的数据范围，
  你可以选择**仅下载当前视图**中的附件，也可以下载**数据表中所有的附件**。设置附件的命名方式，
  你可以选择**以附件原本的名称命名**，也可以选择**索引列（首列）为附件名称**。」
  （[官方帮助：使用附件字段](https://www.feishu.cn/hc/zh-CN/articles/532389628624)）
- **原生的三个硬限制（已核实）**：
  1. **每次最多下载 1 GB**（同一篇 FAQ 原文）；
  2. 范围只有「**当前视图 / 整表**」两种，**没有「只下选中的几行」**；
  3. 只在**表格视图**可用。
- **超过 1 GB 的官方推荐**：同一篇 FAQ 原文「**超过 1 GB 可使用多维表格「附件批量下载」插件**」；
  该插件由三方开发者 **@杨思宇** 开发，托管在 Replit 官方 `@lark-base` 组织下
  （[飞书官网内容页](https://www.feishu.cn/content/7297…)）——**截图里那个就是它**。
- **做什么**：需要应急时，直接用原生右键批量下载，或装这个插件手工选、zip 下载到**操作者本机**。
- **优点**：今天就能用；不动代码；满足「这周就要交报销」。
- **缺点**：落点在**人的电脑**，不是 NAS；**没有导出审计日志**（谁在什么时候导了哪些票）；
  大批量（爆发期一周 588 张图）会卡浏览器；插件为个人开发者作品、**功能细节官方无公开说明**（§4.4）。
- **结论**：**作为兜底与验收对照**（也用来核对我们的服务端导出结果是否一致）。

### 路线 ② 纯 API + Go 服务（推荐主线）

- **做什么**：服务端按视图/清单拉记录 → 取附件临时链接 → 下载 → 命名 → 打 zip → 落 NAS + 本地备份 → 留审计。
- **优点**：一次跑完、可重复、可审计；避开浏览器内存与页面限制；能直接吃现成的 `Client`（重试/限流已实现）。
- **缺点**：没有「点一下就下」的界面，需要一个触发方式（CLI 任务 / 机器人指令 / 极简本地页面）。
- **结论**：**主线实现**，见 §5。

### 路线 ③ 自研插件（有两条子路线，成本与天花板都不同）

**平台事实（已核实）**：官方把手写插件分成**两条并行体系**——

| | ③A · 应用平台插件 | ③B · **侧边栏插件**（= 扩展脚本） |
|---|---|---|
| 官方叫法 | 多维表格插件（记录视图 / 数据表视图 / 自动化操作） | 《多维表格**侧边栏**插件开发指南》 |
| 开发前提 | **要开放平台开发者身份 + 企业自建应用**，需管理员审核发布 | **不要开发者身份、无需上架审批**，默认「仅自己可用」 |
| SDK | `@lark-opdev/block-bitable-api` | `@lark-base-open/js-sdk`（1.0.2） |
| 网络 | 开发指南写「应配置**服务器域名白名单**」 | 另一篇《网络》文档写「**无需开发者配置服务器域名**」——**官方自相矛盾**（§4.4 未定论项） |

> **截图那个插件属于 ③B（侧边栏插件）**：右上角「多维表格插件」图标 → 右侧面板【已核实】。

- **③B-1 · 本地打包插件（推荐度最高的一种插件形态）**：
  用 `ui.selectRecordIdList()` 唤起官方**选择记录对话框**，或 `view.getVisibleRecordIdList()` 取当前视图行；
  再用 `table.getAttachmentUrl(token, fieldId, recordId)` 拿到 URL，**在浏览器里直接打 zip 并下载**。
  **完全不请求任何自建服务器 → 域名白名单、CORS、HTTPS 全部绕开**（网络约束只对"访问自建服务"生效）。
  代价：文件落在**操作者电脑**，**没有 NAS、没有审计**——等于把路线 ① 的现成插件自己重做一遍。
- **③B-2 · 插件 + 服务端**：插件把「记录清单 + 附件 `token` + `permission{tableId,recordId,fieldId}`」POST 给服务端，
  由服务端下载、命名、zip、落 NAS、写审计。**能同时拿到体验与审计**，但要求服务端有一个
  **HTTPS + 有效证书 + 正确 CORS（ACAO 不能为 `*`）** 的地址，且局域网地址**依然不可行**（§4.1 F2）。
- **共性硬约束**：插件的附件 URL **只有效 10 分钟**（F7）；`Bridge.getUserId` 与开放平台 userId **不通**（F9）；
  插件**不能后台常驻**（只在人打开面板时存在）。
- **结论**：**P3 的可选项**。若要做，优先 **③B-1**（不碰域名问题、最有把握）；③B-2 只有在拿到 HTTPS 域名后才谈。

> **一句话取舍**：没有域的插件是**遥控器但没信号**——它能自己下载（本地打包），却指挥不动 NAS 上的发动机。

## 5. 服务端实现设计（路线 ② 主线的落地细节）

### 5.1 新增的客户端能力（`internal/feishu/client.go`）

| 能力 | 接口 | 要点 |
|---|---|---|
| 按视图搜记录 | `POST /bitable/v1/apps/:app_token/tables/:table_id/records/search` | 现有 `SearchBitableRecords` **要补 `view_id` 与分页**（当前只取 1 页）。**已核实**：`page_size` 上限 500、用 `page_token` 翻页、支持 `field_names` 只取需要的列；返回体含 `has_more`/`total` |
| 取临时下载链接 | ⚠️ **`GET`** `/drive/v1/medias/batch_get_tmp_download_url`（**不是我原先写的 POST**） | **已核实**：一次最多 **5** 个 `file_token`；链接**有效期 24 小时**；高级权限表需带 `extra`。scope 任一即可：`bitable:app` / `bitable:app:readonly` / `docs:document.media:download` / `drive:drive` / `drive:drive:readonly` 等 |
| 下载素材 | `GET <tmp_url>` | 直链自带鉴权即可下载；**不要缓存 URL 到磁盘** |
| （可选）直接下载 | `GET /drive/v1/medias/:file_token/download` | 同族 QPS 有明文：**5 QPS / 10000 次每天**（`batch_get_tmp_download_url` 本身官方只标「特殊频控」，未给数字） |

> **附件字段里到底有什么（已核实）**：记录里附件值是 `[{file_token, name, size, type, url, tmp_url}]` 六个 key；
> **写入时只认 `file_token`**；**单个单元格最多 100 个附件**（另载：每表最多 20000 个附件、单附件 ≤ 2GB）。

> **已核实的两个坑（官方原文）**：
> 1. `search` 的 `view_id` **在传了 `filter` 或 `sort` 时会被忽略**——「按视图 + 再加条件」不是叠加关系。
>    → 要么只用 `view_id`（筛选条件写进视图本身），要么不用视图、全用 `filter`。**不要同时依赖两者**。
> 2. `page_size` 最大 500，且响应体过大时返回 `1254030 TooLargeResponse`。
>    → 拉记录时用 `field_names` **只取导出需要的列**，不要把附件列的原始 URL 全量拉回来。


**仍需实测的部分**（照 `cmd/doctor` 的风格加一个 `cmd/download-probe`）：

1. `batch_get_tmp_download_url` 返回结构与本租户的实际 QPS（**数量上限 5 已由官方文档核实**，不必再猜）；
2. 该 app 在**目标表**上是否有 `drive:drive` / `bitable:app` 读素材权限；
3. **高级权限是否开启** → 若开启，`extra` 参数怎么构造（`bitablePerm`），不构造就是 403。

> ⚠️ 这一条是**整个计划的第一个门禁**：探测不过，路线 ② 直接不成立，
> 只能退回路线 ① 或改走「服务端已有本地原图」的旁路（见 §5.5）。

### 5.2 新增命令 `cmd/export`（**清单口径为主**，先 CLI，后接机器人）

```
# ① 主路径：勾选出来的清单（一行一个 实例号 或 record_id）
go run ./cmd/export -table 整合 -records-file list.csv -out export/2026-08-批次1
go run ./cmd/export -table 整合 -records recA,recB,recC -naming "{部门}-{购买人}-{金额}元-{槽位}"

# ② 备选：整批按视图
go run ./cmd/export -table 整合 -view <view_id> -out export/2026-08

# ③ 永远是先干跑
go run ./cmd/export -table 整合 -records-file list.csv -dry-run   # 只打印清单与命名结果，不下载
```

参数与行为：

| 参数 | 说明 |
|---|---|
| `-records-file` | **主路径**：csv/txt，一行一个标识；**自动识别 `审批实例号` 与 `record_id`**，自动去重、报错行号 |
| `-records` | 同上，直接写在命令行（少量用） |
| `-view` | 备选：按视图全量。与 `-filter` **互斥**（见 §3.2 的接口约束） |
| `-fields` | 附件槽位，默认 `发票,订单截图,付款记录` |
| `-naming` | 命名模板，默认取配置 |
| `-out` | 输出目录；zip 与 `manifest.csv` 落在这里 |
| `-dry-run` | 只输出「会导哪些行 → 会命名成什么 → 哪些行有问题」，**不调下载接口** |
| `-force` | 覆盖已存在的同名文件（默认跳过已导过的） |

分支与纪律：

- **串行下载**（或有限并发但按表串行）；不碰写接口，因此不会触发 `1254291 Write conflict`。
- 失败**不得静默吞掉**（沿用 `处理说明` 的教训）：每个文件一条结果，最后打印 `成功/失败/跳过` 汇总，
  `manifest.csv` 里保留失败原因。
- **空附件行单独统计并显著提示**（清单里常有）：例如「12 行中有 3 行的『订单截图』为空」，
  而不是悄悄少几个文件。
- 幂等：`manifest.csv` 里带 `sha256`，重复导出时**已知文件跳过**（`-force` 才覆盖）。

### 5.3 本地库留痕（`internal/store`）

新增两张（或一张）表：

```
export_batch     批次号 / 口径(list|view) / 来源表 / 视图id / 清单sha256 / 清单行数 / 字段 / 命名模板
                 / 操作人 / 开始时间 / 结束时间 / 成功数 / 失败数 / 空附件数 / zip 路径
export_item      批次号 / record_id / 实例号 / 槽位 / file_token / 原始文件名 / 落盘文件名
                 / sha256 / 字节数 / 状态 / 失败原因
```

> `清单sha256` 存的是**清单文件内容的哈希**，不是原文 —— 既能证明「这批是照哪份清单导的」，又不用把名单搬进库。

对应需求矩阵里的「**导出发票并保存导出记录**」「信息包含：操作人、操作时间、操作事项」（高优先级）。
→ 这张表就是那条需求的**审计底账**，同时可作为「报销批次」字段回写的依据（后续阶段）。

### 5.4 落盘与交付

| 位置 | 内容 | 说明 |
|---|---|---|
| NAS（局域网） | `export/<账期>/…` 原始导出 | 票据原图的**第二副本**（能力稿结论 8：不要把附件当唯一副本） |
| Linux 主机 | `export/<账期>.zip` | 交学校/报销时直接取这个文件 |
| 本地库 | `export_batch` / `export_item` | 审计与重放 |

配置新增一节（`config.example.yml`）：

```yaml
export:
  root: "data/export"          # 本机产物
  nas_root: ""                 # NAS 挂载点，留空 = 不复制
  zip: true
  naming: "{部门}-{购买人}-{日期}-{销方}-{金额}元-{槽位}"

  manifest: true               # 生成 manifest.csv（UTF-8+BOM）
  max_files_per_batch: 2000    # 单批上限，防止一次把爆发期全拖下来
```

工作量粗估（不含插件）：P0 ≈ 半天，P1（清单 MVP）≈ 1.5–2 天，P2（视图口径）≈ 半天，P3（机器人收清单）≈ 1 天，P3(插件) ≈ 3–5 天（另计）。

## 7. 风险与硬约束（每条都对应一个已核实的事实）

| # | 风险 | 依据 | 对策 |
|---|---|---|---|
| R1 | **临时链接 24h 失效**，缓存 URL 必炸 | 能力稿 A7；`client.go:626` 实测 authcode 起止相差 86400s | **现取现下**；`export_batch` 只存 `file_token`，不存 URL |
| R2 | `batch_get_tmp_download_url` **一次最多 5 个 token** | **已核实**（官方文档原文） | 分批取链接（5 个/批），并在批内复用同一批下载；不要幻想一次取几百个 |
| R3 | **高级权限表下载素材 403** | 能力稿 A7 原文：需额外 `extra`（`bitablePerm`） | P0 探测里**专门验这一条**；开了高级权限就必须实现 `extra` |
| R4 | **`file_token` 不能跨表复用** | 能力稿 A7 | 导出即下载，不做 token 搬运；跨表要重新上传 |
| R5 | **API 月调用量上限**（免费版 100 万次/月）与读 QPS 20/s | 能力稿 A3/E17 | 分批 + 退避；导出是低频人工动作，量级安全 |
| R6 | **同表禁止并发写** | 能力稿 A3（`1254291`） | 导出只读；将来回写批次号必须走既有串行队列 |
| R7 | **插件沙箱访问不了 NAS/局域网服务**（须 HTTPS+证书，局域网地址无解） | **已核实**（官方《网络》文档，见 §4.1 F2/M7；另：域名白名单是否强制，官方两处**自相矛盾**） | 即 R12。若要插件，优先 **③B-1 本地打包**（不连服务端） |
| R8 | **文件名撞车/非法字符**导致解压失败 | 实测经验（原图名不可读） | §3.5 三条硬规则 + 单测覆盖清洗函数 |
| R9 | **爆发期大导出**（一周 588 张图）超时/占满内存 | 能力稿 §5 实测分布 | 流式写 zip（`archive/zip` 边下边写），不整批进内存；`max_files_per_batch` 兜底 |
| R10 | 导出的「抄本」与表里不一致（人改了表 / 附件被换） | — | `manifest.csv` 记 `sha256` + `file_token` + 导出时间；重导时可比对 |
| R11 | **`view_id` 与 `filter`/`sort` 不叠加**：传了后两者，视图被忽略 | **已核实**（官方原文） | 二选一：筛选逻辑**写进视图**，或不用视图全用 `filter`；在 `cmd/export` 里对同时传参**直接报错**，避免静默导出超集 |
| R12 | **自研插件够不着局域网服务**：插件须 HTTPS + 证书校验 + CORS（ACAO 不能为 `*`），局域网地址无解 | **已核实**（官方《网络》文档，见 §4.1 F2/M7） | 路线 ③ 先把 §4.2 三问回答完再开工；否则插件只做「选择器 + 把清单交给人/机器人」，不直连服务端 |
| R13 | **插件给出的附件链接只活 10 分钟**，且 userId 与开放平台不通 | **已核实**（官方 SDK 文档 §4.1 F7/F9） | 插件只传 `token` + `permission`，由服务端现取现下；审计的操作人另定口径 |
| R14 | **飞书原生批量下载没有「只下选中行」**，且**每次上限 1 GB** | **已核实**（官方帮助原文，§4.1） | 这正是我们要自建导出功能的**直接理由**：原生只能「当前视图 / 整表」，没有按清单挑 |

## 8. 已拍板与待拍板

### 8.1 已拍板（2026-09-19，用户）

| # | 问题 | 决定 |
|---|---|---|
| D1 | 形态 | **服务端下载 + 机器人/CLI 触发**（主线） |
| D2 | 「选择性」的口径 | **按勾选的记录清单**（清单来自飞书自带的多选；插件不是必需品） |

### 8.2 待拍板（开工前需要的前三个）

1. **落点**：NAS 的挂载路径是什么？zip 是**放 NAS**、**发到飞书群/私聊**（注意卡片/消息体上限），还是两者都要？
2. **触发者与权限**：谁能导出？只有财务管理员，还是各部门负责人也能导自己部门的？
   （注意免费版**没有行列高级权限**，按部门裁剪只能由服务端做。）
3. **命名与分组**：§3.5 的模板与「按部门分文件夹」是否符合学校/报销方的接收习惯？有没有他们的既定命名要求？

### 8.3 可以晚点答

4. **是否回写**：导出后要不要把「报销批次 / 已交学校」写回 Bitable（需求矩阵里的「更新发票状态：上传批次 / 已报销 / 已到账」）？
5. **数据表列**：主场景是 **报销整合**（归档票）还是 **报销核对**（在审票）？还是两张都要？
   （建议：先只做**报销整合**，因为「交给学校」的票都在那里。）
6. **清单怎么给**：手工复制粘贴 vs 机器人对话上传（P3 决定）。
7. **官方插件能否满足**：截图那个三方插件（§4.1 F10）**能力细节官方没有公开说明**（§4.4 M4）——
   如果要判断「它到底能不能只导选中的行」，需要在客户端里实测一遍。**建议仍自建**：现成插件给不出
   **导出审计底账**，而那是需求矩阵里的高优先级项；且它是个人开发者作品。
8. **（仅当重启插件路线）SDK 选型**：两套 SDK **服务不同插件体系**——侧边栏插件用 `@lark-base-open/js-sdk`，
   应用平台插件用 `@lark-opdev/block-bitable-api`；官方**没有**交叉使用的说明（§4.4 M7）。
   若选 ③B-1，先验证「插件内能拿到附件并本地下载成功」。
