# 现在产出什么、能验证什么

> 回答用户 2026-09-13：「现在会生成什么，有哪些可以用于验证的」
> 并记录两个决定：① **漏读税额**是常见错误；② **订单与发票真不一致暂不处理，把逻辑空出来**。

---

## 0. 两个决策已落地

### 0.1 金额改为「三件套」，专治漏读税额

最常见的读错就是**只读了不含税金额、漏掉税额**。因此证据表拆成三列：

| 字段 | 含义 | 用途 |
|---|---|---|
| **价税合计_分** | 发票【价税合计】栏 | **★ 匹配主口径（含税）** |
| **税额_分** | 发票【税额】栏 | 单独留存，一眼看出是否漏读 |
| **不含税金额_分** | 发票【金额】栏 | 与价税合计差一个税额 |
| **税额自检** | `OK` / `TAX_MISMATCH` / `NO_TAX_FIELD` / `无法判定` | 程序自算：`价税合计 − 不含税 ≈ 税额`？ |

> **判据**：若 `|价税合计 − 不含税 − 税额| > 容差`，标 `TAX_MISMATCH`。
> 若模型只给出一个金额且无从判断是否含税，标 `NO_TAX_FIELD` 并进人工队列——
> **宁可标不确定，也不要静默采信一个可能漏税的金额。**

### 0.2 真不一致：只记录，不处理

「订单金额 ≠ 发票金额」这种情况**暂时不实现任何处置逻辑**，只做两件事：

1. 三个金额**各自入库**（`发票价税合计_分` / `付款金额_分` / `订单金额_分`）；
2. 在 `金额差异说明` 里如实写出，例如：
   `发票 328.00 / 付款 320.00 / 订单 328.00，差额 8.00`。

**代码里留空的地方**：匹配层会有一个 `MismatchPolicy` 接缝，当前实现为 `RecordOnly`（只记录）。
将来要加"差额容忍""超过 N 元升级审批""自动驳回"等策略，都只改这一个实现，不动主流程。

## 2. 多维表格放 wiki：需要补一个权限

你给的 <https://<TENANT>.feishu.cn/wiki/<WIKI_NODE_TOKEN>> 是**知识库节点**，
`<WIKI_NODE_TOKEN>` 是**节点 token，不是文档 token**，必须先解析才能拿到真正的 `app_token`。

我已实现解析（`GET /wiki/v2/spaces/get_node`），但**调用被拒**：

```
code=99991672 Access denied. One of the following scopes is required:
[wiki:wiki, wiki:wiki:readonly, wiki:node:read]
```

**飞书直接给出了申请链接**，点它即可：

```
https://open.feishu.cn/app/<APP_ID>/auth?q=wiki:wiki,wiki:wiki:readonly,wiki:node:read,&op_from=openapi&token_type=tenant
```

开通后再跑一次，就能拿到该 wiki 下的 `space_id` 与文档 `obj_token`。

> ⚠️ 一个已知限制（能力稿 A6 已核实）：**知识库中的多维表格不支持开启高级权限**。
> 对我们的测试无影响（本来也建议测试期不开高级权限）。

## 3. ★ 现在会生成什么（已实测跑通）

新命令 `cmd/extract` —— **整条管线里第一个产生真实数据的命令**：

```bash
go run ./cmd/extract -limit 2          # 处理 recon 抓到的前 2 个实例
go run ./cmd/extract -instance <code>  # 指定实例
```

它做四件事：

1. **现取**实例详情（附件 URL 只有 24 小时有效期，不能缓存）
2. 下载三个附件槽的每个文件 → 算 `sha256`、记录 `Content-Type` 与真实文件名
3. **PDF → PNG**（Qwen3-VL 不支持 PDF 输入）；JPEG 原样留用
4. 若配了 `ocr.api_key` → 调 SiliconFlow 抽取；否则标记 `SKIPPED`

### 3.1 实跑结果（2 个真实实例，6 个文件，0 失败）

| 槽位 | 原始类型 | 尺寸 | 大小 | PNG | 视觉 token(high) |
|---|---|---|---|---|---|
| **发票文件** | `application/pdf` | 1241×827 | 60–156 KB | 1 页 | **1,350** |
| **订单截图** | `image/jpeg` | 1084×2412 | 519–578 KB | — | **3,393** |
| **付款截图** | `image/jpeg` | 1084×2412 | 265 KB | — | **3,393** |

**三个发现**：

1. **发票 PDF 是半张 A4（1241×827，横版）** —— 电子发票确实小，150 dpi 下只要 1,350 token。
2. **截图是 1084×2412 的手机长截图**，token 反而是发票的 **2.5 倍** —— 贵的不是发票，是截图。
3. **分层策略实测省 4.4 倍**：

| 策略 | 每实例 token |
|---|---|
| 全部 `detail=high` | 8,136 |
| **分层（发票 high / 截图 low）** | **1,862** |

> 这条验证了 `detail_by_kind` 的设计不是纸上谈兵：**截图占了 83% 的 token，而它们只需要读金额/日期，用 `low` 就够**。

### 3.2 产物

| 路径 | 内容 |
|---|---|
| `data/extract/manifest.jsonl` | 每实例一行：槽位/文件名/媒体类型/大小/sha256/页数/PNG 路径/估算 token |
| `data/extract/files/<实例号>/` | 预处理后的图（`invoice-1-1.png`、`order-1.jpg`、`payment-1.jpg`） |

## 5. 一个重要的量级修正（实测）

原估算「年 300–600 张票」**方向对，但载荷极不均匀**：

| 时间窗 | 实例数 |
|---|---|
| 08-15 ~ 08-22 | 4 |
| 08-22 ~ 08-29 | 3 |
| **08-29 ~ 09-06** | **196** ← 报销季爆发 |
| 09-06 ~ 09-13 | 20 |

**结论**：
- 常态每周 3–4 条；**爆发期一周 196 条**（≈588 张图）。
- 所以**不能按 30 天线性外推年量**；年量更可能落在 **200–800** 区间。
- 对成本无影响：按每实例 1,862 token，**800 实例/年 ≈ 1.5M token ≈ 几元到几十元/年**。
- 对设计有影响：**必须能扛住一周 588 张图的峰值**。以 `concurrency=3`、单张 5–20 秒计，
  588 张约需 30–70 分钟跑完 —— 完全可接受，但**队列必须能缓冲**，不能同步等待。

> ⚠️ 另记一个过程教训：我第一版分布统计脚本把**请求失败**误当成「0 条」，
> 得出过"全天全周都是 0"的错误结论。已改为**显式检查错误**后再统计。
> 这正好印证验证表第 15 列（处理说明）的存在意义：**失败必须被如实记录，不能静默吞掉。**
