# 人工审核闭环与写入位置

> 用户 2026-09-13 的四个要求：
> 1. 解释「自洽的错抓不到」；
> 2. 低置信度**发消息给我**；
> 3. 多维表格**多一个字段判断是否通过**；人工通过后从**源表**归档到**整合表**；
> 4. **先确定多维表格写在哪**（权限已给，消息权限未给）。

---

## 1. 什么叫「自洽的错抓不到」

那个校验式是：`价税合计 − 不含税 ≈ 税额？`

**问题：等式两边都来自同一个模型的同一次输出。** 模型"知道"发票上有这个关系，
所以它读到的数字无论对错，都会**凑成满足这个关系**：

```
真值:        455 + 5   = 460
150dpi 输出: 450 + 10  = 460    ← 自洽，校验通过，但错了
300dpi 输出: 4500 + 100 = 4600  ← 也自洽，校验通过，错得更离谱
```

**不是巧合，是必然** —— 模型在保持它认为的结构关系。

> **原则：校验只有在输入来源【互相独立】时才有用。**
> 自校验只能发现"内部矛盾"，发现不了"内部一致地错"。

| 校验 | 两侧来源 | 能否抓自洽的错 |
|---|---|---|
| 税额自洽 | **同一个模型输出**的两个数字 | ❌ **不能** |
| **大写校验** | 阿拉伯数字 vs **中文大写**（两套字形） | ✅ 能 |
| **三单互核** | 发票 / 订单 / 付款 **三张独立的图** | ✅ 能（最强） |

这也是为什么 `大写校验` 被定为**主校验**、`税额自检` 降为辅助。

## 2. ★ 写入位置：确认方案

**位置**：你给的 wiki 节点

```
https://<TENANT>.feishu.cn/wiki/<WIKI_NODE_TOKEN>
  ↓ 解析（GET /wiki/v2/spaces/get_node）
space_id  = 7443744390131810323
obj_type  = bitable
obj_token = <BITABLE_APP_TOKEN>   ← 这就是 app_token
现有内容   = 1 张表「数据表」、1 个字段（默认空表）
```

**两张表都放这一个文档里**（`app_token = <BITABLE_APP_TOKEN>`）：

| 表 | 角色 | 字段数 | 谁写 |
|---|---|---|---|
| **`识别结果_待审`**（源表） | 暂存 + 人审 | **20** | 机器写业务字段；**人只改「人工审核」「审核备注」** |
| **`报销整合`**（整合表） | 审核通过后归档 | **12** | 只有服务写（复制自源表） |

> 若你希望整合表放在**另一个文档**（比如以后要并入正式台账），现在说，改一行配置即可。
> 默认放同一文档是因为：同文档内跨表复制最简单，且 `file_token` 不可跨表复用的限制不涉及（我们不用附件字段）。

## 3. 人工审核闭环设计

```
① 抽取完成
   └─► 写【识别结果_待审】：业务字段 + 处理状态 + 置信度 + 大写校验 + 税额自检
                             人工审核 = 「待审」（默认）、已归档 = 未勾

② 判定是否需要人看（任一成立即需人工）
   · 处理状态 ≠ OK
   · 大写校验 ≠ OK          ← ★ 主判据
   · 税额自检 = TAX_MISMATCH
   · 置信度 < 阈值
   · 三单互核 ≠ MATCHED

③ 需要人工 → 发飞书消息给管理员（你）
   消息含：实例号、槽位、金额、失败原因、**直达该行的链接**

④ 人在表里看原图与数字，把「人工审核」改成「通过」或「驳回」
   （驳回时填「审核备注」）

⑤ 服务检测到「通过」
   ├─ 复制该行到【报销整合】（带 来源表行 / 归档时间）
   └─ 回写源表：审核时间、已归档 ✓（幂等标记）

   检测方式（两选一，见 §3.2）
```

### 3.1 三个设计取舍

| # | 取舍 | 选择 | 理由 |
|---|---|---|---|
| 1 | 归档是**复制**还是**移动** | **复制** | 源表保留全部痕迹，符合 append-only 审计要求；移动会丢过程 |
| 2 | 幂等靠什么 | 源表的**`已归档`复选框** | 服务重启/重复扫描时不会重复归档；比"查整合表是否存在"更快更可靠 |
| 3 | 人改哪个字段 | **只改 `人工审核` / `审核备注`** | 其他字段由服务权威写入；这正是"同一字段只有一个写者"原则的落地 |

### 3.2 怎么检测"人点通过了"

| 方式 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **轮询**（每 N 分钟扫源表 `人工审核=通过 且 已归档=false`） | 实现简单、**不需要额外权限/订阅**、天然幂等 | 有延迟（可接受，人工审核本就是异步的） | ✅ **测试期用这个** |
| `drive.file.bitable_record_changed_v1` 事件 | 实时 | 需**按文档**订阅云文档事件、需 `tenant_access_token` + 双身份权限；且**公式字段变化不触发** | 生产期再上 |

> 轮询还有个好性质：**它天然是"最终一致"的**，服务挂掉重启后仍能补上漏掉的归档。

### 3.3 关于 `人工审核` 字段的两个细节

1. **飞书没有"行级锁"**：人正在改、服务同时在写，可能出现覆盖。缓解：
   **服务只写业务字段，绝不写 `人工审核`/`审核备注`** —— 分工明确就不会撞。
2. **默认值**：飞书新增选项时**没有"默认值"API**。规避：服务写记录时**显式带上 `人工审核="待审"`**，
   不依赖字段默认值。

## 4. 需要的权限（当前缺的）

### 4.1 多维表格写入 —— **实测被拒**

```
POST .../tables/<TABLE_OTHER_2>/fields
→ HTTP 403 code=91403 Forbidden
```

当前只有只读（`bitable:app:readonly`）。**建字段就失败了**，说明写权限确实没给。

| 操作 | scope（任选一个） |
|---|---|
| 新增数据表 | `base:table:create` 或 **`bitable:app`** |
| 新增字段 | `base:field:create` 或 **`bitable:app`** |
| 新增记录 | `base:record:create` 或 **`bitable:app`** |
| 更新记录 | `base:record:update` 或 **`bitable:app`** |

**建议直接给 `bitable:app`**（"查看、评论、编辑和管理多维表格"），一个顶四个。申请链接：

```
https://open.feishu.cn/app/<APP_ID>/auth?q=bitable:app&op_from=openapi&token_type=tenant
```

### 4.2 发消息 —— 你说还没给，确实需要

| 用途 | scope |
|---|---|
| 给管理员发单聊消息 | `im:message`（或 `im:message:send_as_bot`） |
| 可选：互动卡片按钮 | `im:message` + 卡片回调 `card.action.trigger`（可走长连接） |

还需：
- **开启机器人能力**
- **把管理员（你）加入应用可用范围** —— 官方只要求"用户在机器人可用范围内"，**不需要先有会话**

另需 **你的 `open_id`** 作为收件人（`receive_id_type=open_id`）。

> ⚠️ 一个可选但省事的改进：如果给互动卡片加"通过/驳回"按钮，
> 你就可以**在消息里直接审**，不用切到表格。卡片回调 `card.action.trigger` **支持长连接**，
> 不需要公网入口。但按钮操作要幂等 + 校验操作人身份，实现量比轮询大。
> **建议先做"消息通知 + 表里点通过"，跑顺了再加按钮。**

## 5. 落地顺序

1. **你补 `bitable:app`** → 我跑 `bitable-init` 建两张表（20 + 12 字段，含单选项）
2. 我把识别结果写进源表（现在是落本地 `manifest.jsonl`）
3. 实现轮询归档（源表 `人工审核=通过` → 复制到整合表 → 回写 `已归档`）
4. **你补 `im:message` + 开机器人能力** → 接低置信度通知
5. （可选）互动卡片按钮，直接在消息里审
