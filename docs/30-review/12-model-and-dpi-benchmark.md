# 模型横评与 DPI 结论（实测）

> 用户 2026-09-13 提问：什么是 DPI、为什么要限制它；如果成功率不高，试试 `Qwen/Qwen3.5-4B` / `9B` / `27B`。
> 本文是这两问的实测回答。**所有真值均由人工核图确认**，非模型自证。

---

## 1. 什么是 DPI，为什么要"限制"它

**DPI = Dots Per Inch（每英寸点数）**。PDF 是矢量/页面描述格式，本身不含像素；
要交给视觉模型必须先**光栅化**，DPI 就是转换密度：

```
像素 = 英寸 × DPI
A4 = 8.27 × 11.69 英寸
  @150 dpi → 1240 × 1755 px
  @300 dpi → 2480 × 3509 px
```

### 1.1 两个相反的压力

| 提高 DPI | 后果 |
|---|---|
| ✅ 小字更清楚 | 发票票号、纳税人识别号、税额这类小字才读得到 |
| ❌ **token 暴涨** | Qwen 视觉 token ≈ `ceil(h/28)×ceil(w/28)`，**线性尺寸翻倍 → token 翻约 4 倍** |

实测同一张发票：

| DPI | 像素 | 视觉 token |
|---|---|---|
| 150 | 1241×827 | 1,350 |
| 200 | 1654×1103 | 2,400 |
| 250 | 2067×1378 | 3,700 |
| **300** | **2481×1654** | **5,340** |

**所以"限制 DPI"不是目的，是在成本与准确率之间选点。而实测证明：我原来默认的 150 dpi 选低了。**

### 1.2 150 dpi 错在哪（核心教训）

同一张 ¥4.60 的发票，真值 **460 / 5 / 455**（人工核图）：

| | 真值 | 150 dpi | 300 dpi |
|---|---|---|---|
| 价税合计 | 460 | 460 ✓ | 4600 ✗ |
| 税额 | **5** | 10 ✗ | 100 ✗ |
| 不含税 | **455** | 450 ✗ | 4500 ✗ |
| 发票号码 | <INVOICE_NO_3> | null ✗ | ✓ |
| 销售方税号 | 91330782MA29M3QW4H | null ✗ | ✓ |

**150 dpi 下模型读不清 ¥4.55 / ¥0.05 这种小字，于是"编"了一个自洽的三元组。**

### 1.3 ★ 由此推翻了我自己的一个设计

我原以为 `价税合计 − 不含税 ≈ 税额` 这个自检能防漏读税额。**它挡不住**：

```
真值:        455 + 5  = 460
150dpi 幻觉: 450 + 10 = 460   ← 也自洽，自检 = OK
300dpi 幻觉: 4500+100 = 4600  ← 也自洽，自检 = OK
```

**算术自洽 ≠ 事实正确。** 自检通过不代表读对了。

## 2. ★ 更好的校验码：票面自带的大写金额

中文发票上有 **`价税合计（大写）`**，例：`肆圆陆角整` = ¥4.60。

它是**另一套字形**，与小写**独立出错** → 是票面天生的正交校验码。已实现解析器
（`internal/ocr/uppercase.go`，10 个单测全过）：

```
✓ "肆圆陆角整"        → 460 分
✓ "叁圆贰角陆分"      → 326 分
✓ "贰佰贰拾捌圆叁角壹分" → 22831 分
✓ "壹佰万圆整"        → 100000000 分
```

**实测它确实抓住了 10 倍错误**：`Qwen3-VL-30B-A3B` 在 ¥4.60 那张票上给出
`4600 / 100 / 4500`，但大写抄回 `肆圆陆角整`（=460）→ **`UPPER_MISMATCH`**。
而同一份输出的 `税校验 = OK`。

> **结论：`CheckUpper` 比 `CheckTax` 可靠，应作为主校验；`CheckTax` 降为辅助。**

## 3. 模型横评（6 模型 × 2 张难票，300 dpi）

真值（人工核图）：

| 发票 | 价税合计 | 税额 | 不含税 | 发票号码 |
|---|---|---|---|---|
| 宁波盼宸五金 | 460 | 5 | 455 | <INVOICE_NO_3> |
| 兴化永超五金 | 326 | 37 | 289 | <INVOICE_NO_2> |

### 3.1 结果

| 模型 | 宁波盼宸 | 兴化永超 | 全对 | 用时 |
|---|---|---|---|---|
| **`Qwen/Qwen3-VL-32B-Instruct`** | **全对 ✓** | **全对 ✓** | **2/2** | **10s / 13s** |
| `Qwen/Qwen3-VL-30B-A3B-Instruct`（原选） | 4600✗ 100✗ 4500✗ | 全对 ✓ | 1/2 | 14s / 9s |
| `Qwen/Qwen3.5-27B` | 全对 ✓ | 金额全对，**号码漏** | 1.5/2 | 31s / 26s |
| `Qwen/Qwen3.5-9B` | 全对 ✓ | **全 null ✗** | 1/2 | 39s / 37s |
| `Qwen/Qwen3.5-4B` | 全对 ✓ | **全 null ✗** | 1/2 | 19s / 50s |
| `Qwen/Qwen3-VL-8B-Instruct` | **全 null ✗** | **全 null ✗** | **0/2** | 61s / 68s |

### 3.2 三条结论

1. **`Qwen/Qwen3-VL-32B-Instruct` 是明确赢家** —— 唯一 2/2 全对，**而且最快**（10s/13s）。
   已把 `config.yml` 切到它。
2. **小模型不可靠，且不是"稍差"而是"整条交白卷"**：
   - 8B：两次都全 null（还是最慢的）
   - 3.5-4B / 3.5-9B：各错一张，且都是全 null
   → **不能靠"降规格省钱"，会直接丢掉数据。**
3. **你提的 `Qwen3.5` 系列确实能读图**（4B/9B/27B 都接受了图片，第一张票全对），
   但**一致性和速度都不如 VL-32B**。

### 3.3 ★ 推理模型的坑（必须记住）

`Qwen3.5-*` 与 `*VL-*-Thinking` 是**推理模型**，输出含 `reasoning_content`。
第一次测试我用 `max_tokens=64`，**返回内容为空** —— 因为思维链把额度吃光了。

**用法：`max_tokens ≥ 2000`**（我已把 provider 默认调到 3000）。
对照组：非推理的 `Qwen3-VL-8B` 用 64 token 也有输出，推理模型没有。

## 4. 更新后的建议配置

```yaml
ocr:
  model: "Qwen/Qwen3-VL-32B-Instruct"   # ★ 横评赢家
  temperature: 0.0
  max_tokens: 3000                       # 给推理模型留余量（非推理模型无副作用）
  image_detail: "high"
pdf:
  dpi: 300                               # ★ 从 150 提到 300；150 会漏读小字
detail_by_kind:
  invoice: "high"                        # 发票必须 high
  order: "low"                           # 截图只需金额/日期，low 就够
  payment: "low"
```

### 4.1 成本影响（诚实说明）

300 dpi 让发票从 1,350 → 5,340 token。每实例：

| 项 | token |
|---|---|
| 发票（300 dpi, high） | 5,340 |
| 订单截图（low） | 256 |
| 付款截图（low） | 256 |
| **合计** | **≈ 5,852** |

按爆发期一周 196 单 ≈ 1.15 M token/爆发周；全年按 200–800 单估约 **1.2–4.7 M token/年**——
仍是**几元到几十元/年**量级，**准确率远比这点成本重要**。

> 未来可优化：发票只裁"票头（号码/日期）+ 合计块（三个金额）"两个区域送模型，
> 可把 5,340 砍到 1,500 左右。但**裁剪有漏字段风险**，等验证稳定后再做。

## 5. 但即使最好的模型也会错 —— 所以设计上不能只靠模型

这是今天最重要的架构结论：

| 防线 | 抓什么 | 实测有效性 |
|---|---|---|
| `CheckUpper` 小写 vs 大写 | 数字读错（含 10 倍错） | ✅ **抓住了 30B-A3B 的 10 倍错** |
| `CheckTax` 价税合计−不含税≈税额 | 三元组内部不自洽 | ⚠️ **自洽的错抓不到** |
| 三单互核（发票/订单/付款金额一致） | **整体读错** | ⏳ 待实现（最强的一道） |
| 低置信度 → 人工队列 | 模型自己知道没把握 | ⏳ 待实现 |

**没有任何单一防线够用。** 三单互核之所以最强，是因为发票读成不含税、
或读成 10 倍，都会**与订单/付款截图对不上**，从而被拦下。
