# 发票识别的"精确通道"：文字层与二维码（实测）

> 2026-09-13。起因是问题「用 OCR 识别是否会更稳定？发票还有什么信息能用来更稳定提取，比如二维码？」

---

## 0. 结论先行

**问题不是"OCR 还是模型"，而是我们一直在用概率性的方式，去读本来可以确定性读出的东西。**

电子发票 PDF 里有两个**确定性通道**，都还没被用上：

| 通道 | 性质 | 实测结果 |
|---|---|---|
| **PDF 文字层** | 要么有、要么没有，无识别误差 | ✓ 本项目的发票**全部带文字层** |
| **票面二维码** | 解码是确定性的，且含关键字段 | ✓ 0.2 秒解出，与文字层一致 |

现在的做法是 `pdftoppm` 栅格化 → VLM 识别。**在已经存在精确答案的情况下，
引入了本不必要的识别误差和 5340 token/张 的成本。**

---

## 1. 实测一：文字层

对真实发票（本项目测试数据）跑 `pdftotext -layout`：

```
电子发票（普通发票）                     发票号码：<INVOICE_NO>
                                        开票日期：2026年05月02日
购买方 名称：<购买方名称>                  销售方 名称：<销售方名称>
      统一社会信用代码/纳税人识别号：<BUYER_TAX_ID>
                                        统一社会信用代码/纳税人识别号：<SELLER_TAX_ID>
项目名称 …  金 额  税率/征收率  税 额
*金属制品*强力弹簧…   4.55   1%   0.05
合     计            ¥4.55        ¥0.05
价税合计（大写）  肆圆陆角整        （小写）¥4.60
开票人：<开票人>
```

**全部关键字段精确可读**：发票号码、开票日期、购销双方名称与税号、
金额、税额、价税合计大小写。

对比同一张图走 VLM 的结果（`tok≈5340`）：
`价税合计460/税5/不含455 号<INVOICE_NO> 上校验=OK 税校验=OK`

两者结论一致，但**文字层是 0 token、0 延迟、0 误差**。

## 2. 实测二：二维码

票面左上角有二维码。解码（Go 的 `gozxing`，纯 Go 无系统依赖）：

```
01,32,,<INVOICE_NO>,<AMOUNT>,<YYYYMMDD>,,<RAND4>
```

按已知协议拆解：

| 段 | 值 | 含义 |
|---|---|---|
| 0 | `01` | 固定前缀 |
| 1 | `32` | 票种代码（`32` = 电子发票（普通发票）/数电票） |
| 2 | （空） | 发票代码 —— 数电票**没有**发票代码，故为空 |
| 3 | `<INVOICE_NO>` | **发票号码**（20 位） |
| 4 | `<价税合计>` | **金额** |
| 5 | `<YYYYMMDD>` | **开票日期** |
| 6 | （空） | 校验码 |
| 7 | `<随机码>` | 随机码 |

> ⚠️ 第 4 段的语义**随票种变化**：老式增值税票的资料称其为"开票金额"（可能是不含税），
> 而本张数电票的 `4.60` 与票面**价税合计**一致。**不能假设，必须与文字层/大写核对。**

### 关键实现细节

- 二维码在 **整页 300dpi 渲染图**上直接可解，**不需要**先裁切定位 —— 实测 2481×1654 的整页图，`gozxing` + `TRY_HARDER`，**0.19 秒**。
- 也就是说：**管道里现成的 `invoice-1-1.png` 就能用**，零额外依赖。
- 机器人上**没有** `zbarimg` 也没有 `libzbar`，所以选了纯 Go 的 `gozxing`（已在 `go.mod`）。

排查工具：`go run ./cmd/invoice-probe <发票.pdf>`，一次打印文字层 + 二维码全文。

## 3. 但纸质发票没有文字层

文字层只覆盖**电子发票**（含全电发票/数电票）——也就是 PDF 直接下载的那种。
队员**拍照上传的纸质发票**没有文字层，这时二维码仍是最可靠的通道（只要拍清楚）。

所以正确的**通道优先级**是：

```
① PDF 文字层      ← 电子发票。最全、最准、免费
② 票面二维码      ← 纸质发票拍照/扫描。关键字段精确，免费
③ 模型识别(VLM)   ← 截图、无二维码、拍模糊。概率性，最后手段
```

前两条都是**确定性**的，而且**互为交叉校验**：文字层的金额 vs 二维码的金额 vs
票面大写金额，三者一致才放行。这比现在"VLM 读完再用大写校验"强得多。

## 4. 成本影响

| | 现在 | 走文字层/二维码 |
|---|---|---|
| 发票单张 | ≈5340 tok | **0** |
| 订单截图 | ≈256 tok | ≈256（无精确通道，仍需模型） |
| 付款截图 | ≈256 tok | ≈256 |
| **单实例合计** | **≈5852 tok** | **≈512 tok** |

按 500 单/年、当前单价估算，年成本从 ≈¥29–88 降到 **≈¥3–8**。

---

## 5. 这对"稳定性"意味着什么

用户问「OCR 是否会更稳定」。诚实的回答是：

- **传统 OCR 比 VLM 更"可预测"**（不会凭空编造），但对中文发票的版面变化仍需模板，
  且对小字（税号、票号）的准确率并不天然更高。
- **真正的稳定性来自"换成确定性通道"**，而不是"换一种识别模型"。
  文字层和二维码不是"识别得更准"，而是**根本不需要识别**。
- 因此建议：**不要为了稳定而引入传统 OCR，而要把文字层/二维码接进来**，
  把模型降级为"兜底 + 补字段"的角色。
- 两条精确通道 + 大写校验 + 三单互核，构成**多重独立验证**：
  任何单点读错都会被另外两路发现。这是当前架构缺的那一环。

## 6. 落地情况

- [x] 文字层解析接进 `extract` → `internal/exact.ParseInvoiceText`
      （`pdftotext` 已在所有目标机上，含机器人；在删 PDF **之前**读）
- [x] 二维码解码接进 `extract` → `internal/exact.ParseQR` + `gozxing`
      （整页 300dpi 渲染图直接解，无需裁切；只对发票做）
- [x] 两通道交叉校验 → `exact.Merge` 返回**冲突列表**，不一致交人工
- [x] 命中精确通道则不调模型 → `Fields.Sufficient()`（发票号码 + 价税合计）
- [x] 顺带修 bug：税号的数字前缀被当成订单号（按子串排除，不是相等）
- [ ] 多张发票/订单/付款的**分组**（见 docs/30-review/29）

实测（真实测试实例）：

```
◎ 精确通道命中（pdftext+qr）—— 未调用模型，省 ≈5340 tok
✓ 发票 上校验=OK 税校验=OK
✓ 订单截图 与发票一致   ✓ 付款截图 与发票一致
```
