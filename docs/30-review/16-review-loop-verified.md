## 1. 本次踩到并修掉的三个真实问题

### 1.1 ★ `TextFieldConvFail`（1254060）—— 富文本读出来不能直接写回去

`archive` 第一次运行**两条全部失败**：

```
POST .../tables/<TABLE_OTHER_1>/records 失败: HTTP 200 code=1254060 msg=TextFieldConvFail
```

**原因**：飞书**读**文本字段返回的是**富文本片段数组**

```json
[{"text":"兴化市永超五金制品有限公司","type":"text"}]
```

而**写**文本字段需要**纯字符串**。直接把读到的数组写回去就报这个错。

**修法**：`writable()` 把片段数组拼回字符串；非纯文本数组（多选/人员）原样透传。

> **这个坑很典型**：读接口与写接口对同一个字段的表示**不对称**。
> 凡是"读出来直接写回去"的复制逻辑都会撞上。

### 1.2 归档失败时**没有**标记已归档（设计生效）

第一次归档失败后，源表的 `已归档` **一个都没勾上**，所以重跑是安全的。

这正是"**先复制、成功了再标记**"的次序带来的：标记意味着"确实归档过"，
而不是"尝试归档过"。如果反过来先标记，第一次失败就会造成**静默丢数据**。

### 1.3 付款截图的负数在落库时归一化

源表里付款截图此前会是 `-326`，对人看表不友好。现在落库时按"支出为正"归一化，
并在 `处理说明` 留一句 `原图为负号（-326），已按支出归一化`。

**原始值仍完整保留在 `data/extract/manifest.jsonl`**，不丢证据。

## 2. 实测中发现、但**未处理**的两件事

### 2.1 源表里有 5 条空记录

记录 ID 形如 `rec28aWcJsy...`，**所有字段为 null**，不是我们的服务写的
（我们的 15 条是 `recvv5p...`）。推测是该多维表格创建时自带的模板行。

**影响**：不影响幂等（`existingSHA256` 会忽略它们）与归档（筛选条件不匹配）。
**但它们会出现在你的表里，看着碍眼。**

处理需要 `base:record:delete` 权限。**要不要我删掉，你说一声**（删除是破坏性操作，我不擅自动手）。

### 2.2 订单截图的日期疑似读错

同一实例 `C5489DC9`：

| 来源 | 日期 |
|---|---|
| 发票 | 2026-04-20 |
| 付款截图 | 2026-04-18 |
| **订单截图** | **2024-04-18** ← 年份差 2 年 |

很可能是把 `2026` 读成了 `2024`。**目前已归档的那条就是这个实例**，说明：
**日期读错没有被任何校验拦住** —— 因为日期不参与金额互核。

**建议**：给日期加一条软校验（三单日期应在同一时间段内，如 ±30 天），
不一致时标 `NEEDS_MANUAL`。**不做硬拦截**（跨期报销是合理的）。
