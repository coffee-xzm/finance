## 1. 飞书 ID 体系：一个必须讲清的坑

你提供的 `open_id = <USER_OPEN_ID>...` **不能用**，报：

```
99992361 open_id cross app
```

**原因**：`open_id` 是**按应用隔离**的 —— 同一用户在不同应用有不同 open_id。
那个 open_id 属于另一个应用，我们的应用不认。

| ID 类型 | 范围 | 跨应用可用 | 发消息是否需要额外权限 |
|---|---|---|---|
| `open_id` | **单个应用内唯一** | ❌ | 否 |
| `union_id` | 同一开发者旗下 | ✅ | 否 |
| **`user_id`** | **租户内唯一** | ✅ | 需 `contact:user.employee_id:readonly` |

**采用方案**：`receive_id_type=user_id` + `user_id=<ADMIN_USER_ID>`（你补的那个权限生效了）。

> 提醒：将来若要从别处（审批后台、另一个应用）拿 ID，**一律优先用 `user_id`**。

## 2. 年份推断：根因不是模型读错

### 2.1 发现过程

三单日期复核报出 5 条全异常，跨度 **731~1100 天**：

| 实例 | 发票 | 订单 | 跨度 |
|---|---|---|---|
| C5489DC9 | 2026-04-20 | **2024**-04-18 | 732 天 |
| AA774403 | 2026-07-02 | **2023**-06-28 | 1100 天 |

规律极强：**月日都对，只有年份错**。于是我把订单截图调出来看：

> 凭据：**6月26日**下单交易快照

**票面上根本没有年份。** 淘宝的订单页只显示月日，模型被迫输出 `YYYY-MM-DD`，
只能**猜**，于是猜成了 2024/2023。

### 2.2 修法

**提示词**（`internal/ocr/siliconflow.go`）：

```
票面只写"6月26日" → date 填 "06-26"（只给月日，不给年份）
判断依据只有一个：年份是否真的印在图上。
不要根据"截图时间"或"看起来像哪一年"来推断。
（下游会用其它单据的年份补全，你多填一个猜的年份反而会污染数据。）
```

**代码**（`match.InferYear`）按你的要求接入**系统时间**，参考基准优先级：

| 优先级 | 基准 | 理由 |
|---|---|---|
| 1 | **同笔业务的其它单据日期**（发票优先） | 同属一笔交易，年份必然接近；不受"报销滞后多久"影响 |
| 2 | **系统时间** | 兜底：一次只有一张缺年份的单据、没有参照对象时 |

> ⚠ **为什么不是"一律用系统时间"**：报销常滞后。1 月处理去年 12 月的单子时，
> 用系统时间会把年份补成**新的一年**，整整差 12 个月。用发票日期不会错。
> 你的指令我按"系统时间作为兜底"实现；如果你确实要它作首选，说一声改一行。

### 2.3 一个写进逻辑的约束：**票据不可能来自未来**

测试时发现 `01-03` 在 9 月推断会被选成 `2027-01-03`（因为"最近"）—— **未来日期**。
已加入规则：**优先在"不晚于今天"的候选里选最近的那个**，全部落在未来时才退化为取最近。

```
06-26 + 系统时间 9/13 → 2026-06-26 ✓
01-03 + 系统时间 9/13 → 2026-01-03 ✓（不是 2027）
12-28 + 系统时间 9/13 → 2025-12-28 ✓（2026-12-28 在未来）
12-28 + 单据 2025-01-05 → 2024-12-28 ✓（单据优先于系统时间）
```

## 3. 遗留问题（如实记录）

### 3.1 订单截图的日期识别本身不稳定

同一实例 `4C37F5AF` 的订单日期，**三次运行读出三个值**：

```
2024-05-01  →  2026-05-26  →  2026-05-11
```

年份是推断出来的（固定），但**月日也在变**。说明订单页那个日期位置的识别不稳。

**影响**：日期不参与硬拦截，只在跨度 >30 天时告警，所以不会造成误拦；
但如果日后要按日期做账龄分析，这个字段不可靠。

**建议**：订单日期**只作参考展示**，不要用于任何计算或对账。

### 3.2 `sync -update` 会覆盖 `处理说明` 里的「已通知」标记

`-update` 用最新抽取结果覆盖字段（已排除 `人工审核`/`审核备注`/`已归档` 这三个人工字段），
但 `处理说明` 是机器字段，会被覆盖 —— 若该行此前通知过，标记会丢失。

**影响有限**：`处理状态` 同时被刷新，若仍为 `NEEDS_MANUAL` 会再通知一次（重复一条消息）。
**未修**：因为"该不该重复通知"取决于人的容忍度，且目前没有实例触发。

### 3.3 源表仍有 5 条空记录

`rec28aWcJsy...`，全 null 字段，**不是本服务写的**（推测是文档创建时的模板行）。
删它需要 `base:record:delete`。**未动**（破坏性操作需你确认）。
