# 测试多维表格 · 字段设计

> 回答用户 2026-09-13 提问：「多维表格那里的字段怎么填？」
> 生成器：`finance-router/cmd/bitable-schema`（`go run ./cmd/bitable-schema`）
> 依据：`04-approval-test-plan.md` §4.2、`06-direct-approval-initiation.md` §3、`02-architecture-v0.1.md` §4.1。

---

## 0. config.yml 里其实只有两个值要填

很多人以为"填字段"是往配置里塞一堆字段名 —— **不是**。配置里只放**定位信息**：

| 配置项 | 取法 |
|---|---|
| `bitable.app_token` | 多维表格 URL 形如 `https://xxx.feishu.cn/base/<app_token>?table=<table_id>`；**`/base/` 后面那段**，整份文档**共用** |
| `bitable.tables.submission` 等 4 项 | URL 里 **`?table=` 后面那段**（`tbl` 开头），**每张表一个** |

**字段名不需要写进配置**：飞书 Bitable「新增记录」接口的 `fields` 直接接受**字段名或字段 ID**。
字段名改由代码里的**常量**维护（`internal/bitable/schema.go`），比散落在 YAML 里更好重构。

> 注意 `app_token` 是**文档级**的：4 张表在同一个多维表格里，所以 `app_token` 只有一个。

## 1. 四张表的分工

| key | 表名 | 一行 = 什么 | 数据权属 |
|---|---|---|---|
| `submission` | 票据收集台账 | 一条审批实例 | 飞书权威（镜像展示） |
| `evidence` | 识别证据 | 一张图的抽取结果 | 本地权威（镜像展示） |
| `invoice_dedup` | 发票唯一性 | 一个发票指纹 | 本地权威（镜像展示） |
| `approval_result` | 审批结果 | 一次审批状态变更 | 飞书权威（事件回流） |

---

## 2. ★ 字段来源分级（比字段清单本身更重要）

每个字段在生成器里都标了 `SourceOfTruth`，它决定**谁可以写**：

| 标记 | 含义 | 写者 |
|---|---|---|
| `feishu` | 值来自审批表单 / 审批事件 | 服务从飞书读出后回写 |
| `local` | 值由本地服务计算（指纹、匹配状态、sha256…） | **只有服务能写** |
| `derived` | 展示用派生值（如 `金额_元`） | 服务回写，**不参与任何计算** |

**这条纪律的来由**：同一个字段只能有一个写者。一旦"人在表里手改 `匹配状态`"和"服务回写 `匹配状态`"同时存在，
就出现了两个真相，且**无法判断以谁为准**。所以：

> **建议把这些字段设为人工只读**（UI 上不加说明或后续用高级权限锁），避免有人在表里手改。

## 3. 字段清单（完整版由 `go run ./cmd/bitable-schema` 输出）

### 3.1 `submission` 票据收集台账（14 字段）

| # | 字段名 | 类型 | 类型码 | 取值/格式 | 来源 |
|---|---|---|---|---|---|
| 1 | 提交ID | 文本 | `1` | — | local |
| 2 | **审批实例号** | 文本 | `1` | ★ **真正的关联键** | feishu |
| 3 | 申请人 | 文本 | `1` | 先用文本；人员字段(11)需额外 scope | feishu |
| 4 | 申请人ID | 文本 | `1` | open_id | feishu |
| 5 | 组别 | 单选 | `3` | 机械组 / 电控组 / 视觉组 / 运营组 / 其他 | feishu |
| 6 | 业务类型 | 单选 | `3` | 采购 / 差旅 / 其他 | feishu |
| 7 | 资金来源 | 单选 | `3` | 流动资金 / 个人垫付 / 老师垫付 | feishu |
| 8 | **金额_分** | 数字 | `2` | 格式 `0` | local |
| 9 | 金额_元 | 数字 | `2` | 格式 `0.00`，货币 CNY | derived |
| 10 | 三张图 | 附件 | `17` | — | feishu |
| 11 | 匹配状态 | 单选 | `3` | MATCHED / SUSPECT / DEFECTIVE / NEEDS_MANUAL | local |
| 12 | 缺陷清单 | 文本 | `1` | — | local |
| 13 | 提交时间 | 日期 | `5` | `yyyy-MM-dd HH:mm` | feishu |
| 14 | 备注 | 文本 | `1` | — | feishu |

### 3.2 `evidence` 识别证据（16 字段）

`审批实例号`、`图类型`(单选 invoice/order/payment/unknown)、`金额_分`、`日期`(文本)、`对方名称`、
`发票代码`、`发票号码`、`校验码`、`销方税号`、`订单号`、**`图片SHA256`**、`置信度`、`provider`、`model`、`trace_id`、`原始响应`

### 3.3 `invoice_dedup` 发票唯一性（7 字段）

`指纹`、`指纹层级`(L1–L5)、`发票号码`、`首次审批实例号`、`占用状态`(CLEAR/SUSPECT/RELEASED)、`占用批次`、`创建时间`

> **记住**：飞书**没有唯一索引**，这里的"唯一性"只是**镜像展示**。
> 真正的约束在本地 SQLite 的**部分唯一索引**（`WHERE dedup_status='CLEAR'`）。

### 3.4 `approval_result` 审批结果（6 字段）

`审批实例号`、`状态`(PENDING/APPROVED/REJECTED/CANCELED/DELETED)、`操作人`、`操作时间`、
**`事件ID`**、`备注`

> `事件ID` 是**幂等键**：飞书是"至少一次"投递，同一事件会重复到达，靠它去重。

## 4. 三条硬约束（填错会直接报错或数据错乱）

1. **只读字段绝不能作为写入目标**：
   公式(`20`)、查找引用(`19`)、自动编号(`1005`)、创建时间(`1001`)、最后更新时间(`1002`)、
   创建人(`1003`)、修改人(`1004`)。
   → 所有计算结果必须由本地服务算完写进**普通字段**。新增字段也不支持 `19`。
2. **金额一律以「分」存整数**（`金额_分`），禁用小数 —— 避免浮点误差。
   `金额_元` 只是展示，**不参与任何计算**。
3. **同一数据表禁止并发写**（`1254291 Write conflict`）→ 服务侧按 `table_id` 串行写入。

---

## 5. 其他要记住的限制

| 项 | 限制 | 影响 |
|---|---|---|
| 单表行数 | 免费版约 **2,000 行** | 流水类高频数据按年/月分表 |
| 批量写 | 新增/更新单次 **≤1,000 条**，删除 ≤500，且**全成全败** | 大批量导入要分批 + 可重入 |
| 附件 | 单文件 ≤**20 MB**；`file_token` **不可跨表复用** | 跨表引用附件必须重新上传 |
| 仪表盘 | **无法用 API 创建**（只有 list + copy） | 看板手工建一次当模板，之后 `copy` 克隆 |
| 高级权限 | **免费版/基础标准版不支持行列权限** | 个人视图由本地服务做数据裁剪 |
| 协作者 | 应用需被加为文档协作者 | 否则 API 写入 **403** |

## 6. 建议的建表顺序

1. 在**个人文件夹**新建多维表格 → 改名便于识别（如 `财务测试·勿删`）；
2. 按 §3 建 4 张表与字段（照抄 `go run ./cmd/bitable-schema` 的输出）；
3. **把应用加为该文档协作者**；
4. **先别开高级权限**（隔离权限变量）；
5. 从 URL 取 `app_token` 与 4 个 `table_id` 填进 `config.yml`；
6. 确认无误后再跑 recon / 后续链路。

> 表结构是**为验证闭环设计**的，不是最终生产设计。字段名、选项都可以按实际需要调整，
> 调整时同步改 `internal/bitable/schema.go` 并重跑生成器即可。
