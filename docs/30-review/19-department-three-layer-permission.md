# 发起人部门：三层权限与安全兜底

> 用户 2026-09-13 选择"方案②：补权限解析部门名"。本文记录这条路踩到的三层权限，
> 以及一个**必须避开的错误兜底**。

---

## 0. 结论

`发起人部门` **已能填上**（实测 5 条全部 = 机械组）。但走得不是预想的路：

| 层 | 状态 | 说明 |
|---|---|---|
| ① **scope** | ✅ 已开通 | `contact:contact.base:readonly` |
| ② **通讯录数据范围** | ✅ 已开通（你补的） | 之前报 `40004 no dept authority error` |
| ③ **字段权限** | ❌ **仍缺** | `name` 是**字段级**权限，响应里不返回名称 |
| **兜底** | ✅ 已实现 | 用**部门 ID 对照表**精确匹配（见 §2） |

**所以 `发起人部门` 现在能填，但不是靠通讯录接口的 name，而是靠兜底。**

## 1. 三层权限：scope ≠ 数据范围 ≠ 字段权限

这是本次最值得记的一条。三个错误码指向三个不同的层：

| 错误码 | 含义 | 修法 |
|---|---|---|
| `99991672` | **scope 没开通**（错误信息会列出所需 scope） | 开发者后台 → 权限管理 → 开通 |
| `40004 no dept authority error` | scope 有了，但**通讯录数据范围**不含该部门 | 权限管理 → **数据权限范围** → 设为全部成员 |
| 响应里**没有 `name` 字段** | 接口能调、部门能看，但 `name` 是**字段级权限** | 补 **`contact:department.base:readonly`** |

> **同构的坑已经出现第三次了**：
> - wiki 文档权限（scope 有、文档不可写 → `91403`）
> - 多维表格文档权限
> - **通讯录三层权限**
>
> 共同规律：**"能调接口" ≠ "能看数据" ≠ "能看字段"。** 我把这些错误码都写进了 `cmd/doctor` 的诊断分支。

想彻底走通第③层，补这个权限即可：

```
https://open.feishu.cn/app/<APP_ID>/auth?q=contact:department.base:readonly&op_from=openapi&token_type=tenant
```

## 2. ★ 一个必须避开的错误兜底（我第一版写错了）

### 2.1 错误做法（已废弃）

第一版我写的兜底是：

> 通讯录拿不到 name → 就用**本单表单里的「物资所属部门」**当申请人的部门。

**实测"能跑通"** —— 5 条全填出"机械组"。**但它是错的**：

| 字段 | 语义 |
|---|---|
| 表单里的 `物资所属部门` | **物资**归属的部门 |
| 实例里的 `department_id` | **申请人**自己的部门 |

**两者可以不同**：机械组的人替电控组买东西，物资所属部门 = 电控组，而申请人的部门 = 机械组。
用前者冒充后者会**静默填错数据**，而且因为"看起来有值"，没人会发现。

> 这次 5 条恰好都是同一部门（申请人就是买自己组的东西），所以错误被掩盖了。
> **一个"在样本上全对"的兜底，可能只是样本碰巧。**

### 2.2 正确做法（现行）

```
① 调通讯录拿 name ──成功──► 用它
        │失败
        ▼
② 拿响应里的 open_department_id（od-…）
   去【全局部门对照表】精确查名 ──命中──► 用它
        │未命中
        ▼
③ 留空 + 告警（不猜、不借用其它字段）
```

**对照表怎么来**：每次解析表单时，把 `department` 控件值里的
`{"name":"机械组","open_id":"<DEPT_ID>…"}` 累积进内存（`learnDepartments`）。
整个团队只有十来个部门，跑几条单据就能补全。

**关键点：按 `od-` ID 精确匹配**，而不是"取本单第一个部门"。
