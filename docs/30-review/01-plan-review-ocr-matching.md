# 方案评审：Go+SQLite 本地服务 · 发票 OCR 与三单匹配 · 飞书审批复用

> 评审对象：用户于本轮提出的落地方案（原文摘要）
> 1. Linux 部署，主体用 **Go + SQLite**；
> 2. 用 `https://github.com/guanshuicheng/invoice` **识别发票并提取信息存储 JSON**；
> 3. 三单匹配"先用普通 OCR + 文本处理算法，**看信息 JSON 的金额是否匹配**"；
> 4. **不匹配就退回，不把信息加入 JSON**；加入后**同步到多维表格**（参考需求矩阵截图）；
> 5. 提问：**飞书前端能复用飞书的审批吗？**
>
> 评审日期：2026-09-12。前置依据：`docs/20-synthesis/02-architecture-v0.1.md`、`docs/00-brief/02-feishu-capability-facts.md`。
> 本轮新增的**一手核实**见 §6（已实测，非转述）。

## 0. 总评：架构骨架是对的，两处要改，一处要补

| 判断 | 内容 |
|---|---|
| ✅ **可以直接采纳** | Go + SQLite + 单二进制；OCR 做成 HTTP 服务由 Go 只当客户端；识别结果落 JSON；同步到多维表格；飞书做入口与交付面 |
| ✅ **方向正确** | 把"三单匹配"降级为**金额比对 + 文本处理**（不做企业级 PO/GRN 行项目匹配）——对你们的场景是**正确的简化** |
| ⚠️ **必须改①** | **不要把识别结果只喂给发票**。`guanshuicheng/invoice` 只认**增值税发票**，你还有**订单截图 + 付款记录**两类图，它一张都认不了 → 三单匹配会因为"另外两单没有结构化数据"而根本不成立 |
| ⚠️ **必须改②** | "**不匹配就退回、不入库**"这个设计要反转。它把 OCR/相似度的**误判**直接变成队员的**提交失败**，而你已经确认欠票主因是"懒得填"——退回一次就足以劝退。应改为**入库+标记待确认，硬门禁后置到审批/付款** |
| ➕ **要补③** | **幂等 + 单表串行写 + outbox**。飞书事件是**至少一次**投递，Bitable **同表禁止并发写**，这两条会把"识别完就同步"的天真实现打成重复记录/写冲突 |
| ✅ **飞书审批能复用** | 见 §4：**审批界面 100% 复用，但审批表单里显示的内容由你的服务在"创建实例"时灌入**；且官方**明确不推荐**用 API 建审批定义 |

**一句话**：你的方案缺的从来不是"怎么算"，而是"**非发票那两张图怎么变成结构化数据**"。补上这一环，其余按 §5 调整即可进入 P1。

**结论**：可以作为"**发票专用识别器的一个可选实现**"存在，但**不能**当作方案的中枢。理由不是它不准（它的发票字段识别口碑尚可），而是：

1. **它只解决 1/3 的问题**（三类图里只认发票），而你的瓶颈在另外 2/3；
2. 它把你原本"Go 静态单二进制"的部署承诺，变成一个**必须常驻的、锁死 Python 3.6 + TF1.13 的 Python 服务**——这与你要的"便捷可拓展、迭代快"直接冲突；
3. 一个 2023 年后无实质更新的仓库，遇到"我们学校这种发票版式识别不出来"时，**你没有能力改**（改 YOLOv3+CRNN 的训练数据 = 另一个项目）。

**但它有一个真正值得保留的价值**：它证明了"发票识别要做成 **HTTP 微服务**、由 Go 当客户端"这个**架构决策是对的**（架构稿 §4.3 已写：Go 里不做内嵌 OCR，换引擎 = 改一行配置）。**保留这个插槽，换掉插槽里的实现**。

## 2. 三单匹配的真实难度：你选对了简化方向，但卡点在前面一步

### 2.1 先给结论：你的简化是对的，而且比你以为的更对

"三单匹配"这个词来自企业采购（**PO 采购订单 / GRN 收货单 / Invoice 发票**），它的难点是**行项目级**的：数量对不对、单价对不对、部分收货、运费与税额摊分、退货冲销、跨期。**这些你们一个都不需要**：

| 企业级三单匹配要做的 | 你们实际需要的 |
|---|---|
| 明细行 × 数量 × 单价的逐行核对 | ❌ 不需要 |
| 收货单与订单的数量差 | ❌ 不需要（没有收货环节） |
| 部分开票 / 分次付款 | ✅ **需要**（这是唯一真难点，见 §2.4） |
| 税率、税额与不含税金额拆分 | ❌ 不需要（学校只看价税合计） |
| 供应商主数据一致性 | ⚠️ 简化版：销方名称 vs 收款方名称的**字符串相似度** |

所以**"看金额是否匹配"作为第一层判据是正确的**——金额是唯一一个**双方都天然带、且可精确比较**的字段。问题在于：**金额得先从图里被读出来**。

### 2.2 三张图的信息结构完全不同，这才是真正的难点

| 图 | 载体形态 | 能得到什么 | 难度 |
|---|---|---|---|
| **发票** | **强版式文档**（有固定票面、票号、价税合计栏） | 全靠 OCR + 版式定位：发票号、开票日期、销方名称、价税合计 | **中**（有成熟方案，含飞书原生 API） |
| **订单截图** | **手机 App 的 UI 截图**（淘宝/京东/拼多多订单详情页） | 订单号、商品名、实付金额、下单时间、店铺名——**全是自然语言排版，没有版式规律** | **高** |
| **付款记录** | **微信/支付宝账单截图** | 转账金额、时间、收款方——**可能被截断、可能一笔含多单** | **高** |

**"普通 OCR + 文本处理算法"能处理前者的原因是发票有版式；对后两者，普通 OCR 只会吐出无序文本行**——你要自己写规则去判断"哪一行是金额、哪一个数字是订单号"，而这些截图的版式**会随 App 版本、机型、深色模式、字体大小持续变化**。这是"文本处理算法"最容易失控的地方：规则会一直加，且是**脆的**。

### 2.3 因此：识别层必须是"按图类型抽取结构化字段"，不是"OCR + 规则"

**推荐做法**（这是本评审最重要的一条建议）：把三张图统一走**视觉模型抽字段**，输出同一份 JSON：

```jsonc
// 统一抽取结果（每张图一条）
{
  "kind": "invoice | order | payment",        // 由 prompt 让模型判定
  "confidence": 0.0-1.0,
  "amount_cent": 32800,                        // 三张图都有：可精确比较 ← 匹配的主锚点
  "datetime": "2026-08-04",
  "counterparty": "深圳市XX科技有限公司",       // 发票销方 / 订单店铺 / 转账收款方
  "order_no": "...", "invoice_no": "...", "invoice_code": "...", "check_code": "...",
  "items": [{"name":"轴承","qty":2}],          // 可用可不用
  "evidence_sha256": "..."                     // 原图指纹
}
```

理由（成本/可靠性两侧都成立）：

- **一张 prompt 就能覆盖三类图**，而自建 OCR（无论 chineseocr 还是 PaddleOCR）**只能覆盖发票**，订单/付款截图必须另找；
- 一次调用同时完成**分类 + 抽取**，省掉"先判断这是哪种图"的独立模型；
- **量很小**：按年 300–600 单、每单 3 张图 = 年 900–1,800 张，**按张计费在多模态模型上大约是每年几元到几十元**，比维护 TF1.13 的人力便宜几个数量级；
- 与架构稿 §4.3 的"三级可换 OCR"**完全兼容**：这正好是其中的第 ② 级（通用视觉模型），而 `guanshuicheng/invoice` 降为**发票专用兜底（第 ③ 级）**，甚至可以先不接。

> **飞书原生那条路要算一笔账**：飞书 `document_ai/v1/vat_invoice/recognize` 只能认增值税发票（另有火车票/出租车票/车辆票），**认不了订单与转账截图**。而且智能文档解析配额是**按次**计（基础免费版认证后 **100 次/月**），一单 3 张图就接近这个量级 → **飞书原生 OCR 只适合作为发票单图的一个来源，不能承担三单匹配的全部抽取量**。这一点在 `02-feishu-capability-facts.md` A9 已核实。

### 2.4 匹配层：建议的 4 层判据（规则即可，不需要机器学习）

按"可解释 + 可回放"排序（与架构稿 §4.2 的 D 派判据一致，此处给出可实现的算法）：

| 层 | 判据 | 实现 | 处置 |
|---|---|---|---|
| **L1 唯一性（硬）** | 发票指纹：`sha256(invoice_code\|invoice_no)`，无票号时降级 `sha256(销方税号\|开票日期\|价税合计)` | SQLite **部分唯一索引** `WHERE dedup_status='CLEAR'` | **这一条是硬阻断**，也是整个本地服务存在的第一理由 |
| **L2 金额（硬锚点）** | 发票价税合计 = 订单实付金额 = 转账金额，允许**分位容差**（如 ±1 分）+ 明确允许的差额原因（运费/优惠） | `INTEGER` 存"分"，精确比较 | 不等 → 挂缺陷，**不阻断提交**，进审批卡片 |
| **L3 时间（软）** | 付款日 ≤ 订单日 + N 天（建议 N=3），且全部发生在报销周期内 | 日期区间比较 | 越界 → 缺陷列表一条 |
| **L4 收款方（软，字符串）** | 发票销方 vs 订单店铺 vs 转账收款方 | **编辑距离 / Jaro-Winkler / 拼音首字母**；先做**去后缀**（"有限公司""深圳分公司"）+ 全半角/繁简归一 | 相似度低 → 缺陷列表一条（**不要判定为失败**，因为简称/个人收款很常见） |

**"一笔付款对多张订单"的处理——别用算法，用枚举**：队员一次提交的候选订单通常就 3–5 笔。金额锚定后，**枚举子集求和**（`2^5=32` 种）找**精确命中**组合即可，完全可解释、可回放，远比让模型"理解"可靠。这也**顺便解决了能力扩展问题**：同一算法可以自然处理"一次转账付了 3 个订单"和"一个订单分 2 次付款"。

**「资金池」这一维度要单独说清**：个人垫付时，**转账的收款方是商户，不是队员本人**——所以"付款记录里的收款方"与"发票销方"同源，队员身份来自**提交人**而不是转账记录。这一点如果不先想清楚，L4 会被设计成错误的比对。

## 3. 第二处必改："不匹配就退回"要反转为"入库 + 标记"

你的原话是：*"如果不匹配的就退回，不把信息加入 json 中，加入到 json 后将信息同步到多维表格"*。这条**必须改**，理由三条，第 1 条是决定性的：

1. **与"懒得填"的因果冲突**。OCR 与字符串相似度**必然有误判**（尤其是转账截图、店铺简称、个人收款）。一旦"误判 = 提交被退回"，队员会经历"我明明交对了，系统说我错，还要我再填一遍"——**这正是当前流程让人不想交票的机制本身**。产品上不可接受。
2. **被退回的记录等于不存在**。财务看不到"某人被系统拒了 3 次"，无法干预；出了问题（发票后来丢了、钱付了但没报销）**没有任何痕迹**。这与架构稿 §3.1"审计与痕迹由本地权威"直接矛盾。
3. **硬门禁放错了位置**。真正要拦的时点是**付款/报销**，不是**提交**（架构稿裁定 2 已经把这个争论裁定过了：提交时刻只强制 3 张图，三单匹配在审批/付款时刻做硬门禁）。

**建议的三段式（与架构稿 §4.2 表一致，此处落到字段）**：

| 阶段 | 行为 | 状态 |
|---|---|---|
| **提交** | 三张图 → 全部识别 → 全部入库（**无论匹配结果**） | `submission.state = RECEIVED`；`evidence.match_status = MATCHED / SUSPECT / DEFECTIVE` |
| **异步** | 跑 L1–L4，产出一张**缺陷清单**（缺哪一单、哪个字段对不上、差多少） | 缺陷清单**挂在审批卡片上给财务看**，不给队员看"你错了" |
| **审批/付款** | 财务看缺陷清单 → 通过则付款；**L1 唯一性命中直接拒绝** | 这才是硬门禁；驳回走飞书审批的拒绝理由 |

> **对队员的 UX 只保留一件事**：OCR 识别失败时，**绝不要求重填整表**，只私聊问 2 个问题（金额多少 / 哪家商户），并把该条标记 `NEEDS_MANUAL`。这是架构稿 §4.3 已定的降级规则，与本节的改动是同一套逻辑。

## 4. 你的问题：飞书前端能复用飞书的审批吗？

**能复用，而且这是正确选择；但有三条边界必须先讲清楚。**（以下均为**本轮实测官方文档原文**，见 §6）

### 4.1 能复用什么

| 能力 | 能否复用 | 依据 |
|---|---|---|
| **审批界面本身**（表单、审批人流转、同意/拒绝、抄送、移动端） | ✅ **完全复用**，界面在飞书里，不自研 | 审批是飞书原生强项 |
| **审批卡片上显示你的匹配结果**（发票金额/订单金额/转账金额/缺陷列表） | ✅ **能**，机制是：**"创建审批实例"时把值灌进表单控件**。请求体 `form` 是 JSON 压缩字符串，按 `id/type/value` 逐控件传值 | `POST /approval/v4/instances` 的 `form` 参数 |
| **分档审批（≤100 免审 / 100–500 队长 / …）** | ✅ **能，但要在飞书后台配**：分支条件支持"部分控件：**单选、多选、数字、金额、计算公式、日期区间、明细汇总**" | 审批 FAQ 原文 |
| **审批结果回流到本地服务** | ✅ 订阅 `approval_instance` 事件（长连接，**无需公网 IP**），`event_id` 幂等 | 架构稿 §4.8 已核实 |
| 审批里显示**表格/图表/明细列表** | ❌ 不行 | 审批表单只有控件，没有仪表盘 |
| 审批表单里**富文本可点击链接** | ❌ **官方明确"暂无"**（FAQ 原文） | 所以"点一下跳到已预填表单"**不能放在审批表单里**，要放在**机器人卡片**里（卡片支持 deep link） |

### 4.2 三条必须知道的边界（官方原文，直接影响你的设计）

1. **官方明确不推荐用 API 创建审批定义**。`创建审批定义` 接口"使用限制"原文：
   > 「通过该 API 创建的审批定义，**无法从审批管理后台或以 API 方式停用、删除**，请谨慎调用。**不推荐企业自建应用使用该 API 创建审批定义**，如有需要，尽量联系企业管理员**在审批管理后台创建定义**。」
   → **落地建议：审批定义在飞书后台手工建一次（含分档条件分支），API 只负责"创建实例 + 订阅事件 + 读实例详情"。** 这既避开"API 定义不能删"，也顺手拿到条件分支能力。
   → 顺带解决 `02-feishu-capability-facts.md` 未核实问题 #1（"审批定义能否 API 修改"）：**FAQ 原文仍写"不支持，只能在后台修改"**，而接口正文写"传 `approval_code` 即全量覆盖更新"——**官方文档至今自相矛盾**，因此**不要依赖 API 改定义**，这条从"待实测"升级为"设计上绕开"。
2. **创建实例时不校验必填**。FAQ 原文：*"必填的控件即使不传值也不会报错，仍可以成功调用创建审批实例接口"*。→ **"必填"这道校验不能指望审批替你兜**，谁创建实例谁负责校验（也就是你的 Go 服务）。
3. **存在"创建审批实例 API 不支持的控件类型"**。FAQ 原文：若定义含这类控件，创建实例会报错，*"此时建议你通过飞书客户端的审批中心发起审批"*。→ **设计前必须做一次沙箱验证**：确认你打算用的控件（**尤其是附件/图片控件**、明细、金额）都在支持列表内。**这是本方案里最容易踩空的一个点**——因为你想让队员在审批里看到三张图。

### 4.3 那么"三张图怎么进审批"？

三条路，按推荐度：

1. **图片留在多维表格，审批只带 `submission_id` + 金额 + 缺陷清单**（推荐）。理由：Bitable 附件字段支持 API 上传与绑定（架构稿 §4.8 已核实：`upload_all` 拿 `file_token` → 写入记录，单文件 ≤20 MB，**`file_token` 不可跨表复用**）。审批人若要看图，可从机器人卡片里的 deep link 跳表查看。**避开"附件控件在创建实例 API 是否支持"这个未验证点。**
2. **审批表单里放附件控件**——需要先验证 API 能否传附件值；能传则体验最好，但多一个未验证依赖。
3. 审批里只写结论（"3 单匹配通过，金额 328.00"），图完全不进审批。

### 4.4 结论一句话

> **飞书审批可以且应该复用**：**表单与流转在后台手工建**（拿到条件分支、可维护、可删除），**实例由你的 Go 服务创建并把匹配结论灌进表单值**，**审批结果用长连接事件回流**。你要接受的两个"不能"：审批里**不能有图表/表格**，审批表单里**不能放可点击链接**（链接放机器人卡片）。

## 5. 修订后的落库与同步流程（把 ①②③ 三处改动合起来）

```
队员（飞书表单，只强制 3 张图，0 必填）
   │  提交
   ▼
M1 intake-adapter ──► submission(RECEIVED)  ← 先落库，任何情况都不丢
   │
   ├─► 异步：M2 evidence
   │      ① 三张图 → 统一抽取（视觉模型 / 飞书票夹 / chineseocr 三级可换）
   │         → 每张图一条 JSON（amount / datetime / counterparty / 票号 / sha256）
   │      ② L1 发票唯一性（DB 部分唯一索引）← 唯一的硬阻断
   │      ③ L2 金额（分位容差）· L3 时间 · L4 收款方相似度 · 子集枚举解多单
   │         → 产出【缺陷清单】，写 evidence.match_status
   │      ※ 匹配失败【不退回、不丢数据】，只标记
   │
   ├─► M3 ledger（分录，本地权威）
   ├─► M5 notify（D+3/D+7/D+14/D+30 催办，按人走本地引擎）
   │
   ▼
M6 sync-outbox  ← 【补③】幂等 event_id + 单表串行队列 + 指数退避 + 死信
   │  （飞书事件至少一次投递；Bitable 同表禁止并发写 1254291）
   ├─► 多维表格镜像表（附件：upload_all → file_token → 绑记录，不可跨表复用）
   └─► POST /approval/v4/instances（把匹配结论灌进审批表单控件）
   │
   ▼
飞书审批（后台手工建定义 + 条件分支）── approval_instance 事件 ──► 长连接回流 ──► M3/M4
```

**四个必须写死的工程约束**（缺一个都会在真实运行中出问题）：

1. **幂等**：飞书事件"至少一次"投递 → `event_id`/`uuid` 去重；本地写入用 `INSERT ... ON CONFLICT` 并**判断是否真的新建**（架构稿 §4.4 提到 B 派实测过"幂等重放导致额度扣两次"的真实缺陷）。
2. **单表串行写**：Bitable 同表禁止并发（`1254291`）→ outbox 按 `table_id` 串行消费。
3. **只读字段绝不作为写入目标**：公式(20)/查找引用(19)/自动编号(1005)/创建时间(1001)/创建人(1003) 等。**所有计算结果必须由 Go 算完写进普通字段**。
4. **原图只存指纹**：本地 `sha256` 即可完成查重，原图唯一副本在飞书附件（架构稿裁定 12）。若走视觉模型，图会离开你的机器——**这一点需要你确认是否接受**（见 §7 Q1）。

## 8. 建议的下一步（最小验证，1 天内可完成）

1. **沙箱验 3 件事**（对应 §4.2 的三个边界）：
   a. 用 API 创建实例时，**附件控件能否传值**（这决定"图能不能进审批"）；
