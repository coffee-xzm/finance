# 34 · 决策记录：附件导出走「侧边栏插件 · 浏览器本地打包」

## 1. 决策

| 项 | 决定 | 谁定的 |
|---|---|---|
| 形态 | 服务端下载 + 清单输入为主线；**插件走"浏览器本地打包"（③B-1）** | 用户（2026-09-19） |
| 选择性口径 | **按勾选的记录清单**（不是按视图全量） | 用户（2026-09-19） |
| 插件托管 | **Replit**（官方侧边栏插件推荐方式） | 用户（2026-09-19） |

三条决定的关系：**勾选**这件事由插件在飞书里完成（这是插件唯一不可替代的价值），
**打包**也在浏览器里完成（因为服务端够不着，见 §2）。清单口径则决定了插件的最小功能面：
列出当前视图的记录 → 勾 → 下载。

## 2. 为什么不做"插件调服务端"

三条官方事实（详见 `docs/30-review/32` §4.1，均为官方原文）：

1. 插件页面托管在 `https://*.feishupkg.com`，宿主是 `https://*.feishu.com` —— 跨域 iframe。
2. 插件发网络请求要求：**必须 HTTPS、会校验证书、服务端必须开 CORS 且
   `Access-Control-Allow-Origin` 不能包含 `*`**；另有 60s 超时、**并发 5**、不支持 WebSocket。
3. 局域网里的服务（NAS、机器人 `192.168.1.3`）**不可能**满足"公网 HTTPS + 有效证书"。

结论：**插件直连我们的服务在当前基础设施下做不到**；要做得先给服务端一个公网 HTTPS 域名。
在拿到域名之前，插件只能"自己下载、自己打包"。

> 注：官方文档在"是否还要配服务器域名白名单"上**自相矛盾**
> （《网络》说无需配置，插件开发指南说应配置）。但无论哪种口径，
> **HTTPS + CORS 这两条都是明确写着的**，局域网地址依然无解。

## 3. 为什么先做插件（而不是先做服务端导出）

| 理由 | 说明 |
|---|---|
| **不依赖 P0 门禁** | 服务端路线第一步要验证"应用有没有素材下载权限、高级权限表要不要 `extra`"（`docs/30-review/32` §5.1）。插件用的是**用户身份**，走宿主通道，绕开了这道门禁。 |
| **立刻可用** | 拿到 HTTPS 地址就能用，不需要 NAS 挂载、不需要机器人发版。 |
| **反哺服务端** | 命名/分组规则被抽成两侧共用的**冻结向量**，服务端实现（Go）已经写好并过同一份向量——将来做服务端导出不用重写规则。 |

## 4. 落地结果（2026-09-19）

### 4.1 已可用

```
bitable-plugin/                  ← 侧边栏插件（React + Vite + @lark-base-open/js-sdk）
  src/core/naming.ts             ← 记录 → 文件名/目录（纯函数，与服务端共用契约）
  src/core/download.ts           ← 并发下载（tt.request 优先，并发 3；宿主上限 5）
  src/core/zip.ts                ← fflate 浏览器内打包
  src/core/manifest.ts           ← manifest.csv（UTF-8+BOM）+ README.txt
  src/api/bitable.ts             ← 唯一 import SDK 的地方
  src/App.tsx                    ← 界面：选表/视图 → 映射附件列 → 命名规则 → 勾选 → 导出
  testdata/naming-cases.json     ← ★ 冻结行为契约（11 条用例）
  scripts/check-vectors.sh       ← 一条命令跑两侧契约校验
finance-router/internal/naming/  ← Go 侧同名实现 + 过同一份向量的测试
```

### 4.2 可验证的证据（实测）

| 项 | 结果 |
|---|---|
| 插件纯逻辑测试 | **21 项全绿**（`npm test`） |
| 插件生产构建 | 成功，`dist/` 约 1.2 MB（gzip ≈ 373 KB，其中 SDK 占 313 KB） |
| **两侧命名一致性** | **同时通过**同一份 11 条冻结向量（`bash scripts/check-vectors.sh`） |
| Go 侧 | `go test ./internal/naming/` → ok |

> "两侧一致性"是这轮最有价值的自动化：**命名是插件与服务端唯一必须逐字相同的逻辑**，
> 现在任何一侧改了行为而不同步向量，测试立刻红。

### 4.4 明确的取舍（写下来免得日后当成 bug）

- **没有 NAS、没有导出审计**：文件落在操作者电脑。需求矩阵里的
  「导出发票并保存导出记录（操作人/时间/事项）」**尚未满足**，那是服务端路线的事。
- **操作人身份对不上**：`Bridge.getUserId` 与开放平台 `userId` 不是一套（官方 FAQ），
  所以 manifest 里暂时不写操作人（写了也是两套体系的对照表都查不到）。
- **只有"行"粒度**：表里是「一张发票一行」，所以勾选是按行（= 按发票），不是按审批单。
