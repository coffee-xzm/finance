# 提交入口 = 队员直接发起审批：架构修正

> 用户 2026-09-12 确认：**「队员是直接点审批发起的」**。
> 这一条**否掉了** `03-approval-routing.md` §1「方式 A：服务创建审批实例」的前提，
> 并使本地服务的权限面收窄到**纯只读**。
>
> 关联：`03-approval-routing.md`、`05-readonly-parallel-integration.md`、`04-approval-test-plan.md`。

---

## 0. 修正了什么

| | 原设计（已作废） | 新设计 |
|---|---|---|
| 谁创建审批实例 | **服务**调 `POST /approval/v4/instances`，把匹配结论灌进表单 | **队员本人**在飞书点审批发起 |
| 服务对审批的权限 | 需要 `approval:instance`（创建）+ `approval:approval`（读） | **只需 `approval:approval:readonly`（纯读）** |
| 匹配结论怎么给审批人 | 创建实例时灌进表单控件，**审批人打开就能看到** | **机器人卡片事后推送**给审批人 |
| 校验时机 | **事前**：余额不足/匹配失败 → 不创建实例 | **事中**：实例已存在 → 只能标记异常并通知，**不能拦截** |
| 关联键 | 服务灌入的只读控件 `submission_id` | 需要**重新设计**（见 §3） |

### 0.1 这是好事：本地服务变成"纯只读消费者"

新形态下，本地服务**不写审批、不建实例、不改状态、不写旧表**。
唯一的写入是**新的个人文件夹镜像表**（展示用）。风险面从"可能误伤现有审批"降到"只读，不可能误伤"。

### 0.2 但要接受两个代价

1. **结论不再"一眼可见"**：审批人打开表单看到的是队员填的原始内容，
   匹配结论要靠机器人卡片补发（卡片有 30 KB 上限，够放缺陷清单）。
2. **校验从"事前拦截"退化为"事中提示"**：预算不足、发票重复，都**无法阻止审批发起**，
   只能在事件到达后标记异常、通知财务，由人在审批时决定。
   → 这与架构稿裁定 2「校验放在能拦住钱的位置」**仍然一致**：拦住钱的位置是**财务付款**，不是发起。

## 1. 修正后的端到端链路

```
队员在飞书直接发起审批（新定义，填表 + 传三张图）
   │  提交即产生实例 —— 服务没有介入机会
   ▼
approval_instance 事件 ──► 长连接
   │  ① 按 approval_code 硬过滤（见 §2）
   │  ② event_id 幂等
   ▼
GET /open-apis/approval/v4/instances/:instance_code
   │  ← 事件体只有 instance_code/status 等元数据，**表单值必须再查一次**
   │  ← 返回体 form（JSON 字符串，控件 id/type/value）+ status
   ▼
从附件控件取三张图 → 下载（注意：开高级权限时下载附件需 extra 鉴权）
   │  → 算 sha256 → SiliconFlow Qwen3-VL 抽取 → L1–L4 匹配
   │  → 产出 match_status + 缺陷清单
   ├─► M3 ledger 落账（本地权威）
   ├─► M4 budget 记录（不预占，改为"已发生"口径）
   ├─► M6 outbox ──► 写【新的个人文件夹镜像表】（绝不写旧表）
   └─► M5 notify ──► 机器人卡片把匹配结论/缺陷清单推给审批人
   │
   ▼ 审批人通过
approval_instance 事件（status=APPROVED）
   └─► 状态机 → 回填最终状态；若驳回则释放相关占用
```

### 1.1 一个必须验证的假设

**事件体是否携带表单值？** 若**不携带**（我的判断：审批事件通常只带 `instance_code`/`approval_code`/`status`），
则**每条事件都必须再调一次 `instance/get`** —— 这意味着：

- 事件 → **一次 GET** 的额外延迟（可接受，异步 worker 处理）；
- `instance/get` 的调用量 = 事件量（日均个位数，远低于限流）；
- **必须做去重**：`PENDING` 与 `APPROVED` 会各来一条事件 → 避免重复调取与重复落账。

> **列入待实测 T4**：实际事件体里有哪些字段（是否含 `form`）。
> 这条直接决定"要不要额外 GET"以及"幂等键怎么设计"。

## 2. 为什么必须按 `approval_code` 硬过滤（用户提问，展开说明）

### 2.1 物理图景：一条管道，一个回调函数

```
飞书（很多个审批定义）
   ├── 定义A（老的，队员在用）
   ├── 定义B（采购）
   └── 定义C（本项目新做的）
        │
        │  事件都从【同一个出口】推给你：
        │  长连接只有一条，代码里只有一个回调函数
        ▼
   你的服务 onApprovalInstance(ev)
```

**回调是同一个函数**，所有订阅定义的事件都进这里。事件体里**只有 `approval_code` 能区分"这是哪个审批"**。

### 2.2 不过滤会发生什么

| 情形 | 后果 |
|---|---|
| 只订阅定义 C | 只有 C 的事件会来，管道干净 → **过渡期就这样做，物理上不可能串** |
| 日后也订阅了定义 A | A 和 C 的事件**混在同一回调** → 若代码不区分：**队员用老审批报销一笔 → 服务以为走新流程 → 同一笔报销记两次账** |

### 2.3 过滤代码（第一行就做）

```go
func onApprovalInstance(ev Event) error {
    if ev.ApprovalCode != ourApprovalCode {
        log.Info("skip foreign approval",
            "code", ev.ApprovalCode, "instance", ev.InstanceCode)
        return nil // 不是我们的定义：直接丢弃，不落账、不通知、不写任何表
    }
    // ... 才是我们的事件
}
```

**这不是防御性编程，是防串账。** `approval_code` 只标识"哪种审批"，不标识"哪一单"——
认错定义，整条链都会把老单据当新单据处理。

### 2.4 过渡期规则（更简单）

**上线前不订阅现有审批定义。** 只订阅我们的新测试定义 →
从物理上就不会收到现有审批的事件，串流风险为零，过滤代码只是第二道保险。

## 3. 关联键重新设计

原设计用"服务灌入的只读控件 `submission_id`"作为关联键。既然**实例由队员创建**，
服务没办法灌值 → 关联键必须**从表单里已有的东西推导**。

### 3.1 优先级

| 优先 | 关联键 | 条件 | 可靠性 |
|---|---|---|---|
| 1 | **`instance_code` 本身** | 直接用审批实例码做本地主键 | **最可靠**（飞书唯一、必然存在） |
| 2 | 发票指纹 `sha256(invoice_code\|invoice_no)` | 从附件识别得到 | 可靠（用于防重复报销，不是用来找单） |
| 3 | 队员填的"单号/时间/金额"组合 | 仅当表单里有 | 不可靠，**只作辅助** |

> **结论：用 `instance_code` 作为本地主键与关联键。**
> 它天然唯一、天然来自飞书、天然出现在每条事件里 → **不需要队员额外填任何东西**。
> 这也顺带满足了"0 必填"的产品原则。

`submission_id` 降级为**本地生成的内部单号**（如 `S-2026-0001`），只用于展示与人工沟通，
**不再承担关联职责**。这样就不需要在表单里加隐藏字段，也就不用改任何定义。

## 4. 表单设计：图片怎么放（待你定）

签核型审批表单里放**三张附件**会产生语义歧义（哪张是发票？哪张是订单？）。
两个方案：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A：三个明确附件控件**（推荐） | `发票` / `订单截图` / `付款记录` 各一个附件控件 | 语义**零歧义**；匹配层不需要猜测；不需要额外字段 | 队员心里要做 3 次选择 |
| **B：一个附件控件** | 队员一次传 3 张，服务用模型分类 `kind` | 队员零负担 | **模型分错 = 匹配全错**，且错误难发现 |

**推荐 A**：欠票主因是"懒得填"，而**分格子比事后被系统认错要省心**——
错误识别的返工成本远高于多点一下的成本。

### 4.1 待核实：审批定义能否放附件控件

架构稿已标注"创建实例 API 有**不支持**的控件类型"，而我们是**读取**方向，风险较小。
但仍需确认审批表单**能否**放附件/图片控件。

> **列入 T3**：建测试定义时试一下。若不支持 → 退化为"队员把三张图合并成一张长图"或
> "表单填多维表格链接，图片存多维表格"。
