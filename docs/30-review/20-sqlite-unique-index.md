# 本地 SQLite + sha256 唯一索引（已落地）

> 2026-09-13。这是"防重复报销"从**应用层检查**升级为**数据库约束**的一步，
> 也是本项目存在的第一理由（飞书多维表格没有任何唯一索引能力）。

---

## 0. 为什么必须做这件事

`docs/00-brief/02-feishu-capability-facts.md` A2 已核实：

> 多维表格**平台不存在字段级唯一约束**。字段 API 全部参数中无任何 `unique` 项。
> 只有事后方案：`UNIQUE()` 公式、`IF+COUNTIF` 标记、条件格式高亮 —— **均不能阻止重复写入**。
> 写接口 `client_token` 只保证单次请求幂等，不约束值唯一。

再加上 A3：**同一数据表禁止并发写**（`1254291`）。

所以"先查重、再写入"在飞书上天然是 **TOCTOU 竞态**：

```
时间 →
实例A: 查重(无) ────────────► 写入
实例B:      查重(无) ────────► 写入      ← 两次查重都通过，同一张发票进了两次
```

**放到 SQLite 后，这个判定不再依赖时序**。

## 1. 已实现

### 1.1 迁移文件 `internal/store/migrations/0001_init.sql`

四张表：

| 表 | 作用 |
|---|---|
| `submission` | 一行一单（审批实例） |
| `evidence` | 一行一图，带 `sha256` |
| `dept_dict` | 部门 `od-` ID → 名称（对照表兜底） |
| `audit_log` | append-only 审计 |

### 1.2 ★ 两条关键约束（写在 schema 里，不写在代码里）

```sql
-- 同一张图只能进库一次
CREATE UNIQUE INDEX uq_evidence_sha256 ON evidence(sha256);

-- 审计不可篡改
CREATE TRIGGER trg_audit_no_update BEFORE UPDATE ON audit_log
BEGIN SELECT RAISE(ABORT, 'audit_log is append-only'); END;
CREATE TRIGGER trg_audit_no_delete BEFORE DELETE ON audit_log
BEGIN SELECT RAISE(ABORT, 'audit_log is append-only'); END;
```

### 1.3 整单事务

`SaveInstance` 把「提交行 + 全部证据」放在**一个事务**里：

- 任一条证据命中唯一约束 → **整单回滚**（不会出现"3 张图进了 2 张"的半写状态）
- 返回 `*DupError`，里面**指出首次占用该图的实例**，便于人工判断

### 1.4 技术选型（与架构稿一致）

| 项 | 值 | 理由 |
|---|---|---|
| 驱动 | `modernc.org/sqlite` v1.58.0 | **纯 Go 无 CGO** → 静态单二进制不打折 |
| 连接数 | `MaxOpenConns(1)` | SQLite 写锁是库级；与飞书"同表禁并发写"同构 |
| PRAGMA | `journal_mode(WAL)` · `foreign_keys(ON)` · `busy_timeout(5000)` | WAL 读写并发；外键必须显式开 |
| 表类型 | `STRICT` | schema 层禁止类型混用 |
| 金额 | `INTEGER` 存**分** | 禁用浮点 |

## 2. 实测：唯一索引真的拦得住

`internal/store/store_test.go`，6 个测试全过：

| 测试 | 结果 |
|---|---|
| 同一张图第二次提交 | ✅ 被拒，并指出首次来源 |
| **12 个并发提交同一张图** | ✅ **恰好 1 次成功、11 次判重**，库里只有 1 条证据 |
| 三张不同的图 | ✅ 全部入库 |
| 同一实例重跑 | ✅ 命中唯一约束，证据不翻倍 |
| 审计表 UPDATE / DELETE | ✅ **被触发器拒绝** |
| 部门字典 | ✅ 累积与查询 |

**并发那条是关键**：

```
=== RUN   TestConcurrentDuplicateExactlyOneSucceeds
    ✓ 12 个并发提交 → 成功 1 / 重复 11，数据库里只有 1 条证据
```

### 2.1 管线级验证

```
第一次：go run ./cmd/extract -limit 3
       完成：入库 3 单，重复拦截 0 单

第二次：go run ./cmd/extract -limit 3   ← 同一批
       ⛔ 重复报销拦截：该图已存在（sha256=5912ae772481…，首次来自实例 C5489DC9-…）
       ⛔ 重复报销拦截：该图已存在（sha256=27452911a7c3…，首次来自实例 4C37F5AF-…）
       ⛔ 重复报销拦截：该图已存在（sha256=52420eeaabad…，首次来自实例 83C2567D-…）
```

数据库**没有增长**（仍是 3 单 / 9 条证据）—— 事务回滚正确。

## 5. 重新回答"为什么全是待人工审核"（含一处勘误）

顺便把上一个问题讲清楚：

`人工审核` 默认值就是 `待审`，**每一行都要人确认**。这不是缺陷 —— 因为**机器会错**。

> **勘误（2026-09-13 当日修正）**：本节初稿写"¥4.60 那张票给出 4600/100/4500、整条链路全绿"。
> **这个说法是错的** —— 该次输出里 `上校验=UPPER_MISMATCH`，**大写校验已经抓住了它**。
> 三单互核也会抓（4600 vs 460 vs 460 → `AMOUNT_SCALE_ERROR`）。
>
> **真正的"全绿但错"是另一个 case**：更早一次运行给出 `460 / 10 / 450`（总额对、分摊错），
> 此时小写 460 与大写 `肆圆陆角整`(=460) 一致、三单总额也一致 —— **两个校验都拦不住**，
> 因为它们验证的都是**总额**，不涉及**税额/不含税的分摊**。
>
> 该缺口的影响有限：`match.Compare` 只用价税合计做匹配，所以**不影响核心功能**；
> 只是表里「图读税额」一列不可靠，应视为参考值。

`核对结果` 的作用是**排优先级**，不是免审依据：

| 核对结果 | 对待方式 |
|---|---|
| **一致** | 快速扫一眼即可 |
| **存疑 / 缺件** | 重点看（**且只有这两种会发消息通知你**） |

那 1 条"通过"是我做归档实测时手动设的。

### 5.1 各校验的覆盖边界（实测得出）

| 校验 | 验证对象 | 能否抓"分摊错" |
|---|---|---|
| **大写校验** | **价税合计** 小写 ↔ 大写 | ❌ 只看总额 |
| **三单互核** | 发票/订单/付款的**总额**一致 | ❌ 只看总额 |
| 税额自检 | 总额 = 不含税 + 税额 | ❌ 自洽的错抓不到 |
| — | **税额 / 不含税的分摊** | **无独立验证** |

**结论**：总额有三重保护，能抓住 10 倍/位数类错误；
**分摊（税额/不含税）没有任何独立验证**，只能当参考值 —— 好在匹配不依赖它。
