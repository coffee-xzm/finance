# 审批测试方案与「审批通过后剩余工作」

> 回答用户 2026-09-12 的三个问题：
> 1. 审批做完了，**还剩什么没做**？
> 2. 先单独建一个审批入口，**会不会影响现有审批**？
> 3. 想**先在个人文件夹里生成多维表格做测试**，怎么做？
>
> 关联：`02-ocr-provider-interface.md`（识别层）、`03-approval-routing.md`（审批如何回流）、
> `../20-synthesis/02-architecture-v0.1.md`（架构与 7 张表）。

---

## 0. 先给结论

| 问题 | 结论 |
|---|---|
| 新开一个审批入口会影响现有审批吗？ | **不会。** 审批定义是**各自独立**的资源：各自的表单、流程、条件分支、订阅。新建一个定义不改变任何现有定义的行为 |
| 唯一需要注意的全局面 | **事件订阅是"应用级"的**——`approval_instance` 等事件会推给**该应用订阅过的所有审批定义**。所以代码里必须按 `approval_code` 过滤。这不影响任何现有审批，只影响你的代码 |
| 「审批过了」= 链路通了吗？ | **不等于。** 事件配置页配好 ≠ 事件会来。审批是**双层订阅**：事件订阅（控制台）+ **审批定义订阅**（`POST /approvals/:approval_code/subscribe`）。少第二层，一条事件都不会有 |
| 先在个人文件夹测试可行吗？ | **可行且推荐。** 唯一硬点：**应用必须对该文件夹/文档有权限**，否则 API 写入以 `403 / permission denied` 失败 |

## 1. 审批到底会影响什么（逐项判定）

| 影响面 | 会不会被新审批入口影响 | 说明 |
|---|---|---|
| 现有审批定义的**表单** | ❌ 不影响 | 定义级资源，各自独立 |
| 现有审批定义的**流程与条件分支** | ❌ 不影响 | 同上 |
| 现有审批的**进行中实例** | ❌ 不影响 | 实例绑定创建时的定义版本 |
| 应用收到的**事件流** | ⚠️ **会变多** | 事件订阅是应用级的：你订阅了 `approval_instance`，那么**所有已注册订阅的定义**产生的实例都会推给你 → **代码必须按 `approval_code` 过滤** |
| 队员看到的**审批入口** | ⚠️ **取决于你怎么发布** | 新建的定义只要**不发给队员、不放工作台**，队员就看不到。**测试期间不要群发入口链接** |
| **待办/通知噪声** | ⚠️ **每创建一个实例就产生** | 只要调了 `POST /instances`，就真的产生一条待办和通知，进审批人的消息列表。**测试时把审批人设为自己** |
| 正式数据 | ❌ 不影响 | 只要**不往正式多维表格写**。测试用独立的个人文件夹表格 |

> **一句话的纪律**：审批定义之间隔离，但**事件订阅和通知是真实世界副作用**——测试时请把"发起人"和"审批人"都设成你自己。

## 2. 「审批通了」到底意味着什么：双层订阅

这是最容易误判的一处，单独讲清：

```
第 1 层 · 事件订阅（控制台，你已完成）
   「这类事件要不要推给我」
   ← 截图里的 订阅方式=长连接 + approval_instance/approval_task/approval_cc
   ← 【待发布】必须发布才生效

第 2 层 · 审批定义订阅（API，★ 最容易漏）
   「这个审批的实例要不要产生事件」
   POST /open-apis/approval/v4/approvals/:approval_code/subscribe
   ← 官方流程：先订阅接口，再到审批后台订阅
   ← 每新增一个审批定义都要补订阅
```

**两层都完成、且应用已发布，事件才会真的到达长连接。** 判定链路是否真的通，唯一标准是：
**真实发起一次审批，看进程日志里有没有打出事件** —— 不是看控制台页面配得多漂亮。

## 4. 测试方案：独立审批入口 + 个人文件夹多维表格

### 4.1 为什么这个顺序是对的

- **审批定义天然隔离** → 新定义不动任何现有审批；
- **多维表格放你个人文件夹** → 测试数据与正式数据物理分离，任何时候可以整份删除；
- **代价**：需要让应用能访问该文档（见 4.3 的硬点）。

### 4.2 步骤

**阶段一：建测试审批定义（在审批后台手工建）**

| 控件 | 类型 | 用途 | 关键点 |
|---|---|---|---|
| `submission_id` | 文本（**只读**） | 关联键 | 创建实例时灌入；事件回来靠它找单 |
| `amount` | **金额** | 分档条件分支 | 已核实"金额"可作为分支条件 |
| `match_summary` | 文本 | 匹配结论 | 给审批人一眼看 |
| `defects` | 文本 | 缺陷清单 | 缺哪一单/差多少 |
| `applicant_note` | 文本（可选） | 人工备注 | |

流程：单节点审批，**审批人设为你自己**（测试期）。
条件分支：先用一条最简单的（金额 ≥ 某个值 → 加一个节点），验证分支真的生效即可。

> **不要**在测试定义里做复杂的四档分支——那是正式定义的事，测试只需要证明"分支可用"。

**阶段二：建个人文件夹的测试多维表格**

在你的飞书云空间**个人文件夹**下新建一个多维表格，建 4 张表（够验证闭环）：

**表 1 `票据收集台账`**（飞书权威，映射至正式 submission）
`提交ID`(文本) · `申请人`(人员) · `组别`(单选) · `业务类型`(单选) · `资金来源`(单选) ·
`金额`(数字，**分**为单位存 INTEGER 的展示层用元) · `三张图`(附件) · `匹配状态`(单选) ·
`缺陷清单`(文本) · `提交时间`(日期) · `审批实例`(文本，存 instance_code)

**表 2 `识别证据`**（本地权威，镜像展示）
`提交ID` · `图类型`(单选 invoice/order/payment) · `金额` · `日期` · `对方名称` ·
`发票代码` · `发票号码` · `指纹`(文本) · `置信度` · `provider` · `model` · `原始响应`(文本)

**表 3 `发票唯一性`**（本地权威，用于看查重效果）
`指纹`(文本) · `发票号码` · `首次提交ID` · `占用状态`(单选 CLEAR/SUSPECT)

**表 4 `审批结果`**
`提交ID` · `instance_code` · `状态`(单选 PENDING/APPROVED/REJECTED/CANCELED) · `操作人` · `时间` · `备注`

> **建表期三条硬约束**（架构稿 §4.8 已核实，违反就白测）：
> 1. **只读字段绝不能作为写入目标**：公式、查找引用、自动编号、创建时间、创建人、修改人。
>    所有计算结果由 Go 算完写进**普通字段**。
> 2. **附件**：`upload_all` 拿 `file_token` → 写入记录；单文件 ≤20 MB；**`file_token` 不可跨表复用**。
> 3. **仪表盘无法用 API 创建** → 想看看板就手工建一次，或用 `copy` 克隆。

**阶段三：让应用拿到该文档的权限（★ 唯一致命硬点）**

- 应用需要具备 `bitable:app` 权限；
- **并且**该多维表格/文件夹必须在应用的可访问范围内：把应用（或应用所属的机器人）**加为该文档/文件夹的协作者**；
- 若文档开了**高级权限**，下载附件还需带 `extra`（`bitablePerm`）鉴权参数，否则 403。

> 建议测试期**先不开高级权限**，把"权限"这个变量隔离掉。等闭环通了再单独验权限。

**阶段四：跑最小闭环**

```
① 手工在飞书表单/表格里造一条记录（或直接用 API 写一条）
② Go 服务：识别 3 张图（SiliconFlow）→ 写表 2、表 3
③ Go 服务：创建审批实例（灌入 submission_id / amount / match_summary / defects）
      → 记录 instance_code 到表 1、表 4
④ 你在飞书里审批：通过
⑤ 长连接收到 approval_instance 事件 → 过滤 approval_code → 查映射 → 状态机 → 更新表 4 状态
⑥ 机器人卡片通知"审批通过"
```

### 4.3 验收标准（每条都可测）

| # | 验收项 | 通过标准 |
|---|---|---|
| A1 | 长连接连通 | 控制台「验证连接状态」通过；进程日志有连接成功记录 |
| A2 | **事件真的到达** | 发起一次审批后，日志里打出事件；**记录下事件类型与事件体字段**（→ 回填 `03-approval-routing.md` §5） |
| A3 | 关联键可用 | 事件里的 `instance_code` 能通过本地映射找回 `submission_id` |
| A4 | 表单灌入可用 | 审批人能看到 `submission_id` / `match_summary` / `defects` 的值 |
| A5 | 审批结果回流 | 通过后表 4 状态变为 `APPROVED`；驳回变 `REJECTED` 且占用释放 |
| A6 | 幂等有效 | 人为重放同一 `event_id` → 状态与账务**不重复变化** |
| A7 | 乱序安全 | 人为先投 `APPROVED` 再投 `PENDING` → 终态**不被回退** |
| A8 | 附件链路 | 三张图能从飞书附件取回（含高级权限开启后的 `extra` 鉴权） |
| A9 | 不影响正式 | 正式审批定义与数据**零变化** |

## 6. 测试期纪律（避免影响正式）

1. **审批人 = 你自己**，发起人 = 你自己。不拉任何队员。
2. **不发**测试审批入口链接，不放工作台。
3. 测试写入**只落个人文件夹的表格**，`config.yml` 里的 `app_token` 指向测试表。
4. **代码里按 `approval_code` 过滤事件**——否则以后正式定义上线，事件会串。
5. 建表时**不要开高级权限**（先隔离权限变量）。
6. 测完要清理：删除测试多维表格即可；测试审批定义若不想要，**只能删除实例**（定义本身若由 API 建则无法删除 → 这也是当初坚持"后台手工建"的原因之一）。
