# 33 · 采购审批 → 27发票收集 → 流水表：计划 v0.3

> 起因（用户 2026-09-19 需求更新）：
> 1. 发票收集侧：校验通过的发票置「已通过」；**人工审核不再在每次新审批时被机器轮询/代填**，
>    由审批结果驱动；当它从 待审 → 通过 时，才处理该行字段（归档）。
> 2. 新开流水表、采购审批表；新开审批单「采购审批-27Test」并用它；
>    原来的「系统测试」审批已改名为「27发票收集」。
> 3. 所有静态配置写进 config 文件并由它控制。
> 4. **采购审批表只读**；所有表**只填空白单元格，不覆盖任何非空单元格**。
> 5. 采购审批通过后：① 创建一个提交人 = 该采购审批提交人的「27发票收集」审批，把采购信息填进去，
>    等提交人补完剩下的部分并提交；② 把对应记录写进流水表。
>
> 状态：**计划稿，未开工**。§1–§10 是设计与实测依据，§11 起是分期、风险、待拍板项。
>
> v0.2 相对 v0.1 的变化（依据用户 2026-09-19 的答复）：
> - 归档/人工审核**改由审批结果驱动**（不再依赖多维表格变更事件）；
> - 校验没问题 → **服务自动同意审批**；校验有问题 → 人工审核落"有问题"态（v0.3 定为「驳回」）；人再把审批通过 → 通过；

> - **发票侧要写流水**：收齐后把「发票收集进度」改为「已通过」（修正 v0.1 的口径）。
>
> v0.3（第二次答复后的定稿项）：
> - `🔗 发生日期` = **采购审批的完成时间**（=审批通过时刻）；
> - 人工审核沿用原选项名 **待审/通过/驳回**，机器判有问题就写「驳回」，不再纠结取名；
> - 自动同意审批的门禁 = **该实例全部行无问题**（任一行有问题就不自动同意）；
> - 「发票收集进度」改为**单选**字段；「收齐」判据 = 发票收集单**审批通过**
>   （通过来源可以是"校验一致自动通过"或"人工通过"）；
> - 「梯队」只是目标多选字段的历史选项，采购侧没有任何来源会产出它 → 不需要映射（见 §11）。

```

队员提交「采购审批-27Test」
   │ 事件 APPROVED
   ▼

   ├─► 每条【费用明细】写一行【支出】到「27 - 收支表」（表尾新增、只填空）
   │      科目/去向 = 技术组物资 if 项目组∈{硬件组,机械组,电控组,视觉组} else 项目组物资
   │      发票收集进度 = 待办
   └─► 创建一条「27发票收集」审批：提交人=采购提交人，预填 购买人/物资所属部门
         └─ 立即 rollback 到 START（退回发起人），等他补附件后重新提交
                     └──────────────── 发票侧（沿用+改触发）──────────┘
队员补完提交「27发票收集」
   ▼ 事件（长连接）
extract → 校验 → sync 写「报销核对」，并按行落 人工审核：
   全部行无问题 → 人工审核=通过 + 服务调「同意审批任务」自动通过审批
   任一行有问题 → 有问题的行 人工审核=驳回，不自动通过，等人在飞书审批
   ▼
审批实例状态变为 已通过（机器或人）
   └─► 全部相关行 人工审核=通过 → 归档到「报销整合」
   └─► 若该实例是"采购派生"的发票收集单 → 回写对应流水行「发票收集进度=已通过」
```

四条硬边界：

1. **采购审批表只读**：`tbllUFP…` 只 GET，绝不写。
2. **流水由采购派生**；发票侧**只更新**已存在流水行的「发票收集进度」，不新增流水行。
3. **写表只填空单元格**：目标单元格已有值 → 跳过；**但服务自有的状态列例外**（人工审核/已归档/
   审核时间/发票收集进度）——否则"驳回 → 通过"这类状态跃迁根本写不进去（见 §6）。
4. **代建幂等**：`uuid = 采购实例号`；事件重放不重复建单、不重复写流水。

## 2. 需求逐条 → 设计映射

| 用户口径 | 落地设计 |
|---|---|
| 校验通过的发票设置为已通过 | sync 时：该行核对一致且无 problem → 写「人工审核=通过」 |
| 校验没问题直接通过审批 | 实例级判定无问题 → 服务调 `tasks/approve` 自动同意（新增写审批能力） |
| 校验有问题就把人工审核写为不通过 | 有问题的行写「人工审核=**驳回**」（沿用原选项名，用户：不纠结取名） |
| 如果人再把审批单通过就认为人工审核通过 | 审批实例 APPROVED 事件 → 该实例相关行「人工审核=通过」→ 归档 |
| 自动同意的门禁 = 全部行 | 该实例**全部行无问题**才调 `tasks/approve`；任一行有问题就不自动同意 |
| 人工审核不再每次新审批时轮询/代填 | 删掉 `process()` 里的全表 `RunArchive`；机器只对本次同步的行置初值 |
| 新开流水表 / 采购审批表只读 | 写 `tbl2brj…`；只读 `tbllUFP…` |
| 新开审批单并使用 | config 角色化多 code；订阅其事件；APPROVED 时跑采购流程 |
| 原「系统测试」改名「27发票收集」 | `approval_name_expect` 改 `27发票收集` |
| 所有静态配置写入 config | §3 字典化 |
| 只填空白单元格 | §6 `WriteMerge` + 服务自有状态列豁免 |
| 采购通过 → 代建发票收集单 | §5.3 `CreateInstance` + `specified_rollback(START)` |
| 采购通过 → 记流水 | §5.2：**每条费用明细一行**支出 |
| 发票侧收齐后把「发票收集进度」改为已通过 | §5.4：发票收集单「审批通过」（校验一致自动通过 或 人工通过）→ 回写关联流水行 |

## 4. 发票收集侧：校验 → 自动通过 → 人工兜底 → 归档

### 4.1 去掉"每次新审批顺带扫全表"

`process()` 每次会 `pipeline.RunArchive(...)` 扫整张核对表 —— 这就是"每次有新审批时轮询"。
**删掉**；`RunArchive` 只保留为手动/运维命令。

### 4.2 新的状态机（依据用户 2026-09-19 口述）

```
实例提交（PENDING）
  → extract → 校验 → sync
      每行： 无问题 → 人工审核=通过
             有问题 → 人工审核=驳回
      实例级：全部行无问题 → 调 tasks/approve 自动同意该审批
              任一行有问题 → 不自动同意，等人在飞书审批
  → 审批实例 APPROVED 事件（机器同意或人同意都会来）
      该实例所有行 人工审核=通过（覆盖 驳回→通过）→ 归档到「报销整合」
      若是采购派生的发票单 → 回写关联流水行 发票收集进度=已通过（§5.4）
  → 审批被 拒绝/撤回/取消 → 沿用现有剔除逻辑（本地库 + 核对表）
```

要点：

- **触发源是审批状态事件**（`approval_instance`，已经在订阅），不是多维表格单元格变更 →
  **不需要** `drive.file.bitable_record_changed_v1`，也不需要 120s 轮询（可选加一个兜底对账）。
- **服务首次获得"同意审批"能力**：`POST /approval/v4/tasks/approve`（`instance_code`+`task_id`+
  审批人 `user_id`）。task_id 从 `GET /instances/:code` 的 `task_list` 取（需扩展解析）。
- 自动同意失败（权限/任务已被处理）→ 不静默：记本地 + 告警，审批仍可由人处理。
- **覆盖"驳回→通过"是必需的**，与"只填空"冲突 → 用 §6 的服务自有列豁免解决。

## 5. 采购审批侧（新增）

### 5.1 事件路由

按 `role` 路由：`invoice_collect` → 发票链路；`purchase` → 仅 `APPROVED` 入采购队列；
其它 code → 留痕 IGNORED。采购幂等键 = **采购实例 code**（本地表 `purchase_sync`）。

### 5.2 写流水（27 - 收支表）：每条费用明细一行

用户口径：**多条费用明细拆成多行**；`科目/去向` 由**项目组**决定：

| 收支表字段 | 来源 |
|---|---|

| 🔗 科目 / 去向 | 项目组 ∈ {硬件组, 机械组, 电控组, 视觉组} → `技术组物资`；否则 → `项目组物资` |

| 🔗 备注 | 项目名称 + 品名/规格/数量（人可读摘要） |

### 5.4 发票收齐 → 回写流水「已通过」

用户修正：「发票表不管流水」这句作废；**发票侧收齐后把该列改为「已通过」**。

- 关联：本地 `purchase_sync` 存 `invoice_instance_code ↔ purchase_instance_code ↔ ledger_record_ids`。
- 触发：采购派生的发票收集单**审批通过**（通过来源 = 校验一致自动通过 **或** 人工通过）→ 把该采购对应的
  全部流水行「发票收集进度」写 `已通过`（服务自有列，允许覆盖）。
- 判据（用户 2026-09-19 定）：**审批通过 且（校验一致 或 人工通过）**。实操上等价于"该发票收集单状态=已通过"，
  因为通过只有这两条来路。

## 6. 写策略：只填空单元格（含服务自有列豁免）

```
WriteMerge(existing, desired, serviceOwned):
    for k, v := range desired:
        if k ∈ serviceOwned        → 写入
        else if existing[k] 为空   → 写入
        else                       → 跳过
```

| 写点 | 行为 |
|---|---|
| sync 更新核对行 | 业务列只补空；`人工审核` 等服务自有列可覆盖 |
| archive 写整合表 | 新行全写；`已归档`/`审核时间` 只补空 |
| 采购写流水 | 新增行全写；已存在则只补空 |
| 发票回写流水进度 | `发票收集进度` 是服务自有列 → 可覆盖（待办 → 已通过） |

推论：幂等靠"找到同一行"（实例号+发票号 / 采购实例号 + 明细序号），不靠覆盖；
机器写错的**业务列**不能自愈，需要人清空或默认关闭的 `-force` 运维开关。

## 10. 风险与硬约束

1. **没有草稿态** → 只能"创建+退回"；rollback 是否总成功、是否引发事件回环，P0 必验。
2. **创建实例不支持 `text` 控件** → 27发票收集当前 8 控件都支持；**不要给它加「说明」**。
3. **镜像表有同步延迟** → APPROVED 时镜像行可能未到；兜底直读审批实例。
4. **自动同意 = 服务代审批人点头** → 权限与责任都要写清；只对发票收集单生效。
5. **"只填空" vs 状态跃迁** → 必须实现服务自有列豁免，否则 驳回→通过 写不进去。
6. **多明细的镜像行粒度未定** → 直接影响回链与行数，P0 验证。
7. **组名集合不一致** → 项目组有「重装组」，报销核对物资所属部门没有；反之物资所属部门有
   「工程组/英雄组/梯队」而项目组没有。已定别名 工程组/英雄组→重装组；「梯队」在采购侧**没有来源**，
   所以自动映射不会产出它，不需要处理（见 §11）。

### 12.9 「当前金额」公式修正：飞书公式引擎的三个硬限制（2026-09-19）

用户报「收支表的金额计算有问题」。实测把根因和边界都钉死了。

**症状**：`09-19 21:55` 那行（`recvvFRV080p63`，支出 23）的「当前金额」显示 **177**，而正确余额是 **39777**。

**根因**：表里的公式用"上一行"算余额，但取的是上一行的 **「🔗 金额」**（本行差额），不是上一行的**余额**：

```
LET(上一条金额, <最近一条更早的行>.$column[fldUmdBbBw].FIRST(),   ← fldUmdBbBw = 🔗 金额 ❌
    SWITCH(方向, "支出", 上一条金额 - 本行金额, "收入", 上一条金额 + 本行金额,
                "当前本金", 本行金额, ""))
```

前两行（本金 40000、支出 200）**碰巧**正确（本金行的"金额"就等于其余额），第 3 行起退化成"上一行差额 ± 本行差额"。

**实测的引擎限制**（每次都是"写公式 → 回读该列实际计算结果"，用完自动回滚原式）：

| # | 写法 | 结果 |
|---|---|---|
| ① | `SUM(表.FILTER(CurrentValue.$column[方向]="支出").$column[金额])` | ✅ 223 |
| ② | `AND(两个 CurrentValue/本行字段 条件)` + 时间比较 | ✅ 0 / 200 / 223 |
| ③ | `表.FILTER(...).SORTBY(时间,FALSE).$column[金额].FIRST()`（取"最近一条本金"） | ✅ 40000 |
| ④ | `LET` 里放常量变量，再进 `FILTER` 条件 | ✅ 223 |
| ⑤ | `LET` 里放 **lookup 得来的**变量（时间戳），再进 `FILTER` 条件 | ❌ 整列空白 |
| ⑥ | 把 lookup **内联**进 `FILTER` 条件（嵌套 FILTER） | ❌ 整列空白 |
| ⑦ | 公式**引用自己的列**（取上一行余额） | ❌ 整列空白（成环） |

⇒ 「取上一行余额」在当前引擎里**不可实现**：要么自引用成环，要么把 lookup 塞进 FILTER 条件（空）。
所以原设计（链式累减）只能换写法。

**落地写法**（`本金 = 快照重置`语义，与用户原设计一致）：

```
「余额段（辅助列）」 = COUNTA(表.FILTER(AND(方向="当前本金", 登记时间 <= 本行登记时间)).$column[方向])
「当前金额」 = LET(本金,   <最近一条本金行的金额>,
                   支出和, SUM(表.FILTER(AND(CurrentValue.$column[余额段] = 本行余额段,
                                              CurrentValue.$column[方向] = "支出",
                                              CurrentValue.$column[登记时间] <= 本行登记时间)).$column[金额]),
                   收入和, SUM(… "收入" …),
                   本金 - IF(ISBLANK(支出和),0,支出和) + IF(ISBLANK(收入和),0,收入和))
```

- 关键点：把"时间下界"换成"**同段**"（段号是普通列引用，可以出现在 `FILTER` 条件里）。
- 实测结果：**40000 / 39800 / 39777** ✅（新增本金快照行后，历史行数值不变、其后行以新本金起算）。
- 代价：多一个辅助列「余额段（辅助列）」（可在视图里隐藏）。原式已在 `cmd` 临时工具里留档，可随时回滚。
- 备选（不加列）：`当前金额 = 累计(本金 + 收入 − 支出)`，但语义变成"本金=追加"，与"截止目前的本金"快照语义不符，未采用。

**顺带纠正一条旧结论**：`internal/feishu/client.go` 里写着"新增字段不能设置公式表达式（官方限制）"——
实测 **能**：`CreateBitableField(type=20, property.formula_expression=…)` 一次成功（`fldQD74DdA`），
`UpdateBitableField` 改公式表达式也成功。注释已改。

#### 余额公式是否支持"转入"

用户问「余额的计算公式是否同时支持转入和支出」。**支持**，且不需要改公式：

```
当前金额 = LET(本金, <最新一行"当前本金"的金额>,
              支出和, SUM(FILTER(段=本行段 AND 方向="支出" AND 登记时间<=本行)),
              收入和, SUM(FILTER(段=本行段 AND 方向="收入" AND 登记时间<=本行)),
              本金 - 支出和 + 收入和)
```

- 支出是 `-`、收入是 `+`，两项都在（实测链：40000 −200 −48.4 −62.9 −27.6 = 39661.1）；
- 「余额段（辅助列）」= 数到本行为止出现过几行"当前本金"，作为分段 key；
- ★ 表单里的选项文字是「**转入**」，表格里是「**收入**」——同一个意思，由代码映射
  （`flowForm.Direction()`），不需要动表结构、也不需要动公式。

代码侧从这两天的坑里学到的健壮性（都有单测兜着）：

- 建单与退回**分开判定**（draft 模式）：只要 code 拿到就先落 `flow_register` +
  写「流水审批ID」，否则重跑会再建一张（60012）或让覆盖认不出行（写成新行）；
- `draft_state` 分档：`failed`（建单失败）补漏扫描自动重试，`blocked`
  （建出来了但退不回去 = 审批定义问题）**不自动重试**，免得每 10 分钟多建一张作废单；
- `CreateInstance` 撞 `60012` 自动换 uuid 重试；
- 转账日期**只在当天预填**（该控件的范围校验会拒过去日期：
  `1390001 date: 2026-09-21 out of range`），遇到日期类报错还会自动去掉该项重试；
- 无 `event_id` 的事件（实测 `approval_task` v2）不再硬写留痕表刷"留痕失败"。
