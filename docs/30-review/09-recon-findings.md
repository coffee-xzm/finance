> 数据来源：`finance-router/cmd/recon` 对真实审批定义 `<APPROVAL_CODE>`（**<APPROVAL_NAME>**）
> 的只读读取。样本：2026-09-01 ~ 2026-09-13，20 条实例详情。
> 采集日期：2026-09-13。**全程只读，未写飞书任何数据。**

## 0. 三个结论

1. **★ 表单已经长成了我们要的样子** —— 三个附件控件正好是
   `发票文件` / `订单截图` / `付款截图`，**前端一个字段都不用改**。
   用户"先不改前端"的判断被数据证实。
2. **★ 附件能下载，且不需要额外鉴权** —— 但 URL **24 小时过期**，必须现读现用。
3. **★ 表单自带结构化金额与日期**（`费用汇总` 公式 + `费用明细` 明细行），
   这让三单匹配从"纯 OCR 推断"变成"**声明值 vs 单据值 的核对**"，难度大幅下降。

### 2.1 `费用明细`（fieldList）的内部结构

```json
[[
  {"id":"widget16510510138590001","name":"日期（年-月-日）","type":"date",
   "value":"2026-08-07T00:00:00+08:00","timezoneOffset":-480},
  {"id":"widget16510510254730001","name":"金额","type":"amount",
   "value":228.31,
   "ext":{"currency":"CNY","capitalValue":"贰佰贰拾捌元叁角壹分"}}
]]
```

**要点**：
- 外层是**二维数组**：第一维 = 明细行，第二维 = 该行的字段；
- 每行自带 `日期` 与 `金额` → **结构化、可直接用于匹配**；
- `费用汇总` 应该是这些金额的合计（公式算出）。

## 3. ★ 附件链路（T3 / T5 关闭）

### 3.1 实测结构

附件控件的 `value` 是**字符串数组，元素是带 authcode 的下载直链**：

```
https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=<base64>
```

| 结论 | 依据 |
|---|---|
| **没有 `file_token`** | → 走不通 `drive/v1/medias/:file_token/download`，那只适用于多维表格附件 |
| **直链可直接 GET** | 实测 `HEAD` → **HTTP 200**，无额外鉴权头（authcode 自身即凭证） |
| **有效期 24 小时** | authcode 解码为 `<hash>_<hash>_ID:7675647258982370483_1789281781:1789368181_V3`，起止相差 **86400 秒** |
| **不是高级权限 `extra` 那条路** | 无需 `bitablePerm`；这是审批域的下载通道 |

**因此：必须现读现用，不能缓存 URL。** 缓存了也要重取实例详情换新链接。

### 3.2 ★ 媒体类型分布（前 8 条实例，逐个 HEAD 实测）

| 控件 | 类型分布 |
|---|---|
| **发票文件** | **`application/pdf` 11/11（100% PDF）** |
| 订单截图 | `image/jpeg` 6，`application/pdf` 2 |
| 付款截图 | `image/jpeg` 8，`application/pdf` 1 |

**结论：**
1. **发票必然是 PDF** → `pdf2png` 是**必需**组件，不是可选项；这验证了用户"发票一般是 PDF"的判断。
2. **订单/付款截图以 JPEG 为主，但偶有 PDF** → 管线必须**统一处理两种输入**，按 `Content-Type` 分流。
3. 文件名（`Content-Disposition`）是**免费的分类信号**：
   - `滴滴电子发票.pdf`、`如祺出行电子发票.pdf` → 真发票；
   - **`滴滴出行行程报销单.pdf`** → **是行程单，不是发票**！这类必须能被识别出来，
     否则会污染发票唯一性指纹。
   - `Screenshot_2026-08-19-15-52-24-55.jpg` → 明显是手机截图。

### 3.3 一个附件槽可能有多张

`付款截图` 20 条实例里有 26 个附件 → 平均 >1，**存在一个槽放多张图的情况**。
匹配层要能处理"一个槽多张图"（例如两笔转账付一单）。

## 4. 对既有设计的修正

| # | 原假设 | 实测结论 | 影响 |
|---|---|---|---|
| 1 | 附件 value 是 `[{file_token:...}]` | **是 `["<下载URL>"]`** | 解析器已修正；PDF §4.1 的旧说法作废 |
| 2 | 附件下载可能需 `extra` 鉴权 | **不需要，直链即可** | T5 关闭；实现更简单 |
| 3 | 表单里可能没有附件控件 | **三个附件槽齐备且都在用** | T3 关闭；**前端零改动** |
| 4 | 三单匹配全靠 OCR 抽字段 | **表单自带 `费用汇总` + `费用明细(日期/金额)`** | 匹配升级为"**声明值 vs 单据值 核对**"，可信度更高、实现更简单 |
| 5 | 金额字段可写 | **`费用汇总` 是 `formula`（只读）** | **绝不能作为写入目标**；金额若需回写，用别的普通字段 |
| 6 | 发票都是 PDF | **确认 100% PDF** | `pdf2png` 提到必需组件 |
| 7 | 附件最多 1 张/槽 | **可能多张** | 匹配层要支持一对多 |

### 4.1 关于"声明值 vs 单据值"（第 4 条的价值）

表单里的 `费用汇总` 和 `费用明细` 是**队员申报**的金额与日期。
发票/订单/付款三张图是**证据**。所以三单匹配真正要做的是：

```
队员申报的金额与日期  ──比对──  三张单据抽出的金额与日期
        │                              │
   费用汇总 / 费用明细            视觉模型抽取结果
```

这比"从三张图里各自猜出金额再互相比对"**可靠得多**，因为**申报值本身就是一个锚点**。
而且申报值与实际不符时（虚报/漏报），正是最值得报警的情形。

## 5. 遗留的坑与待办

| # | 事项 | 说明 |
|---|---|---|
| 1 | **实例列表限流严重** | `99991400 request trigger frequency limit` 很容易触发；已加客户端限速 + 指数退避重试 |
| 2 | **时间窗 ≤10 小时** | 拉长时间范围会产生海量请求（1 年 ≈ 876 个窗口）。**建议只按需拉最近区间** |
| 3 | **另有非发票的"发票"** | 如"滴滴出行行程报销单" —— 需在抽取 prompt 里区分票据种类，或标记为 `SUSPECT` |
| 4 | `department` 控件的 `open_id` | `od-...` 是部门 open_id，可用于"组别"归类；但**不再需要**，因为部门名就在 `name` 里 |
| 5 | `费用明细` 的 `fieldList` 是否多行 | 样本里都是 1 行；需确认多行时结构（应为外层数组多元素） |
| 6 | 附件 URL 24 小时过期 | 实现时必须**先取详情、立刻下载**，不要分两步隔夜处理 |
