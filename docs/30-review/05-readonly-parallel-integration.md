# 不影响现有审批与自动化的接入方案（只读并行）

> 回答用户 2026-09-12 的诉求：
> 「现在的审批已经有了自动化流程，我们怎么才能不影响他，先不通过但提取信息并做多维表格？」
>
> 关联：`03-approval-routing.md`（审批回流）、`04-approval-test-plan.md`（测试方案）。

---

## 0. 结论：把"读"和"写"彻底切开，风险只有一处

| 动作 | 是否影响现有审批/自动化 | 依据 |
|---|---|---|
| **读审批实例详情 / 表单值** | ✅ **完全不影响** | 纯 GET，不产生任何事件、通知、状态变化 |
| **读审批实例列表**（按定义批量拉历史） | ✅ **完全不影响** | 纯 GET，且**不需要事件订阅** |
| **订阅审批事件**（只读接收） | ✅ **不影响** | 你只是多了一个观察者；飞书为订阅方单独投递 |
| **往【你自己的】多维表格写** | ✅ **不影响现有** | 不同文档 → 不触发现有表的自动化 |
| **往【现有的那张】多维表格写** | ❌ **会触发其自动化流程** | 自动化触发器是"添加/修改记录时" → **这是唯一的真实风险** |

**一句话**：**读永远安全，写只写自己的表。** 只要不碰现有的那张表，就不可能影响它。

### 0.1 「先不通过但提取信息」——可行，且证据充分

已核实（[获取单个审批实例详情](https://open.feishu.cn/document/server-docs/approval-v4/instance/get.md)）：

- 接口返回体里**同时**包含 `status` 与 **`form`（审批表单控件 JSON 字符串）**；
- `status` 在审批中时就是 **`PENDING`** —— **表单值在待审状态下就是完整的**；
- 该接口是 **GET / 只读**，**不改变实例状态，不产生事件**。

**所以你不需要"让审批通过"、也不需要"驳回"来拿数据** ——审批还挂在待办里，信息就已经能取到。
（生产场景下这个特性还顺带解决了"审批周期长，但账要先记"的问题。）

### 0.2 已核实的两个额外收获

| 发现 | 说明 |
|---|---|
| **`approval:approval:readonly` 权限** | [实例详情](https://open.feishu.cn/document/server-docs/approval-v4/instance/get.md)与[实例列表](https://open.feishu.cn/document/server-docs/approval-v4/instance/list.md)的权限要求都列出「访问审批应用(`approval:approval:readonly`)」。**这是正式、最小化的只读接入路径**，比申请 `approval:approval`（含创建/更新/删除）更安全 |
| **`instance/list` 可按定义批量拉历史** | `GET /approval/v4/instances?approval_code=...`（`page_size` 1–100）。**不需要事件订阅**就能把该定义下的全部历史实例拉下来 → 适合**一次性回填**，也适合验证"我能不能正确解析这张表单" |

补充：实例状态枚举为 `PENDING / APPROVED / REJECTED / CANCELED / DELETED`；任务状态另有 `TRANSFERRED / DONE`。
**`DELETED` 只能删实例，没有 API 可删**（`instance/cancel` 存在＝可撤回，`instance/delete` 为 404）。

## 1. 触发源已确认：**「审批通过」** —— 结论与三条铁律

**用户已确认（2026-09-12）**：现有副作用的触发源是「**审批通过**」。

由此得到三条**可以写进代码约束**的结论：

| # | 结论 | 推论 |
|---|---|---|
| **1** | 它**不会**因为我们读审批实例、拉历史列表、订阅事件而被触发 | 读操作仍然完全安全 |
| **2** | 它**会**在**任何一条该审批定义的实例转为 APPROVED** 时触发 | → **测试期绝不能让"现有定义的实例"被审批通过**。最安全的做法是**完全不碰现有定义**：另建独立定义，自己发起自己审 |
| **3** | 它执行的**下游动作**（写旧多维表格）与**本项目要做的事完全重叠** | 用户已裁定：**跑通后旧自动化下岗**；且**旧多维表格也不能写**（见 §1.1） |

### 1.1 用户已裁定的两条边界（比"不影响"更强）

> **①「跑通后之前的自动化下岗」** —— 旧自动化是**待退役**组件，不是需要长期共存的邻居。
> **②「之前的多维表格也不能写」** —— 旧表**只读**，本项目**任何阶段都不写它**，连字段级追加都不做。

**这两条把方案简化了**：不需要设计"与旧自动化共存"的复杂协调，只需要**在跑通前保持零接触**。
代价是：测试期**不能**用旧表当数据源或展示面 → 只能落在你个人文件夹的测试表（已在做）。

### 1.2 唯一残留的技术风险：**事件串流**

应用级订阅会收到**该应用订阅过的所有审批定义**的事件。若日后订阅了现有定义，
则"现有审批通过"也会推到我们的长连接。代码里**必须按 `approval_code` 过滤**：

```go
const testApprovalCode = "<新测试定义的 code>"

func onApprovalInstance(ev Event) error {
    if ev.ApprovalCode != testApprovalCode {
        // 不是我们要处理的定义 —— 记录一条日志后【丢弃】，不落账、不通知、不写任何表
        log.Info("skip foreign approval", "code", ev.ApprovalCode, "instance", ev.InstanceCode)
        return nil
    }
    ...
}
```

> **过渡期规则**：**上线前不要订阅现有审批定义**。只订阅我们自己的测试定义 →
> 从物理上就不可能收到现有审批的事件，串流风险为零。

### 1.3 目标架构（据"触发源 = 审批通过"重新校准）

这条信息**校准了架构判断**：既然副作用挂在"审批通过"上，那么**本项目要做的正是"审批通过之后那一段"**，
旧自动化所做的"通过 → 写表"就是我们要**取代**的那一段。因此回流路径必须完整实现：

```
队员提交（飞书表单 / 测试表）
   │
   ▼ M1 intake ──► submission + 3×image_sha256（本地库）
   │
   ▼ M2 evidence ──► SiliconFlow Qwen3-VL 抽取 → L1–L4 匹配 → 缺陷清单
   │
   ▼ 创建【我们自己的】审批实例（灌 submission_id / amount / match_summary / defects）
   │
   ▼ 审批人（测试期=你自己）通过
   │
   ▼ approval_instance 事件 ──► 过滤 approval_code ──► 幂等 ──► 状态机
   │
   ├─► M3 ledger 落账（本地权威）      ← 这一段【取代】旧自动化
   ├─► M4 budget 占用→已支出
   └─► M6 outbox ──► 写【新测试表】镜像    ← 绝不写旧表
```

**注意一个此前的判断需要修正**：如果现有流程里"队员提交"用的是**审批表单本身**（而不是多维表格表单），
那么"我们自己创建审批实例"（`03-approval-routing.md` 的方式 A）就不适用——
因为申请人是队员、不该由服务代建。这种情况下应改为
**队员在飞书审批里发起新定义 → 服务订阅该定义 → 服务补充信息与匹配结论**。
**这一点需你确认现有流程的提交入口**（见 §5）。

## 2. 分阶段方案（风险严格递增，每阶段独立可停）

### 阶段 1 · 纯只读接入（**零副作用，建议立刻做**）

**做什么**
1. 申请 `approval:approval:readonly`（最小权限，不含创建/更新/删除）；
2. 调 `instance/list` 拉取现有审批定义的**历史实例**；
3. 对每条调 `instance/get` 取 `form`，解析出字段；
4. 全部落**本地 SQLite**（不写飞书任何表）。

**产出**：一份"现有审批表单长什么样"的真实样本集 → 用于写解析器、并回答"我们缺哪些字段"。

**保证**：不发消息、不写信、不建实例、不改状态。**对现有流程的影响是零，可随时中断。**

> 这一步还有独立价值：**注册审批事件需要先订阅定义**，而 `instance/list` **不需要订阅**就能拿到历史，
> 等于在"动订阅"之前先把数据摸清。

### 阶段 2 · 测试表入库（**零风险**）

在**你个人文件夹**新建测试多维表格（4 张表，见 `04-approval-test-plan.md` §4.2），
把阶段 1 解析出的结构化数据写进去；**同时**把应用加为该文档/文件夹的协作者。

- 写入**只落个人文件夹的表** → 与现有表物理隔离；
- **先别开高级权限**，隔离权限变量。

### 阶段 3 · 关联到新审批定义（**低风险，需要你真发起一次**）

建**独立的测试审批定义**（不要复用现有的定义）→ 订阅 → 起一次真实实例，验证事件回流。
此时才**第一次产生真实副作用**（一条待办 + 通知）→ **发起人 = 审批人 = 你自己**。

### 阶段 4 · 与现有审批的关系（**待决策，不要现在做**）

`03-approval-routing.md` §4.2 已指出：**已有的审批实例表单值不能改，且表单里没有我们的关联键**。
所以要"接管"现有审批，必须先选定一种对接方式：

| 方式 | 做法 | 代价 |
|---|---|---|
| **R1 纯并行（最安全）** | 只读订阅现有定义，本地按 `instance_code` 关联；**不往表单塞结论** | 财务看不到匹配结论（只能靠卡片补充）；**依赖现有表单的字段名不变** |
| **R2 加一个隐藏字段** | 让管理员在**现有定义**里加一个只读文本控件承载 `submission_id` | 需要改**现有定义**（会走审批管理后台的变更流程）→ 有影响，需评估 |
| **R3 你来创建实例** | 队员提交 → 你的服务创建**新定义**的实例 | 与现有定义并存，需**明确二者主从**，否则重复审批 |

> **用户已裁定，本节降级为历史记录**：不做 R1/R2/R3 三选一，而是**新建独立定义 + 跑通后旧自动化下岗**。
> 因此正确姿势是：**阶段 1–3 完全不碰现有定义**（连 R1 的"订阅现有定义"都暂不做），
> 先把新链路端到端跑通；等新链路稳定，再决定是否需要读旧数据做历史迁移。

## 3. 无论做哪一阶段，这四条纪律都不变

1. **只申请 `approval:approval:readonly`**，暂不申请带写权限的 `approval:approval` / `approval:instance`。
2. **不订阅 `drive.file.bitable_record_changed_v1`**（多维表格记录变更事件）—— 这是唯一会让我们"感知并可能反应"到现有表变更的订阅，**明确不要开**。
3. **绝不往现有的多维表格写入**，任何字段都不写（包括"只加个组"这种想法）。
4. **事件按 `approval_code` 过滤**：应用级订阅会收到所有已订阅定义的事件，串了会算错账。

## 4. 验收标准（阶段 1，全部可测）

| # | 验收项 | 通过标准 |
|---|---|---|
| B1 | 拿到现有定义的历史实例 | `instance/list` 返回条数与审批后台一致 |
| B2 | 能解析出全部表单字段 | `form` JSON 里每个控件都有 `id`/`name`/`type`/`value`，且**人与单据能对上** |
| B3 | 能识别关联线索 | 判断出**现有表单里有没有可作为关联键的字段**（如工号/单号/时间戳）；没有则记录"缺关联键" |
| B4 | 对现有流程零影响 | 该表的记录数、自动化执行次数、发出的消息**完全未变** |
| B5 | 审计结论 | 明确写出"A/B/C 属于哪一种触发源"+ 是否存在**功能重叠** |
