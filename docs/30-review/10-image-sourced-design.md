## 0. 反转的含义

**之前**（我在 `09-recon-findings.md` 里当成"意外收获"的）：

```
队员申报值（费用汇总 / 费用明细）  ──比对──  三张单据抽出的值
         ↑ 当作锚点
```

**现在**：

```
三张单据抽出的值  ──互相核对──  这就是三单匹配
（申报值完全不参与）
```

### 0.1 这个决定是对的，理由有三条

| # | 理由 |
|---|---|
| 1 | **申报值本来就不可信** —— 它是队员手填/表单算的。若用它当锚点，等于"用被检验对象去检验自己" |
| 2 | **绕开只读字段问题** —— `费用汇总` 在审批里是 `formula`（只读）、在表里是数字；不管哪种，我们都不再需要它，**"绝不能写入公式字段"这条约束自然消解** |
| 3 | **管线不再依赖表单结构** —— 只依赖三个附件槽 + 几个分类字段。表单将来改字段，识别管线不受影响 |

### 0.2 代价（要接受）

| 代价 | 说明 | 缓解 |
|---|---|---|
| 失去"申报 vs 实际"的差异告警 | 不再能自动发现"队员报了 228 但单据是 300" | 三单互相核对仍能发现**单据之间不一致**；申报值仍留在飞书原表里，事后可人工比对 |
| 完全依赖识别准确率 | 识别错 = 数据错 | 因此**必须**保留"读不到就留空、禁止猜测"的硬约束，并把低置信度标为 `SUSPECT` |
| 金额来源需要唯一化 | 三张图可能给出三个金额 | 见 §3.2 的分层策略 |

## 2. 两个新发现

### 2.1 ★ 那张表的 URL 字段**不能当图源**（实测 404）

表里 `发票文件`/`订单截图`/`付款截图` 是**超链接(15)**，值形如：

```
https://www.feishu.cn/approval/admin/previewAttachment?key=<base64>
```

**实测 HEAD → HTTP 404。** 结论：

| 来源 | 形态 | 可用性 |
|---|---|---|
| **多维表格 URL 字段** | `www.feishu.cn/approval/admin/previewAttachment?key=...` | ❌ **404，不可用**（面向 Web 管理后台，需会话） |
| **审批 API 附件** | `internal-api-drive-stream.feishu.cn/.../download/authcode/?code=...` | ✅ **HTTP 200，直接 GET** |

→ **图片只能从审批 API 取**，不能从多维表格取。这反过来确认了"必须有本地服务订阅/回读审批"这一架构。

### 2.2 ★ `SourceID` 里藏着 `instance_code`

表里的 `SourceID` 是 base64，解码后：

```
7665354950683151343 : <APPROVAL_CODE_OTHER2> -1 : daba753ea822698121472f99d25c9c8f : 1
       ↑ 表/租户标识          ↑★ 这就是 approval instance_code        ↑ 节点序号   ↑ hash
```

**用途**：多维表格的一行 ←→ 审批实例的**反查通道**。
在只读期若要拿"现有表某一行对应的审批实例"，靠它就能定位，不用猜。

> ⚠️ 注意 `申请编号` 的 applink 里也有 `instanceId=7600309640437468348` —— 那是**数字 ID**，
> 与审批 API 的 `instance_code`（UUID 形式）**不是同一个东西**。**用 `SourceID` 那个**，不要用 applink 的数字。

## 3. 对齐后的表设计

设计写在 `finance-router/internal/bitable/schema.go`，用 `go run ./cmd/bitable-schema` 输出。

| key | 表名 | 字段数 | 说明 |
|---|---|---|---|
| `submission` | **报销记录** | 23 | 一行一审批实例；字段名对齐真实表 + 图读结果 |
| `evidence` | **识别证据** | 19 | 一行一张图（PDF 一行一页） |
| `invoice_dedup` | **发票唯一性** | 9 | 本地唯一约束的镜像 |
| `pipeline_log` | **处理日志** | 8 | 事件幂等与状态机验证 |

### 3.1 与旧版设计的差异

| 变更 | 原因 |
|---|---|
| `submission` 字段名改为**真实表命名**（物资所属部门/物资种类/购买人/资金来源/报销类型…） | 便于迁移，不另造一套词汇 |
| `物资所属部门` 从**单选改多选** | 真实表就是多选(4) |
| 新增 `图读金额_分` / `图读日期` / `对方名称` | 落实"全部从图读" |
| **删除** `金额_分`（原用于承接申报值） | 申报值不再参与 |
| 新增 `槽位` / `序号` / `文件名` / `媒体类型` 到证据表 | 一个槽位可能多张图（实测 20 条实例里付款截图有 26 个附件） |
| `图类型` 增加 `itinerary` | 实测存在"滴滴出行行程报销单"，**是行程单不是发票** |
| 原 `审批结果` 表 → 改名 `pipeline_log`，新增 `事件ID`/`处理结果` | 用于验证幂等与状态机 |

### 3.2 三张图金额不一致时以谁为准（需定）

既然三个来源都可能给金额，必须定优先级。建议：

| 优先级 | 来源 | 理由 |
|---|---|---|
| 1 | **发票**（价税合计） | 唯一有法律效力、且带票号可唯一化 |
| 2 | 转账/付款记录 | 实际出账金额，反映真实付出 |
| 3 | 订单截图 | 可能含优惠/运费差，且易被裁图 |

**三者不等时不要静默取一个** —— 应全部记入证据表，并在 `缺陷清单` 写明"发票 328.00 / 付款 320.00 / 订单 328.00，差额 8.00"。
