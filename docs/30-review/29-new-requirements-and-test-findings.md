## 2. 实测：测试实例 `7DB9ADCF…`（状态 pending）

归属组=视觉组，资金来源=个人，**是否为支付宝付款=是**，发票/订单/付款各 1 个。

### 2.1 发票走精确通道 —— 两个通道完全一致

```
文字层（pdftotext -layout）            二维码
─────────────────────────────         ─────────────────────────────────────────
电子发票（普通发票）                    01,32,,<INVOICE_NO>,
发票号码：<INVOICE_NO>                 48.90,20260602,,7014
开票日期：2026年06月02日
购买方：<购买方> / <购买方税号>          [3] 发票号码  <INVOICE_NO>  ✓ 一致
销售方：<销售方> / <销售方税号>          [4] 金额      48.90                 ✓ 一致
价税合计（大写）肆拾捌圆玖角整            [5] 开票日期  20260602              ✓ 一致
           （小写）¥48.90
开票人：<开票人>
```

**发票信息不需要"识别"，只需要"读取"。** 这两条通道都是确定性的。

### 2.2 ★ 关键发现：两个强键，以及一个极易搞错的地方

| 截图 | 字段名 | 值 |
|---|---|---|
| 订单截图 | **支付宝交易号** | `<ALIPAY_TXN_ID>` |
| 付款记录（支付宝账单详情） | **订单号** | `<ALIPAY_TXN_ID>` ← **同一个值** |
| 付款记录 | 商家订单号 | `T200P<ORDER_NO>` |
| 订单截图 | **订单号** | `<ORDER_NO>` |
| 发票备注 | — | `<ORDER_NO>` ← **同一个值** |

⚠️ **支付宝账单把"交易号"标成了「订单号」**，而把真正的商家订单号放在「商家订单号」里。
如果按字面去找"订单号"字段，会把两个不同的键混为一谈 —— 表现是"看不出错，但就是匹配不上"。

因此链路是：

```
      支付宝交易号                     订单号（备注）
订单 ──────────────► 付款      发票 ──────────────► 订单
   （确定性）                          （确定性，若能读到备注）
                                          │
                                     读不到备注时
                                          ▼
                                       金额（需求指定）
```

需求说"发票↔订单用金额匹配"。实测发现**发票备注里直接带着订单号**，
这是比金额更强的确定性键。所以建议：
**有备注订单号就用订单号，没有再退回金额。**

### 2.3 金额核对（测试单）

## 3. 强制规则（来自表单与需求）

成员提交时必须满足，**系统在审核前校验**：

| 情形 | 允许的提交形态 |
|---|---|
| 支付宝支付 + **一发票对一订单** | 可上传**多张**发票、订单、付款 |
| 支付宝支付 + **一发票对多订单** | **只允许 1 张发票**，订单可多 |
| 非支付宝支付 | （表单未写明，需确认） |

「是否符合形态」本身是可判定的：看发票数、订单数、以及实际匹配出的分组结果。

## 4. 三阶段流转

```
提交审批
   │
   ├─ 被退回 ──────────────► 剔除（报销核对表里不留）
   │
   └─ 在审 / 已通过
          │  写入「报销核对」表（原数据）
          │
          ├─ 形态合规 且 能匹配 ──► 直接可归档
          │
          └─ 不符合要求 / 无法匹配 ──► 进「报销核对」待人工
                                          │
                          ┌───────────────┴───────────────┐
                      人工「通过」                    人工「退回」
                          │                               │
                   加入「报销整合」              退回审批单 + 从核对表剔除
```

即：**原来的多维表格只记录在审与通过的原数据；退回的剔除。**

## 5. 与现有实现的差距

| 需求 | 现状 | 差距 |
|---|---|---|
| 发票精确提取 | 走 VLM（`tok≈5340/张`） | 需接入文字层 + 二维码 |
| 订单↔付款按交易号 | 无此概念 | 抽取要新增「支付宝交易号」字段 |
| 发票↔订单按金额 | `Compare` **只取 `inv[0]`** | 需支持多张与求和 |
| 一发票多订单的限制 | 无 | 需在审核前校验形态 |
| 在审/通过才入表、退回剔除 | 未按状态过滤 | 需按实例状态决定写入/删除 |
| 核对表人工通过/退回 → 整合/剔除 | `archive` 已实现"通过则归档" | 需补"退回则从核对表剔除" |

## 7. 实施进展与实测修正（2026-09-14）

### 7.1 已落地

- 绑定切到新表单（`approval_code` + `approval_name_expect`）。
- `buildMeta` 改为「名称包含」匹配（新表单控件名带长括号说明）。
- **修 bug**：附件槽位只按名字匹配会被「是否为支付宝付款（…上传多张发票…
  上传多张订单、付款记录…）」这个 radio 控件抢走 —— 它的名字包含全部三个关键词
  且排在附件控件前面。改为先按控件类型过滤。
- 发票走精确通道（文字层 + 二维码），命中则不调模型。
- 「老师垫付」→ 忽略付款记录。注意表单里写的是**垫付**不是"代付"。
- 新增 `alipay_txn_id` 字段。

### 7.2 ★ 实测推翻了"用支付宝交易号配对"

同一笔交易，**三个来源读出三个不同的交易号**：

| 来源 | 读数 | 位数 |
|---|---|---|
| 订单页（VLM, high） | `2026…11416735029` | 27 |
| 支付宝账单（VLM, high） | `2026…111416735029` | 28 |
| 人工看图 | `2026…11416735029` 的真值 | 28 |

28 位纯数字，识别读不稳，**即使把 detail 提到 high**。

同时模型在支付宝账单上**把两个字段填反了**：
把「订单号」（其实是交易号）填进 `order_no`，
把「商家订单号」填进 `alipay_txn_id`，且没去掉 `T200P` 前缀。

**但同一份数据里有更稳的键**：商家订单号（19 位），它同时出现在
- 淘宝订单页的「订单号」
- 支付宝账单的「商家订单号」（带前缀）

而且**两次都读对了**。

### 7.3 改后的方案：按「共有长数字段」配对

`internal/match/keys.go`：把单据里所有 ≥15 位的数字段汇成 `KeySet`，
两份单据**求交集**（取最长共有段）即视为配对。

这样同时对两件事免疫：
1. 模型把值填进了错误的字段；
2. 值上带前缀（`T200P`）或分隔符。

支付宝交易号仍保留在数据里，只作为"两边读得完全一致"时的辅助证据。

### 7.4 detail 必须提

`order`/`payment` 从 `low` 改 `high`：low（256 tok）下订单页的
「支付宝交易号」**完全读不出来**（返回空）；high（2139 tok）能读到。

代价：每实例从 ≈512 tok 升到 ≈4278 tok（发票仍是 0）。
仍低于改造前的 ≈5852，但远高于当初"精确通道"设想的 512。
